# Reproducing and verifying

## Conditions

A reproduction holds constant what the claimed cause depends on and nothing it does not. A deterministic defect in code, a tool, or a script reproduces with a command or test run from a clean state; repeating it a few times confirms that the conditions, not leftover state, produce the failure. Agent behavior varies between runs, so an attempt is a set of fresh runs, and the failure condition is a count over that set fixed in advance ("the agent stops before step 2 in at least 4 of 5 runs"). Five runs per attempt is a common floor; the Split Testing trial runtime reports each rate with an interval so a before-and-after difference can be told from noise. Run-to-run variation is often larger than it looks: one unchanged text can pass a scenario in nearly every run and in almost none in another trial, so a set of consecutive passes after a change shows a heal only beside the unchanged source run in the same trial, twice where the decision is close, since the gap between two copies of one text is how far chance alone moves the counts. Spend runs in stages: the deterministic check or the cheapest decisive comparison first, and model runs only where their result could change what you do.

Start each run from a fresh environment that carries the source under test and the task, and nothing written by an earlier run. Where the source serves several hosts or models, a reproduction on one host speaks for that host.

Reproduce a severe incident that is unsafe to repeat in place, such as a destructive command, in a disposable copy of the environment.

## The check

A check reads resulting state (files, commits, remotes, recorded tool calls, the change's own output) in preference to wording. Before relying on it, run a reference behavior that should pass and one that should fail; a check that passes both or fails both measures something else. Then read a sample of real runs against what the check said about them, since real agents do legitimate things the reference behaviors did not, and keep the check where the agent cannot move it. A check can also be wrong about the requirement: counting every mention of "ask" in a repaired skill counts "without asking" as asking. Correct such a check when the requirement shows it wrong, and keep the correction and its reason with the evidence.

Scenarios written for a reproduction are lasting assets. Add the failing scenario to the set that later changes run against, and keep a few scenarios out of development to test whether a change generalizes beyond the cases that shaped it.

## The trial runtime

For agent behavior, [`trial.py`](../../split-testing/scripts/trial.py) in Split Testing runs each arm on each scenario in isolated homes and working directories, repeats, interleaves, applies checks and an optional blind judge, and keeps every run's native record. The arms are the source before the change, the source after it, and, when the question is whether the source should exist, no source; record whether each run actually read or loaded the source under test, so an unread change is not mistaken for one that failed. Its plan and scenario format are in [trials.md](../../split-testing/references/trials.md).

## How an agent read its instructions

Four kinds of evidence exist, with different weight:

- Exposure. Native session logs record the instruction text actually delivered, including host-provided system prompts, loaded skills, compaction summaries, and tool output. Whether a file existed, whether its text entered the context, and whether the agent said it followed it are three different facts.
- The agent's account at the time. An observation written in the moment records what the agent took its guidance to mean before any outcome was known. It is a self-report, and it covers only what the agent recognized as worth recording.
- A later interview of a forked session. It has the exact context and can state an interpretation, and it remains a self-report. Hosts that keep reasoning private do not disclose it to a fork.
- Replay. Branching the session before the instruction's first relevant exposure, changing that one instruction, and regenerating the rest N times shows whether the instruction influenced the behavior. Unchanged reruns give the baseline variation, and a meaning-preserving rewording separates the instruction's content from its wording. Removing an instruction after it has already shaped a plan tests responsiveness to a late edit, not the instruction's influence.

An account that names an instruction as the reason for a behavior is a hypothesis that replay can test.

## Session logs

`scripts/gather.py [--since 7d|YYYY-MM-DD] [--until YYYY-MM-DD] [--out DIR] [--force] [--root HOST=PATH ...] [--max-chars N]` reads Codex rollouts (`~/.codex/sessions` and `.../archived_sessions`, or under `$CODEX_HOME`), Claude Code transcripts (`~/.claude/projects`, or `$CLAUDE_CONFIG_DIR/projects`), and Gemini CLI chats (`~/.gemini/tmp/*/chats`, both its legacy `.json` and its current append-only `.jsonl` shape), plus the git state of the working directories those sessions used. A session is in the window by its own records' times (its latest at or after `--since`, its earliest before the end of `--until`'s day; `--until` takes a date and refuses a time of day, and the midnight after that date is out), not by when its file was last written: a log is skipped without being parsed only if neither its file's time nor its own last record (read from the end of the file) is from `--since` on, and a file's time decides alone only for a session whose records carry none. A log whose last records and file's time both predate the window is skipped unread, so a recent record placed before older ones in such a file is not seen (an accepted limit). With no `--out` it writes to a new private (mode 0700) temporary directory and prints that path; an explicit `--out` that already has content in it is refused unless `--force`. It writes an index and one faithful, timestamped transcript per session, named for its host and a hash of its raw log's path, so that no masking touches the name and no two logs share a file (the index says which session each is; a Claude subagent transcript shares its parent's session id). A transcript has user messages (including those typed while the agent was working), agent messages, the reasoning in Claude Code's thinking blocks that carry text, tool calls and results, compactions, hook output, and, from Claude Code logs, a line naming each instruction file and skill that reached the agent without quoting it. Provenance outranks content: text an agent or a harness wrote is not shown as the user's where the log says so, though a log can store it as a user message. A compaction's summary, the brief that starts a subagent or side thread, and what the delegating side or the harness sends it afterwards are labeled lines of their own, and a background-task notice and a message from a coordinator or another session are event lines. A record a person wrote stays the user's message, counted, whatever its text begins with (a person may paste a system reminder, an AGENTS.md, or a state snapshot for review); where it begins with a block the harness may have added, the line says so and keeps all of the text. Content alone labels a record only where nothing says a person wrote it: a Gemini user message that begins with the CLI's own state snapshot is a `message whose author the log does not record` line with all its text, because that log does not say who wrote a user message (the CLI writes its own summary so, and a person may type one, or a request after it), and the index counts it in its last column as unattributed, neither the user's nor the agent's. Any other record is a note naming its type, never dropped; consecutive notes share one line with each type's count and where in the raw log they come from (the range of raw lines and of message numbers, as the run has them), and the raw log is named once, in the transcript's header. It also writes a workspace file of each repository's branches, worktrees, and stashes, and any scheduled automations it can find, as facts only. It does no counting-as-interpretation of what a message means; masks token-like strings, keys, bearer/basic/URL credentials, and key=value or JSON-shaped assignments (a quoted value to its closing quote, however many words it has) in everything it writes, paths and references into raw logs included, while leaving a bare 40- or 64-character hex string (a git SHA, a sha256 digest), a Codex rollout's file name and a host's encoded working-directory name (unless a word in it is token-shaped) unmasked as evidence a pass needs to check state. A text is masked whole and then cut to `--max-chars`, and every JSON object and array in it, and every string with an escape in it (a document encoded again is one), is decoded and masked as the values it holds, whatever escapes it uses and however long it is, within bounds: to 100 levels of nesting, and until the brackets that look like the start of JSON and are not count more than a thousand, and one more for every 128 characters of the text, each counting one more for every 2,048 characters from it to where the decoder failed; past a bound only the patterns see an escaped secret, and they follow a quote escaped up to five levels. Masking recognizes the shapes secrets commonly have; it cannot catch every secret, so the output is as sensitive as the logs it came from.

Codex logs keep reasoning encrypted, and their readable summaries are short headings, so the agent's own account of its interpretation exists only where it wrote one.
