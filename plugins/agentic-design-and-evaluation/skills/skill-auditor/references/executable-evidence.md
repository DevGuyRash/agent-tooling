# Executable Evidence

You SHOULD judge the behavior the actual user or host receives. You SHOULD establish the mechanism's permitted effects, protected state, inputs, outputs, failure meaning, and consumer boundary from the target and adopted authority. A passing helper or normal example is partial evidence when a consequential promise concerns composed behavior.

You SHOULD use source inspection and observations capable of falsifying material claims. A successful exit can accompany the wrong object changing, a skipped effect, an unusable result, or partial work hidden by a wrapper. Where state transitions matter, before/after evidence can reveal what an exit code or destination file misses. Relevant refusal, partial failure, retries, and concurrency depend on the actual reachable contract, not a stock checklist.

One recurring historical blind spot involved caller-selected roles that resolved to the same underlying object: changing the allowed role also changed protected state. Separate parameter names, paths, or preflight branches did not preserve the intended authority boundary. When a target's actual design makes aliasing, indirection, shared backing state, or replacement plausible, a bounded probe can resolve that concern. The historical result does not require an aliasing experiment or a fresh observer for every executable audit.

You SHOULD choose a safe observation boundary within the mandate. Disposable copies or faithful simulations can support mutation tests without affecting protected or live state. A simulation establishes only what its fidelity supports. If the necessary effect is unauthorized or cannot be observed safely, you SHALL retain the material gap rather than treating inspection as execution or crossing the permission boundary.

You SHOULD check the instrument as well as the target. An auditor-chosen working directory, interpreter, argument, or environment can create a failure the host would never produce; it can also hide a real dependency. Execute through the actual consumer's declared interface when that boundary controls the claim. You SHALL keep raw outputs sufficient to distinguish target behavior from capture, infrastructure, and checker failures.

A second observer can be useful when a distinct unresolved property would benefit from separate attention and participation is authorized. You SHALL give it legitimate authority, original material, and the needed evidence boundary. Another context is not automatically isolated or independent, and this skill requires no extra participant.

For a repair, you SHALL preserve the failure evidence and verify the changed property alongside consequential adjacent behavior. A narrow edit can still have broad effects. A proposed explanation needs evidence that distinguishes it from plausible alternatives before it becomes a causal or generalization claim.
