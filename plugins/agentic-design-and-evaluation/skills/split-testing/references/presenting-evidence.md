# Presenting evidence

A report is optional: use one when a reader needs to inspect, decide from, or return to the evidence, and let a short answer stand when it serves.

For a trial, run `trial.py report RUN_DIR --out trial.json`, then `assets/visuals/report.py --skeleton narrative.json --trial trial.json` to start the narrative (every arm and case id spelled as the trial records it), then `assets/visuals/report.py --trial trial.json --narrative narrative.json --output report.html`. The narrative carries the decision you reached by applying the plan's rule, readable labels for arms and cases, the arms that received identical material, and any extra sections; the composition already shows what was compared (the arms' settings and instruction texts, with the differences between texts), each case's task and pass criteria, every run, why runs failed, invalid runs, intervals, differences from a baseline, checks, pairwise judgments, and cost. The [visual library catalog](../assets/visuals/catalog.md) describes the narrative, every block for a specification of your own, and what each view keeps faithful; [packaging reports](../assets/visuals/PACKAGING.md) covers custom compositions, the offline contract, and checking a file before delivery; [Mermaid diagrams](mermaid-diagrams.md) and [qualifying visuals](qualifying-visuals.md) cover diagrams and checking rendered views. The library offers views; it never decides what the report says or requires every one.

For any other comparison, write the evidence as comparison data and let the composition show it: `assets/visuals/report.py --data comparison.json --output report.html`, or `--csv table.csv` for a long table with one observation per row (columns `alternative`, `metric`, `value`, and optionally `case`, `group`, `unit`, `n`, `valid`, `note`, `source`, `invalid_reason`, `excerpt`). The data names the alternatives (with nested groups, settings, and the text compared), the cases, the metrics (kind, which way is better, unit, threshold), the observations or, where only totals exist, aggregates, head-to-head preferences and rankings, the baseline, the alternatives given identical material, and the decision rule fixed before results. `report.py --skeleton narrative.json --data comparison.json` starts a narrative with every id spelled as recorded; the narrative adds the decision, labels, extra sections, and the criteria of a decision matrix, whose weights are the decider's own. A comparison needs only the parts it has: a few ratings and a verdict make a complete report. A trial can also be read through these general views with `report.py --trial trial.json --general`, where its narrative is a comparison narrative; the trial composition stays the richer default for trial data. The [catalog](../assets/visuals/catalog.md) describes the data fields and every view.

Open with the question and the decision, with enough purpose and context for the reader to know what was compared and why. Put the conditions that could change the decision beside it, then order the rest around the reader's decisions. Explain the practical question and finding in ordinary language while keeping exact measures, units, source identities, and distinctions.

A view is faithful when it keeps failures, missingness, ties, vetoes, and invalid runs visible; invents no scores, weights, rankings, or uncertainty; reads a pooled result beside the parts it pools, since a pool over unequal coverage can mislead; keeps development findings apart from fresh confirmation; and lets the reader reach the native record behind each consequential claim. Aggregation, collapsed content, ordering, color, and interaction are part of the evidence: an attractive overview that hides a consequential exception is inadequate. Color reinforces a distinction that words or marks also carry.

Choose views from the evidence: requirement coverage, paired observations, distributions and tails, changes across rounds, trade-offs, qualitative excerpts, objections, provenance, and cost are common, and none is mandatory.

A standalone HTML report is one self-contained file with its styles, scripts, data, fonts, and images embedded, so it opens offline without a server or build step; the working files and native evidence stay in the run or context directory. Before delivering it, run `report.py --check` on its inputs, then open it from an unrelated location without network access and check values, missingness, layout, keyboard access, and safe display of untrusted evidence text. A report that renders correctly says nothing about whether its analysis is valid.
