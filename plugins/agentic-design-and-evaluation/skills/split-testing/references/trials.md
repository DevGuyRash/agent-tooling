# Trial runtime

`scripts/trial.py` runs every alternative (an arm) on every scenario a set number of times, each run in its own fresh home and working directory, in an interleaved order, and summarizes pass counts with 95% Wilson intervals. You write the plan and scenarios for the question; the runtime owns isolation, confinement, repetition, the per-run record, blind judging, and aggregation. [Trial flow](trial-flow.md) pictures these stages and what each guarantees. An arm's instructions can brief a chef, an artist, or a business analyst as easily as an engineer, and a `command` arm can run any non-agent tool.

```bash
python3 <skills-file-root>/scripts/trial.py run PLAN.json [--jobs 6] [--repeats 5] [--only s1,s2] [--arms a,b] [--sandbox confined|none]
python3 <skills-file-root>/scripts/trial.py summarize RUN_DIR [--baseline ARM]
python3 <skills-file-root>/scripts/trial.py pairwise RUN_DIR --arms A,B [--judge-model MODEL]
python3 <skills-file-root>/scripts/trial.py report RUN_DIR [--out FILE] [--baseline ARM]
python3 <skills-file-root>/scripts/trial.py latest 'model-*' IDS.txt
```

Runs land under `~/.cache/agent-trials/<plan>-<timestamp>/` by default; the runtime refuses an output directory inside a git repository, because executors would otherwise pick up that repository's instructions. Rerunning with the same `--out` reuses finished runs and replaces partial ones, including a `result.json` the runner never finished writing, and scores the runs a [host executor](#host-executor) left awaiting. Every run records its arm's executor, model, effort, `base_url`, instructions digest, resources digest (below), a launcher's script digest and its `hide` and `watch` lists, and a command arm's command (executors read a copy of the instructions kept in the run directory, so the digest is what every run received), and the judge that scored it (its executor, model, effort, `base_url`, and a launcher judge's script digest; an arm's own judge when it names one, see [Plan](#plan)); a rerun whose arm or judge differs from those records is refused, so one run directory never mixes models, instructions, launchers, resources, or judges. Each run also records the conditions it was made under (`conditions` in its `result.json`): a digest of what its scenario gives it (scenario.json's fields other than the scoring ones, the fixture as the run receives it, `setup.sh`, and the fake tools), a digest of what scores it (`required`, `judge`, `judge_role`, `judge_required`, `timeout_fails`, `unclear_fails`, `artifact`, and `check.py`, though not a helper `check.py` imports), the sandbox its process ran in, a launcher's `binary` as digested after following its links (an executor that updated itself is another executor), and the arm's `readable` paths, `copy` home paths, and `pass_env` names. A rerun whose selected arms and scenarios would now run under other conditions than their stored runs, finished or awaiting the host, is refused; when only what scores them changed, `trial.py recheck` re-scores the stored runs, after which the rerun goes on. What `env_file`, `api_key_var`, a `pass_env` variable, a `readable` path, or a `copy` file holds is not compared, since a key or a sign-in can change without changing what a run measures. A directory whose runs record no conditions (written by an earlier trial.py) is not rerun into, though `summarize`, `report`, `recheck`, and `pairwise` read it as before; and when runs of one arm on one scenario record different conditions (a fixture edited, or an executor that updated itself, while the trial ran), `summary.md` names them in its header. One `run` or `recheck` uses a directory at a time.

## Plan

```json
{"name": "kernel-screen", "repeats": 5, "seed": 1, "sandbox": "confined", "baseline": "none",
 "arms": {"none":   {"executor": "launcher", "script": "launchers/my-agent.sh", "binary": "my-agent",
                     "model": "${TRIAL_MODEL:-model-a}", "effort": "high"},
          "kernel": {"executor": "launcher", "script": "launchers/my-agent.sh", "binary": "my-agent",
                     "model": "${TRIAL_MODEL:-model-a}", "effort": "high", "instructions": "arms/kernel.md"},
          "kernel-b": {"executor": "launcher", "script": "launchers/other-agent.sh", "binary": "other-agent",
                       "model": "model-b", "base_url": "https://proxy.example", "instructions": "arms/kernel.md"},
          "kernel-hosted": {"executor": "host", "model": "the host's own agent", "host_env": true,
                            "instructions": "arms/kernel.md"}},
 "judge": {"executor": "launcher", "script": "launchers/other-agent.sh", "binary": "other-agent", "model": "model-b"},
 "scenarios": ["scenarios/gate-deploy", "scenarios/pr-no-merge"]}
```

Plan-level fields beyond `name`, `repeats`, `seed`, `arms`, `scenarios`, and `judge`:

- `sandbox`: the default confinement for a scenario that names none of its own (`"confined"` or `"none"`; see [Confinement](#confinement)). `--sandbox` on `run` or `recheck` overrides it for that invocation and is then stored as the directory's new default.
- `baseline`: the arm `summarize` (or the `run`/`recheck` summary it writes), and `report`, compare other arms' cost and timing against as a percentage; `--baseline ARM` on `summarize` or `report` overrides it for that call.
- `pairwise`: `{"arms": ["A", "B"]}` names the default pair `trial.py pairwise RUN_DIR` compares when called with no `--arms` (see [Pairwise judging](#pairwise-judging)).
- `decision_rule`: free text stating how to decide between the arms once the numbers are in (for example, "ship whichever arm has no scenario below 90% and costs less"); `report` carries it through verbatim for a visualizer to show, and draws no conclusion of its own either way.
- `prune_build_output`: `false` keeps a finished run's own regenerable build output (a Cargo `target/`, a Go or npm build cache, `__pycache__`) instead of pruning it by default once that run's checks and judge finish (see [Reading results](#reading-results)); `TRIAL_PRUNE_BUILD_OUTPUT=0` (or `false`) in the environment keeps it too, whatever the plan says.

An arm may carry its own `"judge"`, with exactly the shape the plan's takes, which scores that arm's runs in place of the plan's; an arm without one is scored by the plan's. One plan can then judge each family of executors with a judge from another family, so that no arm shares a family with its judge, where a single judge would share a family with some of the arms. An arm's judge accepts and validates everything the plan's does (a `host` judge too, asked of that arm's runs only), is resolved and recorded in `plan.json` the same way, and scores only its arm's runs, each of which records the judge that scored it; a rerun whose arm's judge differs from the one that scored that arm's stored runs is refused, naming the arm. A judged scenario's run whose arm and plan name no judge is `judge-missing`. Between two arms judged by different judges, a difference in pass rate may come from the judges as well as the arms, since judges differ in how strictly they read the same question: compare arms that share a judge, such as one family's arms with each other, and let the deterministic checks decide between arms that do not.

The settings fields `model`, `effort`, `base_url`, `binary`, `env_file`, and `api_key_var` of arms and judges (the plan's and an arm's own) expand `${VAR}` and `${VAR:-default}` (without nesting; a command arm's `command` does not expand, because its `$TRIAL_*` variables belong to its shell), and a field other than `model` that expands to nothing is unset (an empty `model` is an error). Expanded values are recorded verbatim in the run directory, in `plan.json` and in each run's `result.json`, and can appear in error messages, so put a key only behind `env_file` and `api_key_var`; an arm records its model as written as `model_spec` when it expanded to another. A launcher names its model exactly: a `latest:` model is refused, since the runtime asks no endpoint which models exist. `trial.py latest GLOB IDS.txt` picks the newest from a list of model IDs you obtained (one per line, from your provider's own listing): each `*` (at most three) is a version number (`5-5`, `6.1`; from a date stamp of four or more digits on, a version only breaks ties), so `'model-*'` picks the newest version and never a variant such as `-thinking`, and a family sharing a non-numeric suffix is named by including that suffix after the last `*` (for example `'*-preview'`). Name the exact model it prints, which keeps a comparison reproducible across run directories.

A host arm or judge that names no model records `unknown`.

Each run's directory is `runs/<scenario>__<arm>__r<repeat>`, named by its scenario (its scenario.json's `name`, else its directory's name) and its arm, so a name is letters, digits, `.`, `-`, `~`, and single `_` between them, starting with a letter or digit, at most 100 characters; the runtime refuses any other name, and two scenarios of one name, before it writes anything.

Scenario, `instructions`, `script`, and `env_file` paths are relative to the plan; `~` expands. An arm's `instructions` file reaches its executor as its launcher places it, as standing instructions where the executor has them (see [launching](launching.md)); a host's controller places it as the host can, and a command arm gets its path in `TRIAL_INSTRUCTIONS`. Executors:

- `launcher`: a script you write for whatever agent command line you can run, which the runtime runs once per turn inside its confinement, with the trial's inputs hidden, after probing it; the run is scored from the record the script writes. [Launching executors](launching.md) gives the contract, the record, what the runtime enforces, the probe, and the questions to answer about your executor. A launcher can also be a judge. `binary` names the executable it starts, found the way a shell would find it (`~` expanded, then a bare name looked up on `PATH`; never an install-path guess), and its install is made readable inside confinement; `readable` lists extra host paths (for example a toolchain under `$HOME` such as `~/.cargo/bin` and `~/.rustup`) a confined run can read and use — name the narrowest directory that actually holds what the arm needs, since a path listed here is exposed exactly as given: `~/.cargo` as a whole, for instance, also holds `credentials.toml`.
- `command`: a shell command, for non-agent comparisons (scripts, builds, tools, or any deliverable a `check.py` can inspect) and for qualifying checks. It receives `TRIAL_PROMPT`, `TRIAL_SCENARIO_DIR`, `TRIAL_JOB_DIR`, `TRIAL_INSTRUCTIONS` (the arm's instructions file, if any), `TRIAL_REPLY`, and `TRIAL_RECORD`; `readable` and `confine: false` (skip confinement for this arm) work as above. A command arm is no agent: when it writes no record, the run holds no agent action, and when it writes one (a reference behavior recording what it did, see [Qualifying checks](#qualifying-checks)), the run is read from it as a launcher's is, and a record saying `"finished": false` makes the run `unfinished`.
- `artifact`: no model call. `"artifact"` names a file or directory, relative to the plan, that *is* the alternative — a business plan, a recipe, a design, a pitch, anything a person or a judge can read. It is resolved and digested like a resource (a rerun that would judge different content under the same arm name is refused; a single file's name counts, since the run receives it under that name), frozen under the run directory when the trial starts (a source that changed after the plan loaded refuses the run), and copied into the run's working directory unchanged. A single-file artifact's own text becomes the judged output directly; a directory with more than one file gives every file's content, each under a `--- relative/path ---` line, unless the scenario's own `"artifact"` field (below) names one file inside it precisely. An artifact a judge cannot read as text, such as an image, is judged only through evidence the scenario's `check.py` gives (`judge_context`); otherwise its runs are `judge-unassessed` (see [Scenario](#scenario)). Its run holds no agent action. Write a scenario for artifact arms as an evaluation context, not a task: its `prompt` frames who is judging and against what (an investor, a home cook, an accessibility reviewer), and its `judge` question asks what that reader wants to know.
- `host`: no process. The host that runs `trial.py` starts the executor by its own means, such as its subagent tool or an app's agent feature, so an arm can run where no command line here reaches its executor (see [Host executor](#host-executor)). Its `model` is free text, recorded as given, or as `unknown` when absent; `"host_env": true` says the host runs the executor's commands in the environment `dispatch.json` gives it.

Any arm (or the judge) can also list `pass_env`: names of extra environment variables to pass into its run from this process's own environment, on top of the fixed allowlist (see [Confinement](#confinement)).

An arm's `"resources"` is a map from a path relative to the run's private home to a file or directory relative to the plan, copied read-only into that home before the run starts — a skill, a reference doc, a settings file the launcher reads, or anything else an arm's instructions can point the agent at by a fixed path. Each source is resolved and digested like `instructions` (a directory's digest covers every entry's path and kind, each file's content and executable bit, each link's target, and empty directories; a link that leads out of the source, or a special file such as a FIFO, is refused), so a rerun that would give the same arm name different resource content is refused (`stub_skills`, under [Selection trials](#selection-trials), adds generated skills the same way), and is frozen under the run directory (`resources/<digest>/`) when the trial starts, so every job receives the content its recorded digest describes even when a source is edited during a long trial; a source that changed between loading the plan and freezing it refuses the run. For example, to hand an arm a skill it can use, and tell it where to find it:

```json
{"arms": {"kernel": {"executor": "launcher", "script": "launchers/my-agent.sh", "binary": "my-agent", "model": "model-a",
                     "instructions": "arms/kernel-with-skill.md",
                     "resources": {"skills/deploy-helper": "skills/deploy-helper"}}}}
```

where the arm's instructions file names the path in its own text (for example, "A skill at `~/skills/deploy-helper` covers this; read its `SKILL.md` first"). The copy is read-only, so the agent can consult it but not edit the very thing a check might compare its work against.

### Keys

A launcher arm or judge that authenticates with a key names the variable with `api_key_var`, and the runtime finds its value in this order, never in a built-in default file:

1. The arm's own `env_file` — a shell snippet, typically `VAR=value` lines (though `export`, comments, and shell quoting are honored too, since the file is sourced, not parsed literally), read in a subshell outside any sandbox so only that one variable is ever exported to the run (and to nothing else, including this process).
2. Otherwise, `TRIAL_ENV_FILE` (an environment variable naming a file in the same format), when the arm names no `env_file` of its own.
3. Otherwise, the variable read directly from this process's own environment.

That one variable reaches the run (its launcher tells the executor where to find it, as `TRIAL_API_KEY_VAR` says), and a key found nowhere is an error naming all three ways to supply it. A launcher that needs no key names none. `base_url` stays optional throughout: without it, the executor reaches its own default endpoint.

**Logging in without an API key.** An executor that authenticates only through a login on this machine can be given one with the launcher's `"copy"`, which copies the named files (a login file, for example) writable into the run's private home before it starts and removes them after it (see [launching](launching.md)). **This exposes that login to the agent under test**: it is a file in its own home like any other, and the arm's instructions, its tool calls, or a bug in its own code could read or exfiltrate it. Use it only when no API key is available and the user's own words accept that exposure for this trial.

## Scenario

```
scenario.json   {"prompt": "...", "followups": ["continue"], "timeout_s": 900,
                 "required": ["check_a", "check_b"], "bin": ["../_shared/bin"],
                 "artifact": "relative/path",
                 "judge": {"question": "...", "pass_when": "..."}, "judge_role": "...",
                 "judge_required": true, "timeout_fails": true, "unclear_fails": false}
                -- "sandbox" (confined or none) is optional here; when omitted, the
                   scenario takes the plan's default (or --sandbox), which is how `--sandbox none` reaches
                   every scenario at once. Set it on a specific scenario only to override that default.
                -- "timeout_fails": a run that reaches timeout_s fails instead of being invalid, for a
                   scenario where ending is the behavior under test; otherwise counting only finished runs
                   scores an arm that never ends on the runs it happened to finish.
                -- "unclear_fails": a judge's "unclear" verdict fails the run instead of leaving it unassessed,
                   for a scenario whose acceptance, fixed in advance, requires the output to show it meets
                   the question; otherwise an unclear verdict is judge-unclear, not a failure.
fixture/        copied into the working directory
setup.sh        runs in the working directory first (for example, to create a repo and a local origin)
bin/            fake tools, copied into the run and first on PATH; they may append JSON lines to $TRIAL_HARNESS/calls.jsonl
check.py        def check(run) -> {name: bool | number | str}; optional def judge_context(run) -> str
qualify/        good.sh and bad.sh reference behaviors for qualifying the checks
```

What a scenario's `setup.sh` and an arm's `resources` install is decided as [conditions and setup](designing-comparisons.md#conditions-and-setup) describes: starting from none, scoped to every arm or to one, admitted after an independent check of its grounds, and probed live under the scored launch mode before any scored run, unless setting it up is itself what the comparison observes.

A run passes when the executor finished, the file its scenario's `artifact` names exists, every `required` check is `True`, and the judge (when the scenario asks one, `judge_required` is not `false`, and the plan or the run's arm names a judge) says `pass`. It fails when any of those is observed not to hold — a `required` check is `False`, the artifact is missing, or the judge says `fail` — even when something else about it is unknown (a failing check decides a run whose judge gave no verdict). It is invalid, neither passed nor failed, when what would decide it was not observed: a `required` check that returned anything but `True` or `False` (`check-missing`; a check that cannot tell returns a string such as `"unknown"`, which is reported as a measure), a judge question with no judge (`judge-missing`, never a silent pass — unless the scenario sets `judge_required: false`, in which case the `required` checks alone decide, exactly as without a `judge` field at all), a judged output that is not text a judge can read (`judge-unassessed`, below), a judge error, or an `unclear` verdict (`judge-unclear`: the judge said the evidence cannot decide; under the scenario's `unclear_fails` it fails instead). Numbers and strings are reported as measures without deciding the pass. `followups` continue the same conversation, which is how a scenario reproduces a user sending "continue". `sandbox` here always wins over the plan's or `--sandbox`'s default (see [Confinement](#confinement)). `judge_role` replaces the judge prompt's opening sentence, which by default frames the subject neutrally as "one run of the task below" — never an assumption that the subject is an AI agent's code change; write a scenario-specific role when the judge should be told more about what it is looking at (for example, "You are a pastry chef judging one plated dessert against a written brief."). `artifact` names a file the executor was asked to write, relative to the working directory: when it exists, its own text becomes `run.final_message` (and what a judge sees) in place of the executor's transcript, so any executor — not only the `artifact` executor — can be compared on a specific deliverable it produced rather than on what it said about producing it. When it does not exist, `run.final_message` is an explicit "artifact not produced" marker instead of the transcript, `result.json` records `artifact_missing: true`, and the run fails without a judge being asked — never a silent fall-back to whatever the executor said. A judged output that is not UTF-8 text (an image, a document format, any file holding a NUL byte) or is larger than 64 MiB is not shown to a judge: `run.final_message` holds a placeholder saying so, and the run is `judge-unassessed` unless the scenario's `check.py` defines `judge_context`, which then gives the judge the evidence it reads in the output's place (a description an extractor produced, for example).

`check(run)` sees the resulting state and the run's record: `run.workdir`, `run.harness`, `run.final_message`, `run.artifact_missing`, `run.messages`, `run.commands`, `run.calls` (fake-tool log), `run.usage`, `run.git(...)` and `run.git_rc(...)`, `run.file(rel)` and `run.read(path)`, `run.copy_workdir()`, `run.sandboxed(cmd, cwd=..., timeout=...)`, the record's `run.actions(*kinds)`, `run.evidence(*kinds)`, `run.covers(kind)`, `run.turns`, `run.listed`, and `run.exposed(path)` ([checks and exposure](launching.md#checks-and-exposure)), `run.events` (whatever the executor printed on standard output, as JSON lines), and the skill helpers `run.skills_loaded()`, `run.skill_loaded(name)`, and `run.skills_listed()` (see [Selection trials](#selection-trials)). Prefer checks on state (files, commits, remotes, tool calls) over checks on wording. `run.commands` and `run.messages` are the main agent's, and they and `run.actions` raise when the record does not cover what they ask for, which makes the run invalid rather than failed. `run.final_message` is the scenario's own `artifact` file when one is named and the executor wrote it, or otherwise the last `final-*.md` the run wrote, or — for a command arm that wrote none, such as a build or render step whose only output is its own stdout — that stdout's own bounded tail, so a command arm's plain output still reaches a judge's `<final_message>` without special-casing. When the scenario names an `artifact` and the executor never wrote it, `run.artifact_missing` is `True`, `run.final_message` holds an explicit marker instead of silently falling back to the transcript, and the run fails whatever its checks return.

The agent controls its repository's configuration, the links in its files, and its code, so read or run them in a check only through these: `run.git` overrides git settings that run commands and runs git confined and read-only (unless this run resolved to `"sandbox": "none"`, in which case it runs the same way but unconfined — never a silent fallback when confinement was actually needed); `run.file` and `run.read` return nothing for a path that resolves outside the run directory or is not a regular file, and read at most 64 MiB; `run.sandboxed` runs agent-written code the same way (no network, the host read-only, the user's home hidden, its own process namespace, unless unconfined), typically on `run.copy_workdir()` so the working directory stays as the agent left it (the copy leaves out files over 256 MiB, and is empty when the agent replaced the working directory itself with a link).

## Confinement

This section covers the processes the runtime starts itself, the checks of a host run among them; a host arm's executor and a host judge run wherever the host starts them, outside all of it (see [Host executor](#host-executor)).

By default (`"sandbox": "confined"`, whether from the scenario, the plan, or the built-in default) launcher and command runs, and launcher judges, execute inside bubblewrap: the host is read-only, the user's home is hidden, `/run` is hidden too (it holds Unix-domain sockets — a user systemd/D-Bus bus, a container runtime's control socket — with no network-namespace boundary of their own, so a read-only bind of the rest of the host would otherwise leave them fully reachable; whichever DNS stub resolver keeps its own files there is read back in read-only, so name resolution over the network confinement leaves reachable still works), only the run directory is writable, and everything the agent starts lives in its own process namespace and ends with the run; an executor's own sandbox, if it has one, is the launcher's to turn off inside it so agents can commit. An `--out` outside both the user's home and `/tmp` is hidden the same way as those two, so a confined process cannot list its sibling run directories or read `plan.json` from its own job directory; a launcher run also has every trial input hidden and every file and dot-entry above it emptied ([what the runtime holds a launcher to](launching.md#what-the-runtime-holds-a-launcher-to)). Judges run the same way, able to write only their own opaque cell directory under `out/judges/.cells/` (see [Reading results](#reading-results)), with an environment built there. The read-only paths a confined launcher run additionally needs (its resolved binary's own directory, the package root above it, a sibling `lib/` for an npm-style global install, and the interpreter a script's shebang names — for example the node runtime a JS launcher needs) are derived from the resolved binary itself, following symlinks, without assuming any particular install layout or directory depth; `readable` adds more, for a command arm the same as for a launcher. The user's home directory stays hidden even when the binary lives inside it: a package root discovered above the binary is punched back through only when it sits well below home, never when it IS home or one of its immediate children (`~/.local`, `~/.cargo`, `~/bin`, ...) — those are broad and can hold unrelated credentials. The binary's own containing directory is narrower still: it is exposed whole when it is scoped to this one executor — including an immediate child of home such as `~/bin`, where the binary is commonly the only thing there — but never one level below one of those (a shim placed directly in `~/.local/bin` or `~/.cargo/bin`, for example, as both a native app installer and an npm-style global install can produce), where only the binary file itself is exposed, never the shared directory around it (package managers and version managers fill those with many unrelated entries). An arm's `resources` (above) stay read-only under confinement even against the agent's own `chmod`: each one is bound read-only again after the run directory itself, which the agent cannot undo the way it could a copy's own write bit alone; unconfined, that write bit is the only protection there is.

**The environment is an explicit allowlist, never the parent environment minus a scrub list.** A run's environment (a host arm's executor's only where the host applies the one `dispatch.json` gives) carries only: `PATH` (the scenario's copied tools first — so a scenario's own fake `gh`, `curl`, or `make` is always found before anything else — then a confined executor's own directories and interpreter, then system directories including `/usr/local` and Homebrew's, then — in unconfined mode only — this process's own `PATH` verbatim, so a host's Homebrew, `/usr/local`, or user-prefix toolchain is reachable when unconfined); a throwaway `HOME` and `TMPDIR`, always the run's own, never the real ones; `LANG`, every `LC_*` variable, `TERM`, `TZ`, `USER`, and `LOGNAME`; any names an arm lists in `pass_env`; and the one API key variable an agent executor or judge uses (see [Keys](#keys)). Nothing else — no other token, credential, or host-specific variable — reaches the run. Git and gh configuration are private to the run in every mode.

**Bubblewrap is required for confinement, with no silent unconfined fallback.** Where it is missing, a scenario, plan, or judge resolved to `"confined"` refuses to start rather than quietly running unconfined — this applies uniformly to launcher and command arms, checks that call `run.git` or `run.sandboxed`, and launcher judges alike. The only way to turn confinement off is the literal, explicit `"sandbox": "none"` — on the scenario itself, or as the plan's (or `--sandbox none`'s) default when the scenario names none of its own; nothing else does, so a typo or another tool's own sandbox name can never silently drop it. Every finished run records the sandbox mode it actually resolved to, and whether its own process actually ran confined, in its own `result.json`; a run directory that holds any unconfined run says so in `summary.md`'s header, whatever the directory's current default is, so an unconfined result is never mistaken for a confined one and a later rerun (including a `recheck --sandbox`) that changes the default cannot make the notice disappear.

Before scheduling any jobs — before `plan.json` is written, before `--out` exists, before any scenario's `setup.sh` has run — `run` refuses outright if bubblewrap is missing and any selected scenario would actually need it (any effective sandbox other than the literal `"none"`), rather than letting each job discover that on its own once its own executor or check first needs confinement. The [probe](launching.md#the-probe) then runs each launcher once, confined the same way a job would be: a broken `PATH` shim (a launcher that re-execs and cannot find the real executable once confinement hides the paths it assumed) fails there, once, rather than per job. This is the common failure of a version-manager shim (volta, mise, asdf), whose launcher re-execs the real executable by re-reading `$HOME`, replaced with a throwaway one under confinement; resolve the shim once yourself (`volta which <name>`, `mise which <name>`, `asdf which <name>`) and name that path as `binary`.

After a run the runtime writes, reads, and prunes the run directory without following a link, waiting on a special file, or stopping at a directory or permissions the agent left there, so what the agent planted cannot reach the host or end the trial; `derive` copies an artifact only when it is a regular file inside that run's own working directory.

**macOS and other hosts without bubblewrap.** Bubblewrap is Linux-only; on macOS (and a Linux host that simply lacks the package) every scenario needs `"sandbox": "none"` — set on the plan, or passed as `--sandbox none` on `run`/`recheck` — to run at all, since the built-in `"confined"` default refuses outright (see above) rather than silently running unconfined. Unconfined, an arm's own process, checks, git, and the judge all run directly on the host with the parent shell's own `PATH` reachable (see the allowlist above) — a throwaway `HOME` and working directory still isolate each run from the others, but not from the rest of the host the way bubblewrap does.

## Host executor

A `host` arm runs where this runtime cannot start the executor itself: the host that runs `trial.py` starts it by its own means, such as its subagent tool or an app's agent feature, and the runtime does the rest. `trial.py run` prepares a host run exactly as any other (a fresh run directory, the fixture, `setup.sh`, the arm's instructions copied into the run directory, its `resources` in the run's private home) and then, instead of starting a process, leaves the job awaiting: it writes no `result.json`, keeps a marker beside the run directory (`runs/<job>.awaiting`, alongside `.pending`) so a later run tells an awaiting job from a partial one, and lists the job in `RUN_DIR/dispatch.json`.

`dispatch.json` lists every job in the run directory that awaits its executor, whichever run prepared it, in the interleaved schedule order, each as `{"job", "workdir", "prompt", "followups", "instructions", "env", "reply", "record"}`: the absolute working directory; the scenario's prompt and its followups; the path of the instructions copy (`null` without instructions); the environment the runtime would have given the executor (`HOME` and `TMPDIR` in the run's private home, `PATH` with the scenario's fake tools first, `TRIAL_HARNESS`, private git and gh configuration, and the values of any `pass_env` names), for a host that can apply one; and the paths where the host's controller writes the executor's final reply and its record. Each entry also gives the arm's requested `model`, `effort`, and the scenario's `timeout_s`, which the host applies where it can. For each entry the controller (the agent running `trial.py`) starts a fresh executor with no inherited conversation, gives it the instructions as its standing (system) instructions where it can and otherwise prepended to the prompt, gives it the prompt and the working directory, sends the followups in order to the same executor, writes the final reply after the last one verbatim to `reply` (empty if it gave none), and then writes `record`. An executor that cannot reach the run's files, such as a subagent outside the sandbox where `trial.py` runs, gets the workspace relayed: the controller gives it the content of the working directory the task needs, takes back the files it produced or changed, and writes them into the working directory before the scoring run, since checks read the working directory as the controller left it. The record is a JSON object of what only the host knows, which nothing the judge sees includes. `finished` (true or false) is required; `workspace` (how the executor reached the working directory: `"direct"` when it reached that and nothing else of the trial directory, `"shared"` when it could also reach the rest, `"relayed"`, or `"none"`), `model`, `instructions` (`"system"` or `"prompt"`), `env_applied`, and `fresh` say how the host ran the executor, and `usage` (an object of numbers such as `input_tokens`) and `commands` (the command lines the executor ran) carry what the host saw of them; `applied` lists the requested settings it applied, and the record may take the full shape a launcher's does ([the record](launching.md#the-record)), with `actions`, `covers`, `turns`, `listed`, and `transcripts`. A record field with the wrong shape leaves the job awaiting, with the reason. Scoring is the same whichever way the executor reached the workspace; `result.json` keeps the record, and `report` shows it, so a reader can tell which runs were relayed.

A later `trial.py run` with the same `--out` scores each awaiting job whose reply and record exist as any finished run: checks on the working directory and the reply, which becomes `run.final_message`; the judge; and `result.json`, which keeps the record as `host` and says `confined: false`. A record whose `finished` is false makes the run invalid (`status: "unfinished"`), or failed under the scenario's `timeout_fails`, as a timeout does. A job without its reply and record stays awaiting and is listed again; a reply without a record, a record without a reply, or a record that is unreadable, not valid JSON (NaN, Infinity, and a number too large for a float included), or without a boolean `finished` leaves the job awaiting too, with the reason printed on that job's line. A host run records no commands, usage, or executor seconds of its own: its `commands` (`null` when the record lists none), `usage`, and `run.commands` are what the record supplies, and `seconds` is `null`. `--retry-invalid` starts an invalid host run over from a fresh run directory, and `summary.md` notes host runs in its header.

The executor runs outside this runtime's confinement, in the host's own environment unless the host applies the one it is given. A host arm on a scenario that ships fake tools (`bin/`, or the directories its `"bin"` lists) is therefore refused when the plan loads unless the arm sets `"host_env": true`, the host's commitment to run the executor's commands in that environment; without it, the executor would reach the real `gh`, `curl`, or `make` the fake ones stand in for. Preparing and scoring host runs needs only Python's standard library, the scenario's own files, and whatever its `setup.sh` and checks call (such as git): where bubblewrap is missing, as in a hosted Python sandbox, and even with no network, `--sandbox none` runs a plan of host arms and a host judge, with checks unconfined (see [Confinement](#confinement)).

Blindness and isolation are the host's to keep, since the runtime cannot reach what the host starts: run directories are named after their arm, and the markers beside them and a re-judging's record tie each judge cell to its run, so an executor or a judge that can read the trial directory can learn which arm it is, or is judging. The controller therefore gives each executor only its own working directory, or relays it, and gives a judge the prompt's text, never its path, through an executor that cannot reach the trial directory. A host that cannot keep an executor out of the rest of the trial directory records `"workspace": "shared"`, and judging by a judge it cannot keep out is not blind, which the comparison's report says.

`"judge": {"executor": "host"}`, with an optional free-text `model` recorded the same way, is asked the same way (on an arm, of that arm's runs only). Where a launcher judge would be called, the runtime writes the judge prompt it builds, ending with a request for JSON matching the schema, to `prompt.md` and the schema to `schema.json` in the run's opaque judge cell, `RUN_DIR/judges/.cells/<cell>/judge/`, and lists the cell in `RUN_DIR/judge-dispatch.json` as `{"cell", "prompt", "schema", "reply"}`, naming neither the arm nor the scenario. The controller gives each prompt to a fresh judge executor and writes its JSON reply to `reply`; a later run validates it against the schema, and a reply that does not validate (or holds a non-finite number) gives the verdict `error`, an invalid run, as a launcher judge that gives no verdict does. Each run scores a run awaiting the host judge again, with its checks from the current `check.py` and its prompt rebuilt: a prompt that differs from the one the cell asked (a changed check, evidence, or question), or a judge other than the one it asked, replaces it, a reply to the old one is discarded, and the run keeps waiting. A run is put to a host judge only when its executor finished and its checks ran, since no verdict decides any other run. A host judge is given only its prompt, so `resources` on it are refused when the plan loads. A run directory keeps one judge for each arm, so a run that changes a judge while runs await the host judge is refused. [Re-scoring](#re-scoring-stored-runs) and [pairwise judging](#pairwise-judging) ask a host judge the same way.

Every `run` and `recheck` rewrites `dispatch.json` and `judge-dispatch.json` from every job in the run directory that waits on the host, not only the jobs it took up, listing each until it is answered (a host executor's reply and a usable record, a judge's reply), removes a file that lists nothing, and prints how many jobs await their executor and how many runs await the host judge, with each file's path. A job whose reply and record are written but that a run filtered out (`--arms`, `--only`, fewer `--repeats`) still waits, and the next run that includes it scores it. `run` exits 3 when the failure breaker skipped runs (see [Reading results](#reading-results)), whether or not anything awaits the host; otherwise `run` and `recheck` exit 4 while anything in the run directory awaits the host and 0 when nothing does, and either exits 2 on an error. The cycle is to run, answer what the dispatch files list, and run again with the same `--out` until it exits 0; a host arm under a host judge takes three runs, one to dispatch the executor, one to score its reply and ask the judge, and one to read the verdict.

## Qualifying checks

Before relying on a scenario, run its reference behaviors with the `command` executor:

```json
{"name": "qualify", "repeats": 1,
 "arms": {"good": {"executor": "command", "command": "sh \"$TRIAL_SCENARIO_DIR/qualify/good.sh\""},
          "bad":  {"executor": "command", "command": "sh \"$TRIAL_SCENARIO_DIR/qualify/bad.sh\""}},
 "scenarios": ["scenarios/gate-deploy"]}
```

The good behavior must pass and the bad one must fail. A check that reads the run's record (its commands, edits, reads, or loads) is qualified by reference behaviors that write the record those actions would leave to `$TRIAL_RECORD`, in [the record's](launching.md#the-record) shape, alongside what they do; a command arm that writes none took no agent action. Qualify a check that only an agent can trigger on agent runs instead.

## Two-stage trials

When the question is whether what an agent writes works for the agent that later follows it (a skill, a brief, a repaired instruction), judge the artifact by its consumer, not by reading it. After the authoring run:

```bash
python3 <skills-file-root>/scripts/trial.py derive RUN_DIR --scenario repair-ask-first-skill \
  --artifact skills/deploy-helper/SKILL.md --consumer scenarios/use-deploy-skill \
  --repeats 2 --plan consumer.json
python3 <skills-file-root>/scripts/trial.py run consumer.json
python3 <skills-file-root>/scripts/trial.py summarize CONSUMER_RUN_DIR --group
```

Each produced artifact becomes an arm named `<authoring arm>~r<repeat>`; `--group` pools them back into their authoring arm. Each derived arm's executor and settings start from what its own source run actually recorded — so a two-stage trial reuses the same launcher and model by default, per source arm, rather than a guessed one — with `--executor JSON` overriding or extending them, for example `--executor '{"model": "model-b"}'` to keep the source launcher but pick a model, or `--executor '{"executor": "launcher", "script": "...", "model": "..."}'` to replace it outright; replacing the executor drops the source's launcher settings. A relative `env_file` or `script` in `--executor` is rewritten relative to the derived plan.

## Selection trials

A selection trial asks whether an executor, given a catalog of skills and a request, loads the skill the request needs and leaves the others alone. It is an ordinary plan with three additions.

**Placement.** Put each catalog skill where the executor discovers skills, as an arm `resources` entry keyed by that location inside the run's private home (the launcher's author knows where; [launching](launching.md#questions-to-answer-about-your-executor) asks), and keep the arm's instructions silent about it when the question is whether the executor's own listing leads there. Every catalog also holds the executor's own built-in skills, and an executor may read a host-wide skill or settings directory, which the launcher's `hide` keeps out. An executor that skips skill discovery in its non-interactive mode measures no selection until its launcher turns discovery on; everything such a run can then load comes from what the arm places in its private home and what the scenario's fixture or setup puts in its working directory, since the runtime empties every file and dot-entry above a launcher's run. Executors shorten or drop listed descriptions beyond a listing budget, so pin the listing state a trial depends on with the settings the executor reads, placed as a resource.

**Detection.** In `check(run)`, `run.skills_loaded()` returns `{name: [evidence, ...]}` for each skill whose instructions reached the model, and `run.skill_loaded(name)` answers for one. A skill counts when the run's record shows:

- a successful load naming it (`plugin:name` counts for `name`): the executor's own mechanism putting it into the model's context;
- a successful read of a path ending in `<name>/SKILL.md`, in any form (`~`, absolute, relative, Windows);
- any other action's output showing that SKILL.md's frontmatter (a `---` line, then a top-level `name: <name>` line; line numbers are ignored).

Shell commands are judged by what they returned, never parsed, so every way of reading a file counts (a glob, `find -exec`, `xargs`, `$(cat ...)`, a `cd` in an earlier call), and a command that only names a path does not (a listing, `rg --files`, a write or heredoc, `git add`, a patch, a comment). A failed action counts only when its output shows the frontmatter, and nothing an edit holds counts. A read that skips the frontmatter or a search that returns only matching lines does not count; a command that echoes a SKILL.md it writes (`tee`) or re-reads one the agent wrote does. Each entry's `evidence` names the action, so whenever a check's own corroboration disagrees with the detection (a correct deliverable without a load, or a load without one), read the evidence before counting the run. A skill the executor merely listed never counts. `<name>` is the skill's directory name, which the portable skill format requires to equal its `name`. `run.skills_loaded()` raises when the record does not cover reads, loads, commands, and other actions, since a skill read could hide in any of them; `run.skill_loaded(name)` answers yes from any evidence and raises only for a no the record cannot establish.

`run.skills_listed()` returns `{name: description}` for the listing the executor sent the model (the record's `listed`), with `""` for a skill listed by name alone, and `None` when the record shows no listing. A listing check is a placement check: it shows that the executor picked the skill up and whether its description was shown, not that the model read it.

Before trusting a selection rate, qualify it on each executor with a positive control (a request that plainly needs a placed skill, loaded on every run) and a negative control (an unrelated request done through tool calls, never loading it). A near-neighbor request that resembles the skill's own but does not need it measures over-selection.

**Padding.** A fresh home starts with only what the arm places, while a real catalog is larger and squeezes the executor's listing budget. An arm's `"stub_skills": {"dir": ".agents/skills", "count": 35, "chars": 13900, "seed": 0}` adds `count` generated skills under `dir`, read-only like resources: neutral names and descriptions about unrelated hobbies, the `chars` split evenly across the descriptions (each at most a word short of its share), and the same stubs for the same spec. Stubs join the arm's resources digest, and may not land inside or on top of a `resources` entry.

**Reading the result.** A selection rate belongs to one executor, model, effort, and catalog: its size, the neighbors each skill competes with, which descriptions the executor shows, and its built-ins. Report it that way; it does not carry over to another executor or catalog.

## Re-scoring stored runs

After a check changes, `trial.py recheck RUN_DIR` re-scores finished runs without running any agent again (the runtime compiles `check.py`, and what it imports from beside the scenarios, from source on every load and writes no bytecode for them, so an edit always takes effect), reads each run's exposure again from its stored record by the current rule, keeps their stored verdicts, and rewrites `summary.md` from the rescored results; `--rejudge` also asks each run's judge, qualified first by the [probe](launching.md#the-probe) in the confinement it will judge in, (its arm's own, else the plan's) again with the scenario's current question and evidence, and `--judge JSON` does so with a different judge, which becomes the judge of every run and drops the arms' own judges from the stored plan: it re-judges every run a judge scores, refusing before it judges anything when the checks of one of them fail to run and changing nothing when the new judge gives no verdict for one of them, so `--only` cannot limit it while scenarios outside `--only` have finished runs with a judge question; `--only s1,s2` limits the others to those scenarios. `--sandbox confined|none` overrides the directory's plan-level default sandbox for this and future rechecks (a scenario's own `sandbox` still wins), the same as `run --sandbox`. A run whose verdict comes from another judge than the one its arm calls for (or that has none) does not score: `recheck` reports it as `judge-stale` until `--rejudge` judges it. `--rejudge` too changes nothing when the judge gives no verdict for a run, and names the judge's error. A plain `trial.py recheck` turns a judge error recorded as a failure into an invalid run. With a [host judge](#host-executor), `--rejudge` (or `--judge` naming one) puts the prompt of every judged run it scores into a fresh cell, listed in `judge-dispatch.json`, records the re-judging (its judges, `--only` selection, sandbox, and cells) in `RUN_DIR/rejudge.json`, and exits 4; no other judge is called while a reply is outstanding. Every later `recheck` goes on with it as it began, and one that asks for another judge, `--only`, or `--sandbox` is refused, as `run` is, until it finishes: the stored verdicts stay in force until every reply is in, when they all change together, and a reply that does not validate changes nothing and drops the re-judging, as a launcher judge that gives no verdict does. A judge decides runs the checks cannot, so qualify it the way checks are qualified: fixed reference outcomes (the same state with different replies, for example), each judged several times, where the expected verdict is known. A judge from another model family than the executors guards against a judge that favors its own family's style.

## Pairwise judging

`required` checks and the per-run judge each score one arm's run against a fixed bar; they cannot say which of two arms that both pass is better. `trial.py pairwise RUN_DIR --arms A,B` does: a plan `"pairwise": {"arms": ["A", "B"]}` block names the default pair so a bare `trial.py pairwise RUN_DIR` needs no flags. For every `(scenario, repeat)` where both `A` and `B` finished (`status: "ok"`) and the scenario asks a judge question, a blind judge sees both outputs' own `run.final_message` and, when the scenario's `check.py` defines `judge_context`, each one's own evidence too (the same text and evidence a per-run judge would see, including a scenario's `artifact` override) labeled only "response 1"/"evidence_1" and "response 2"/"evidence_2" — never an arm's name, and never which one is which — and is asked which better answers the scenario's judge `question`, or "tie"; it is asked twice per pair, once with `A` shown first and once with `B` shown first, so a judge that just prefers whichever answer comes first is caught rather than mistaken for a real preference. If `judge_context` raises for either side, neither side gets evidence for that pair (never just the side whose call happened to succeed), and the pair's own record (below) carries an `evidence_errors` object (`"a"` and/or `"b"`) naming what failed. Each judge call's own working directory is an opaque, per-pair id that names neither the scenario nor either arm (look it up in the pair's own result file, below), since an executor can put its own working directory in the model's context and that would otherwise tell it which response is which arm. `--judge-model MODEL` runs the pairwise judge with a different model while keeping the run directory's judge executor and other settings; without it, the directory's own judge is used as recorded. Pairwise judging uses the plan's `judge`: an arm's own judge does not apply to it, so a plan whose judges are all arms' own has none for `pairwise` to use. A [host judge](#host-executor) is asked between calls: each `pairwise` call puts every order not yet answered into its cell and lists it in `RUN_DIR/pairwise/<A>__<B>/dispatch.json`, as `judge-dispatch.json` lists cells, exits 4 while any waits, keeps a cell's reply for as long as its prompt and its judge stay the same, removes the comparison's earlier aggregate while any order waits, and writes the new one once every order of every pair is answered; a reply that does not validate is an error for its order, which makes the pair invalid. A launcher judge is probed before it judges and runs confined exactly like a per-run judge (see [Confinement](#confinement)), and a judge that produces no verdict on either order makes that pair invalid, never a guess.

A pair is decisive and consistent only when both presentation orders name the same arm; a tie in both orders is consistent but not decisive; anything else — the two orders disagreeing, or one deciding while the other ties — is order-inconsistent, reported separately and never averaged away. `A`'s win rate (with a 95% Wilson interval) is computed only over decisive, consistent pairs. Results land under `RUN_DIR/pairwise/<A>__<B>/<scenario>__r<n>.json` (each pair's both-order verdicts, arms, and outcome, plus `cell`: the id of its actual judge transcripts under the arm- and scenario-blind `RUN_DIR/pairwise/.cells/<cell>/order-1/` and `order-2/`, each kept exactly as a per-run judge's own directory is) and the aggregate at `RUN_DIR/pairwise/<A>__<B>.json`; `summarize` (both the markdown and `--json`) and `report` include every aggregate found there, keyed `"A__B"`.

## Reading results

`summary.md` lists passed / valid runs per scenario and arm with intervals, a per-arm table of mean input tokens, output tokens, cost (when the record reports `cost_usd`), commands, seconds, and a count of runs that reported no usage at all, plus each check's rate; with a `baseline` arm (from the plan or `--baseline`), every other arm's cost and timing cells show a percentage difference from it. Invalid runs (timeouts, executor errors, a launcher run whose record is missing or malformed (`no-record`, `record-invalid`), whose turn changed watched configuration (`config-changed`), or whose follow-up reported another session or model (`session-changed`, `model-changed`), broken checks, a required check that gave no true or false (`check-missing`), `judge-missing`, an output the judge cannot read (`judge-unassessed`), a judge that gave no verdict or one its schema does not allow (any judge's verdict is checked against the whole schema), an `unclear` verdict (`judge-unclear`), a verdict from another judge than the one its arm calls for or on another question or evidence (`judge-stale`)) are listed separately and never counted as failures of the arm; a run with a failed required check or a missing artifact is a failure even when its judge gave no verdict; `--retry-invalid` reruns them, and a launcher's transient failure (exit 75) is retried automatically. A directory holding any run that resolved to `"sandbox": "none"`, or whose own process ran unconfined for any other reason, says so in the header, whatever the directory's current default is. Each run's private-home cache (`~/.cache`) is pruned when it finishes, and a launcher's `copy` files are removed once the run is over, and the directories of its private home, where resources and stub skills sat read-only for the agent, are made owner-writable again, so a finished run directory deletes with a plain `rm -rf`. Once a run's checks and judge (when it asks one) finish and `result.json` is written, its own regenerable build output — a Cargo `target/`, a Go or npm build cache, `__pycache__`, a toolchain or crate download in the run's private home (`.rustup`, a Cargo `registry`), wherever they sit under the run's own directories — is pruned too, by default: build agent code in a check from `run.copy_workdir()`, never in `work/` itself, so no check or later `recheck` reads build output there; a trial with compiled scenarios can otherwise fill a disk with nothing but rebuildable output (tens to hundreds of MB per Rust run alone). `result.json`'s own `pruned_build_output` field lists what was removed, relative to the run directory, when anything was; `"prune_build_output": false` on the plan, or `TRIAL_PRUNE_BUILD_OUTPUT=0` in the environment, keeps it instead (see [Plan](#plan)). The runtime also stops scheduling what keeps failing: after `TRIAL_FAILURE_STREAK` (default 6; 0 turns it off) consecutive executor failures of one executor family (executor, model, endpoint, effort, and a launcher's script), that family's remaining runs are skipped, and after that many consecutive judge errors, every remaining run that needs that judge is (the plan's judge and each arm's own judge count apart); skipped runs are never written, the run exits 3 naming the cause, and running the same plan into the same `--out` once the cause is fixed runs them. The runtime stops scheduling when free space falls below `TRIAL_MIN_FREE_GB` (default 5); its own stop message names this pruning and says such a directory's build output is always safe to delete by hand too, for the same reason. Each run directory keeps `events.jsonl` (what the executor printed on standard output), the final messages, `record.json` and the executor's own session files its `transcripts` name (an executor's session files hold the exact instructions it received), `calls.jsonl`, and `result.json`; the judge's own prompt, verdict, and usage live under the opaque `out/judges/.cells/<cell>/judge/` directory `result.json`'s own `judge_cell` field names (see [Confinement](#confinement) for why it is opaque).

**A run's usage is what its record reports, in the shared vocabulary [the record](launching.md#the-record) defines**: `input_tokens` counts every input token, cached ones included, `cached_input_tokens` is the cached part, `output_tokens` includes reasoning, and `cost_usd` is the run's cost. Executors count differently — some report running totals across a session, some each turn's own figures, some cached input apart — and each launcher converts its executor's counting so every turn counts once. A negative value, or one too large for a float, is dropped rather than corrupting a mean, and a record holding a number that is not finite is not read at all.

**Cost and timing figures are means over every run that reached that stage, whether or not it later passed** — a run a check or judge ruled invalid still spent whatever tokens, dollars, commands, or seconds its own record shows; excluding it would understate the real cost of an arm that fails expensively. `seconds` is the executor's own wall time only, never setup, checks, or judging, each timed and recorded on its own (`setup_seconds`, `checks_seconds`, `judge_seconds`) instead. `input_tokens` carries no percentage between two arms whose usage comes in different vocabularies (a run scored before launchers existed, from an executor's own events, beside one scored from a record); every record uses one vocabulary, so arms scored from records compare.

**A baseline percentage is computed per scenario, then aggregated across scenarios** — never pooled from every run across every scenario at once. For each field, and each scenario where both arms have a value, `(arm's mean on that scenario − baseline's mean on that scenario) / baseline's mean on that scenario` is one data point; the arm's percentage difference is then the **median and the mean** of those per-scenario points, alongside `n_scenarios` (how many scenarios contributed). Pooling every run together first can let one scenario's mix of expensive, excluded runs flip the sign of the whole comparison — for example, if a cheaper arm's few timeouts on one scenario are the only invalid runs there, pooling-and-valid-only would count that scenario's other, cheap runs but drop its expensive ones, while computing the percentage per scenario first (on every run, valid or not) does not let that happen. Report the number of scenarios along with the median and mean; a comparison over few scenarios is only loosely bounded, the same way a handful of runs only loosely bounds a pass rate.

`summarize --json` mirrors this: a `scenarios` object keyed `"scenario|arm"`, an `arms` object with each arm's `passed`, `valid`, `runs`, `usage_mean` (every numeric usage field, including nested ones and cost, meaned over every run that reported it — see above), `no_usage` (how many of this arm's runs reported no usage at all), `commands_mean`, and `seconds_mean`, and, with a baseline, a `pct_vs_baseline` object giving each other arm's `{"median": ..., "mean": ..., "n_scenarios": ...}` for each field (an `input_tokens` entry is omitted between two usage vocabularies — see above); with any pairwise results on disk, a `pairwise` object as described above. An explicit `--baseline` (on `summarize` or `report`) naming no loaded arm is an error listing the valid arms; the plan's own stored `baseline` naming none — for example after `--arms` filtered it out — is not, the same as leaving `--baseline` off entirely.

## Report data

`trial.py report RUN_DIR [--out FILE] [--baseline ARM]` writes one JSON document meant for a visualization agent to read and render — data only: no HTML, no chart, no verdict of its own. It never runs an agent or a judge; it only reads what `run`, `recheck`, and `pairwise` already wrote. The bundled `assets/visuals/report.py --trial FILE [--narrative NARRATIVE.json] --output report.html` renders this document as a standalone HTML report (see [presenting evidence](presenting-evidence.md)); `report` itself stays data-only. Its shape:

- `name`, `run_directory`, `generated_at` (when this document was written, ISO-8601 UTC) and `ran` (`first` and `last`: the earliest and latest `result.json` modification times of the runs, UTC, so a `recheck` moves them; omitted when none is readable).
- `plan`: `arms` (each arm's recorded settings and digests — `executor`, `model`, `effort`, `base_url`, `instructions_sha256`, `artifact_sha256`, `resources_sha256`, `script_sha256`, `hide`, `watch`, `command`, whichever apply), `scenarios` (each one's `name`, `prompt`, `followups`, `judge` question, `judge_role`, `required` checks, and `artifact` field), `judge` (its settings the same way an arm's are given; an arm that names its own judge carries it as `judge` in its entry), and `decision_rule` — the plan's own free text stating how to decide, carried through verbatim when the plan has one, omitted otherwise (`report` states no rule of its own). Each arm also carries `model_spec` (its model as written, when that differs from the resolved one), `resources` (the home-relative paths its resources were placed at), and `stub_skills` when set, plus `instructions_text` and, for an `artifact` arm, `artifact_text` (a directory of several files gives each under a `--- path ---` line): the snapshot under `RUN_DIR/instructions/` or `RUN_DIR/artifacts/` that its digest names, read without following a link and given only while its content still has that digest, cut to the first 24,000 characters (`REPORT_TEXT_CHARS`) with `instructions_truncated` or `artifact_truncated` saying whether it was cut; each scenario also carries its scenario.json's free-text `description`, under the same bound with `description_truncated`, and `judge_required`, `timeout_fails`, and `unclear_fails` when set. Any of these whose source is missing, unreadable, or changed is omitted rather than failing the report.
- `runs`: one record per finished run — `job`, `scenario`, `arm`, `repeat`, `status`, `passed`, `valid` (`passed is not None`), `invalid_reason` when invalid (its status when the executor did not finish, else `check-error`, `check-missing`, `judge-missing`, `judge-unassessed`, `judge-stale`, `judge-unclear`, or `judge-error`), `checks` (the check values `check.py` returned), `judge` (`verdict` and `reason`, when a judge scored it), `usage`, `commands`, `seconds` (the executor's own wall time; `setup_seconds`, `checks_seconds`, and `judge_seconds` alongside it), `confined` (whether this run's own process actually ran under bubblewrap), `artifact_missing` (true when the scenario named an artifact the executor never wrote), for a host run `host` (its host's record, such as whether the workspace was relayed, without the `usage` and `commands` given beside it), and `final_message_excerpt` — the judged output's own text, truncated to a bounded size (`REPORT_EXCERPT_CHARS` in the code) so the document stays sized for a visualizer's own context, not for reading the full native record (which stays in the run directory itself, named by `run_directory` and each run's `job`).
- `arms` and `scenarios`: the same per-arm and per-scenario aggregates `summarize --json` reports, each with a 95% Wilson `interval` added.
- `pairwise`: every pairwise aggregate found under `RUN_DIR/pairwise/`, keyed `"A__B"`, exactly as `summarize --json` includes them.
- `baseline` and `pct_vs_baseline`, when a baseline arm is named (by `--baseline` or the plan's own `"baseline"`) — the same percentage differences `summarize` shows.

Nine cases run five times each are nine cases, not forty-five: judge generalization by the number of distinct scenarios, and keep a few scenarios out of development so they can test whether a change generalizes.
