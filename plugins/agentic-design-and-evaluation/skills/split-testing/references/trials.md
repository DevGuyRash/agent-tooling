# Trial runtime

`scripts/trial.py` runs every alternative (an arm) on every scenario a set number of times, each run in its own fresh home and working directory, in an interleaved order, and summarizes pass counts with 95% Wilson intervals. You write the plan and scenarios for the question; the runtime owns isolation, confinement, repetition, the per-run record, blind judging, and aggregation. Nothing here is specific to code: an arm's instructions can brief a chef, an artist, or a business analyst as easily as an engineer, and a `command` arm can run any non-agent tool.

```bash
python3 <skills-file-root>/scripts/trial.py run PLAN.json [--jobs 6] [--repeats 5] [--only s1,s2] [--arms a,b] [--sandbox confined|none]
python3 <skills-file-root>/scripts/trial.py summarize RUN_DIR [--baseline ARM]
python3 <skills-file-root>/scripts/trial.py pairwise RUN_DIR --arms A,B [--judge-model MODEL]
python3 <skills-file-root>/scripts/trial.py report RUN_DIR [--out FILE] [--baseline ARM]
python3 <skills-file-root>/scripts/trial.py models [--match 'claude-sonnet-*'] [--latest] [--base-url URL] [--gemini] [--env-file F] [--api-key-var V]
```

Runs land under `~/.cache/agent-trials/<plan>-<timestamp>/` by default; the runtime refuses an output directory inside a git repository, because executors would otherwise pick up that repository's instructions. Rerunning with the same `--out` reuses finished runs and replaces partial ones, including a `result.json` the runner never finished writing. Every run records its arm's executor, model, effort, `base_url`, instructions digest, resources digest (below), command, `allowed_tools`, `permission_mode`, `approval_mode`, and a Claude arm's `bare` (executors read a copy of the instructions kept in the run directory, so the digest is what every run received; a Claude arm's own effective `permission_mode`, and a Gemini arm's own effective `approval_mode` — each one's default differs between confined and unconfined, see [Confinement](#confinement) — is recorded even when the arm never set one itself), and the judge that scored it (executor, model, effort, `base_url`); a rerun whose arm or judge differs from those records is refused, so one run directory never mixes models, instructions, resources, or judges. Other settings (including `env_file`, `api_key_var`, `binary`, `readable`, `pass_env`, `copy_auth`, and `sandbox`), CLI versions, and scenario content are not compared. One `run` or `recheck` uses a directory at a time.

## Plan

```json
{"name": "kernel-screen", "repeats": 5, "seed": 1, "sandbox": "confined", "baseline": "none",
 "arms": {"none":   {"executor": "codex", "model": "${TRIAL_CODEX_MODEL}", "effort": "high"},
          "kernel": {"executor": "codex", "model": "${TRIAL_CODEX_MODEL}", "effort": "high",
                     "instructions": "arms/kernel.md"},
          "kernel-claude": {"executor": "claude", "model": "${TRIAL_CLAUDE_MODEL:-latest:claude-sonnet-*}",
                            "base_url": "https://proxy.example", "instructions": "arms/kernel.md"},
          "kernel-gemini": {"executor": "gemini", "model": "${TRIAL_GEMINI_MODEL:-latest:gemini-*-pro}",
                            "instructions": "arms/kernel.md"}},
 "judge": {"executor": "codex", "model": "${TRIAL_CODEX_MODEL}", "effort": "high"},
 "scenarios": ["scenarios/gate-deploy", "scenarios/pr-no-merge"]}
```

Plan-level fields beyond `name`, `repeats`, `seed`, `arms`, `scenarios`, and `judge`:

- `sandbox`: the default confinement for a scenario that names none of its own (`"confined"` or `"none"`; see [Confinement](#confinement)). `--sandbox` on `run` or `recheck` overrides it for that invocation and is then stored as the directory's new default.
- `baseline`: the arm `summarize` (or the `run`/`recheck` summary it writes), and `report`, compare other arms' cost and timing against as a percentage; `--baseline ARM` on `summarize` or `report` overrides it for that call.
- `pairwise`: `{"arms": ["A", "B"]}` names the default pair `trial.py pairwise RUN_DIR` compares when called with no `--arms` (see [Pairwise judging](#pairwise-judging)).
- `decision_rule`: free text stating how to decide between the arms once the numbers are in (for example, "ship whichever arm has no scenario below 90% and costs less"); `report` carries it through verbatim for a visualizer to show, and draws no conclusion of its own either way.
- `prune_build_output`: `false` keeps a finished run's own regenerable build output (a Cargo `target/`, a Go or npm build cache, `__pycache__`) instead of pruning it by default once that run's checks and judge finish (see [Reading results](#reading-results)); `TRIAL_PRUNE_BUILD_OUTPUT=0` (or `false`) in the environment keeps it too, whatever the plan says.

The settings fields `model`, `effort`, `base_url`, `binary`, `env_file`, and `api_key_var` of arms and the judge expand `${VAR}` and `${VAR:-default}` (without nesting; a command arm's `command` does not expand, because its `$TRIAL_*` variables belong to its shell), and a field other than `model` that expands to nothing is unset (an empty `model` is an error). Expanded values are recorded verbatim in the run directory, in `plan.json` and in each run's `result.json`, and can appear in error messages, so a key belongs only behind `env_file` and `api_key_var`. A model `latest:GLOB` resolves to the newest model the endpoint serves in which each `*` (at most three) is a version number (`5-5`, `6.1`; from a date stamp of four or more digits on, a version only breaks ties): `latest:claude-sonnet-*` picks the newest Sonnet and never a variant such as `-thinking`, and a family sharing a non-numeric suffix is named by including that suffix after the last `*` (for example `latest:*-preview`). A Claude arm's models are listed at its `base_url` (Anthropic format), a Gemini arm's at its `base_url` or, absent one, Google's own public endpoint (Gemini format — each entry's `models/<id>` name is reported with that prefix stripped, matching what `-m` and `GEMINI_MODEL` expect), any other arm's at the Codex model provider (OpenAI format); the key that lists them follows the same three-step lookup as running an arm (below), and the key never follows a redirect, and an endpoint URL carrying credentials, a query, or a fragment is refused. `trial.py models` lists what an endpoint serves (`--latest` shows what `latest:MATCH` resolves to; `--gemini` asks the Gemini format instead of the Codex provider), and `TRIAL_MODELS_FILE` (one ID per line) replaces the query. A run directory resolves each spec once and keeps every resolution in `plan.json` (an arm records the spec as written as `model_spec` and the expanded `latest:` spec as `model_query`); a rerun, or an arm added later with the same spec and endpoint, takes the recorded model, while a new directory gets the newest. `--dry-run` asks no endpoint and shows a spec the directory has not resolved as unresolved, unless `TRIAL_MODELS_FILE` answers it. Name an exact model when a comparison must stay reproducible across run directories.

Scenario, `instructions`, and `env_file` paths are relative to the plan; `~` expands. An arm's `instructions` file becomes the executor's user-level instructions (Codex `AGENTS.md` in `~/.codex`, its `CODEX_HOME` inside the run's private home; Claude appended system prompt in `--bare` mode; Gemini `GEMINI.md` in `~/.gemini`, its own private home). Executors:

- `codex`: `codex exec` with only the user's model provider settings copied into a private home, so no plugins, skills, memories, or user instructions load beyond the arm's. `binary` names the `codex` executable (default: `TRIAL_CODEX_BIN`, then whatever `codex` this process's own `PATH` finds — never an install-path guess); `readable` lists extra host paths (for example a toolchain under `$HOME` such as `~/.cargo/bin` and `~/.rustup`) a confined run can read and use, beyond what the resolved binary itself already needs — name the narrowest directory that actually holds what the arm needs, since a path listed here is exposed exactly as given: `~/.cargo` as a whole, for instance, also holds `credentials.toml`.
- `claude`: `claude -p --bare`, which skips hooks, plugins, memory, and CLAUDE.md discovery and authenticates only through an API key, never OAuth (`"bare": false` runs it without `--bare` for a [selection trial](#selection-trials)). `binary` (default: `TRIAL_CLAUDE_BIN`, then `PATH`) and `readable` work the same as for `codex`. With `"base_url"` set to an Anthropic-compatible endpoint (such as a model proxy) Claude talks to that endpoint instead of its own default one; either way the run is confined like codex runs, with its own `HOME`, and permission prompts are bypassed inside the sandbox. The plan's `judge` accepts the same `executor`, `model`, `base_url`, `binary`, `readable`, and `resources` settings.
- `gemini`: `gemini`, its prompt sent on stdin — never as a `-p` argument, which a long prompt (or judge evidence) could overflow past the OS argument-length limit — with its own private `$HOME/.gemini` (`GEMINI_CLI_HOME` is set alongside `HOME`, since Node's own `os.homedir()` ignores `HOME` on Windows), holding only a confinement `settings.json` (telemetry, usage statistics, and checkpointing off, no MCP server configured) and the arm's `GEMINI.md`, so nothing but the arm's own instructions loads — no user settings, extensions, or memories (Gemini CLI's own bundled skills, such as `skill-creator`, and its built-in subagents still load unconditionally; nothing here turns them off). This runtime also pins a system-tier settings file (the highest-priority tier) with the same confinement values, and a decoy, empty workspace `.env`, so a trusted (`--skip-trust`) workspace `.env` or `.gemini/settings.json` an agent's own tool calls plant in the working directory during one turn cannot change what a later turn loads; such a file appearing, changing, or disappearing between turns refuses the run instead. `binary` (default: `TRIAL_GEMINI_BIN`, then `PATH`) and `readable` work the same as for `codex`. `"approval_mode"` (`"default"`, `"auto_edit"`, `"yolo"`, or `"plan"`, Gemini CLI's own choices) defaults to `"yolo"` confined and `"auto_edit"` unconfined, the same reasoning as Claude's `permission_mode`; the effective default is recorded the same way. With `"base_url"` set to a **Gemini-API-compatible** endpoint (never an OpenAI-compatible one — Gemini CLI always speaks its own native request shape) Gemini talks to that endpoint instead of Google's own public one; its own `settings.json` forces the `"gemini-api-key"` auth type for this, since Gemini CLI's own non-interactive auth check refuses the `"gateway"` auth type `GOOGLE_GEMINI_BASE_URL` would otherwise select on its own (`"base_url"` together with `"copy_auth"` is refused outright: `copy_auth`'s own OAuth login never reads it). Gemini CLI's own build-file protection (`Makefile`, `pyproject.toml`, `package.json`, and similar) denies `write_file`/`replace` on those files even in `"yolo"` mode; nothing here can turn it off, so a gemini arm is handicapped on a scenario that expects one of them edited directly (a shell command can still edit them). Gemini CLI has no CLI-level structured-output flag; as a judge, the JSON schema is asked for directly in the prompt (every `@` escaped first, so an agent's own final message cannot make Gemini CLI treat part of the prompt as a file or subagent reference) and the model's own reply text is parsed as that JSON — never a file the judge process itself might have written: its own `"plan"` approval mode is not actually read-only in headless mode (a model's own `exit_plan_mode` call is auto-approved non-interactively and switches the whole session to `"yolo"`), so an admin-tier policy denying that call (and `enter_plan_mode`, `write_file`, `replace`, `run_shell_command`, `invoke_agent`) is passed on every gemini judge call, and only a value this runtime itself parsed from the process's own stdout is ever trusted as the verdict. The plan's `judge` accepts the same `executor`, `model`, `base_url`, `binary`, `readable`, and `resources` settings as the other two.
- `command`: a shell command, for non-agent comparisons (scripts, builds, tools, or any deliverable a `check.py` can inspect) and for qualifying checks. It receives `TRIAL_PROMPT`, `TRIAL_SCENARIO_DIR`, `TRIAL_JOB_DIR`, and `TRIAL_INSTRUCTIONS` (the arm's instructions file, if any); `readable` and `confine: false` (skip confinement for this arm) work as above.
- `artifact`: no model call. `"artifact"` names a file or directory, relative to the plan, that *is* the alternative — a business plan, a recipe, a design, a pitch, anything a person or a judge can read. It is resolved and digested like `instructions` (a rerun that would judge different content under the same arm name is refused) and copied into the run's working directory unchanged. A single-file artifact's own text becomes the judged output directly; a directory with more than one file leaves a bounded listing there instead, unless the scenario's own `"artifact"` field (below) names one file inside it precisely. A scenario written for artifact arms is an evaluation context rather than a task: its `prompt` frames who is judging and against what (an investor, a home cook, an accessibility reviewer), and its `judge` question asks what that reader wants to know.

Any arm (or the judge) can also list `pass_env`: names of extra environment variables to pass into its run from this process's own environment, on top of the fixed allowlist (see [Confinement](#confinement)).

An arm's `"resources"` is a map from a path relative to the run's private home to a file or directory relative to the plan, copied read-only into that home before the run starts — a skill, a reference doc, or anything else an arm's instructions can point the agent at by a fixed path. Each source is resolved and digested like `instructions`, so a rerun that would give the same arm name different resource content is refused (`stub_skills`, under [Selection trials](#selection-trials), adds generated skills the same way), and is frozen under the run directory (`resources/<digest>/`) when the trial starts, so every job receives the content its recorded digest describes even when a source is edited during a long trial; a source that changed between loading the plan and freezing it refuses the run. For a `codex` arm (or the judge), a key under `~/.codex` that collides with a file `run_codex` writes itself (`config.toml`, `AGENTS.md`, `auth.json`, `models_cache.json`), or that would leave `~/.codex` or `~/.codex/sessions` itself read-only, refuses the run instead of silently losing the resource or breaking Codex's own session logging; a `gemini` arm (or the judge) is refused the same way for a key under `~/.gemini` colliding with `GEMINI.md`, `settings.json`, `oauth_creds.json`, or `google_accounts.json`. For example, to hand an arm a skill it can use, and tell it where to find it:

```json
{"arms": {"kernel": {"executor": "codex", "model": "${TRIAL_CODEX_MODEL}",
                     "instructions": "arms/kernel-with-skill.md",
                     "resources": {"skills/deploy-helper": "skills/deploy-helper"}}}}
```

where the arm's instructions file names the path in its own text (for example, "A skill at `~/skills/deploy-helper` covers this; read its `SKILL.md` first"). The copy is read-only, so the agent can consult it but not edit the very thing a check might compare its work against.

### Keys

An agent executor (`codex`, `claude`, or `gemini`) or the judge needs one API key variable, looked up in this order and never with a built-in default file:

1. The arm's own `env_file` — a shell snippet, typically `VAR=value` lines (though `export`, comments, and shell quoting are honored too, since the file is sourced, not parsed literally), read in a subshell outside any sandbox so only that one variable is ever exported to the run (and to nothing else, including this process).
2. Otherwise, `TRIAL_ENV_FILE` (an environment variable naming a file in the same format), when the arm names no `env_file` of its own.
3. Otherwise, the variable read directly from this process's own environment.

The variable name is `api_key_var` when the arm sets it; absent that, a Claude arm (or a Claude judge) defaults to `ANTHROPIC_API_KEY`, a Gemini arm (or a Gemini judge) defaults to `GEMINI_API_KEY` — the variable Gemini CLI's own `getAuthTypeFromEnv` checks to pick its `"gemini-api-key"` auth type, and the one still sent (as `x-goog-api-key`) when a `"base_url"` is also set, forcing that same `"gemini-api-key"` auth type rather than the `"gateway"` type `GOOGLE_GEMINI_BASE_URL` would otherwise select on its own (see the `gemini` executor above) — and a Codex arm (or a Codex judge) defaults to the model provider's `env_key` from this host's Codex config (`~/.codex/config.toml`), or `CODEX_API_KEY` when that config names none — the variable OpenAI's own docs name for authenticating a non-interactive `codex exec` process; `OPENAI_API_KEY` is not read by `codex exec` itself absent a provider config naming it as `env_key`, which is why most people — anyone with no custom `model_providers` block at all — need `CODEX_API_KEY` specifically. A key found nowhere is an error naming all three ways to supply it. `base_url` stays optional throughout: without it, Claude, Codex, and Gemini reach their own default endpoints; the key lookup is the same either way.

**Logging in without an API key.** Every executor above authenticates through an API key; a ChatGPT-login Codex CLI, a Claude.ai-login Claude CLI, or a Google-login Gemini CLI (none of which the key lookup above reaches) cannot run an arm or a judge with a key alone. The explicit opt-in `"copy_auth": true` on an arm (or the judge) copies this host's own login file(s) — `~/.codex/auth.json` for Codex, `~/.claude/.credentials.json` for Claude, `~/.gemini/oauth_creds.json` (and, when present, `~/.gemini/google_accounts.json`) for Gemini — into the run's private home before it starts, the same way `resources` does (above), and, for Codex and Gemini, skips the key requirement entirely (the copied login is the whole authentication; a Gemini arm's `copy_auth` also sets `GOOGLE_GENAI_USE_GCA=true`, which is what selects its own `"oauth-personal"` auth type). **This exposes that login to the agent under test**: it is a file in its own home like any other, and the arm's instructions, its tool calls, or a bug in its own code could read or exfiltrate it. Use `copy_auth` only when no API key is available and you accept that exposure for this trial's arms and judge. **For a Claude arm, `copy_auth` has no effect under this runtime**: `claude` runs `-p --bare` here (see below; an arm with `"bare": false` refuses `copy_auth` instead), and `--bare`'s own documented behavior is that OAuth and keychain state are never read, so a copied `.credentials.json` sits in the run's home unused; a Claude arm still needs an actual API key (`env_file`, `api_key_var`, or the process environment) either way. A Claude arm behind Bedrock, Vertex, or Foundry is not currently supported by this runtime either: it still requires an `ANTHROPIC_API_KEY`-style key even when those credentials are forwarded with `pass_env`.

## Scenario

```
scenario.json   {"prompt": "...", "followups": ["continue"], "timeout_s": 900,
                 "required": ["check_a", "check_b"], "bin": ["../_shared/bin"],
                 "artifact": "relative/path",
                 "judge": {"question": "...", "pass_when": "..."}, "judge_role": "...",
                 "judge_required": true}
                -- "sandbox" (confined/none/a Codex-native mode) is optional here; when omitted, the
                   scenario takes the plan's default (or --sandbox), which is how `--sandbox none` reaches
                   every scenario at once. Set it on a specific scenario only to override that default.
fixture/        copied into the working directory
setup.sh        runs in the working directory first (for example, to create a repo and a local origin)
bin/            fake tools, copied into the run and first on PATH; they may append JSON lines to $TRIAL_HARNESS/calls.jsonl
check.py        def check(run) -> {name: bool | number | str}; optional def judge_context(run) -> str
qualify/        good.sh and bad.sh reference behaviors for qualifying the checks
```

A run passes when the executor finished, every `required` check is `True`, and the judge (when the scenario asks one, `judge_required` is not `false`, and the plan names a judge) says `pass`. A scenario that asks a judge question under a plan that names no judge is invalid (`judge-missing`), never a silent pass — unless the scenario sets `judge_required: false`, in which case the `required` checks alone decide, exactly as without a `judge` field at all. Numbers and strings are reported as measures without deciding the pass. `followups` continue the same conversation, which is how a scenario reproduces a user sending "continue". `sandbox` here always wins over the plan's or `--sandbox`'s default (see [Confinement](#confinement)). `judge_role` replaces the judge prompt's opening sentence, which by default frames the subject neutrally as "one run of the task below" — never an assumption that the subject is an AI agent's code change; write a scenario-specific role when the judge should be told more about what it is looking at (for example, "You are a pastry chef judging one plated dessert against a written brief."). `artifact` names a file the executor was asked to write, relative to the working directory: when it exists, its own text becomes `run.final_message` (and what a judge sees) in place of the executor's transcript, so any executor — not only the `artifact` executor — can be compared on a specific deliverable it produced rather than on what it said about producing it. When it does not exist, `run.final_message` is an explicit "artifact not produced" marker instead of the transcript, and `result.json` records `artifact_missing: true` — never a silent fall-back to whatever the executor said, which is exactly the gap this field exists to close.

`check(run)` sees the resulting state and the native record: `run.workdir`, `run.harness`, `run.final_message`, `run.artifact_missing`, `run.messages`, `run.commands`, `run.calls` (fake-tool log), `run.usage`, `run.git(...)` and `run.git_rc(...)`, `run.file(rel)` and `run.read(path)`, `run.copy_workdir()`, `run.sandboxed(cmd, cwd=..., timeout=...)`, and the skill helpers `run.skills_loaded()`, `run.skill_loaded(name)`, and `run.skills_listed()` (see [Selection trials](#selection-trials)). Prefer checks on state (files, commits, remotes, tool calls) over checks on wording. `run.final_message` is the scenario's own `artifact` file when one is named and the executor wrote it, or otherwise the last `final-*.md` an executor wrote, or its last parsed message, or — for a command arm that wrote neither, such as a build or render step whose only output is its own stdout — that stdout's own bounded tail, so a command arm's plain output still reaches a judge's `<final_message>` without special-casing. When the scenario names an `artifact` and the executor never wrote it, `run.artifact_missing` is `True` and `run.final_message` holds an explicit marker instead of silently falling back to the transcript — a check that scores an artifact scenario should treat a missing artifact as a failure in its own right, not rely on the judge alone to notice.

The agent controls its repository's configuration, the links in its files, and its code, so a check reads and runs them only through these: `run.git` overrides git settings that run commands and runs git confined and read-only (unless this run resolved to `"sandbox": "none"`, in which case it runs the same way but unconfined — never a silent fallback when confinement was actually needed); `run.file` and `run.read` return nothing for a path that resolves outside the run directory or is not a regular file, and read at most 64 MiB; `run.sandboxed` runs agent-written code the same way (no network, the host read-only, the user's home hidden, its own process namespace, unless unconfined), typically on `run.copy_workdir()` so the working directory stays as the agent left it (the copy leaves out files over 256 MiB, and is empty when the agent replaced the working directory itself with a link).

## Confinement

By default (`"sandbox": "confined"`, whether from the scenario, the plan, or the built-in default) codex, claude, gemini, command, and judge runs execute inside bubblewrap: the host is read-only, the user's home is hidden, `/run` is hidden too (it holds Unix-domain sockets — a user systemd/D-Bus bus, a container runtime's control socket — with no network-namespace boundary of their own, so a read-only bind of the rest of the host would otherwise leave them fully reachable; whichever DNS stub resolver keeps its own files there is read back in read-only, so name resolution over the network confinement leaves reachable still works), only the run directory is writable, and everything the agent starts lives in its own process namespace and ends with the run; Codex's own sandbox is off inside it so agents can commit, and so is Gemini's own (`-s`/`--sandbox` is never passed to it). An `--out` outside both the user's home and `/tmp` is hidden the same way as those two, so a confined process cannot list its sibling run directories or read `plan.json` from its own job directory. Judges run the same way, able to write only their own opaque cell directory under `out/judges/.cells/` (see [Reading results](#reading-results)), with an environment built there. The read-only paths a confined `codex`, `claude`, or `gemini` run additionally needs (its resolved binary's own directory, the package root above it, a sibling `lib/` for an npm-style global install, and the interpreter a script's shebang names — for example the node runtime a JS launcher needs) are derived from the resolved binary itself, following symlinks, without assuming any particular install layout or directory depth; `readable` (below) adds more, for a `claude`, `gemini`, and a `command` arm the same as for `codex`. The user's home directory stays hidden even when the binary lives inside it: a package root discovered above the binary is punched back through only when it sits well below home, never when it IS home or one of its immediate children (`~/.local`, `~/.cargo`, `~/bin`, ...) — those are broad and can hold unrelated credentials. The binary's own containing directory is narrower still: it is exposed whole when it is scoped to this one executor — including an immediate child of home such as `~/bin`, where the binary is commonly the only thing there — but never one level below one of those (a shim placed directly in `~/.local/bin` or `~/.cargo/bin`, for example, as both a native app installer and an npm-style global install can produce), where only the binary file itself is exposed, never the shared directory around it (package managers and version managers fill those with many unrelated entries). A `binary` or `TRIAL_*_BIN` value is resolved the way a shell would — `~` expanded, then a bare name looked up on `PATH` — rather than treated as a literal path relative to the current directory. An arm's `resources` (above) stay read-only under confinement even against the agent's own `chmod`: each one is bound read-only again after the run directory itself, which the agent cannot undo the way it could a copy's own write bit alone; unconfined, that write bit is the only protection there is.

**The environment is an explicit allowlist, never the parent environment minus a scrub list.** A run's environment carries only: `PATH` (the scenario's copied tools first — so a scenario's own fake `gh`, `curl`, or `make` is always found before anything else — then a confined executor's own directories and interpreter, then system directories including `/usr/local` and Homebrew's, then — in unconfined mode only — this process's own `PATH` verbatim, so a host's Homebrew, `/usr/local`, or user-prefix toolchain is reachable when unconfined); a throwaway `HOME` and `TMPDIR`, always the run's own, never the real ones; `LANG`, every `LC_*` variable, `TERM`, `TZ`, `USER`, and `LOGNAME`; any names an arm lists in `pass_env`; and the one API key variable an agent executor or judge uses (see [Keys](#keys)). Nothing else — no other token, credential, or host-specific variable — reaches the run. Git and gh configuration are private to the run in every mode.

**Bubblewrap is required for confinement, with no silent unconfined fallback.** Where it is missing, a scenario, plan, or judge resolved to `"confined"` refuses to start rather than quietly running unconfined — this applies uniformly to agent arms, `command` arms, checks that call `run.git` or `run.sandboxed`, and judges alike. The only way to turn off checks', git's, and judges' own bubblewrap protection is the literal, explicit `"sandbox": "none"` — on the scenario itself, or as the plan's (or `--sandbox none`'s) default when the scenario names none of its own; nothing else does, so a typo or an unrelated value can never silently drop it, for a `claude`, `gemini`, or `command` arm's own process either: only `codex` has a sandbox vocabulary of its own, so setting `sandbox` to a Codex-native mode name (for example `"workspace-write"`) is passed straight through to a `codex` arm's own `-s` flag in place of this runtime's bubblewrap — but a `claude`, `gemini`, or `command` arm sharing that scenario, and checks and judges regardless of executor, stay bubblewrap-confined, exactly as under `"confined"`, since that value means nothing to them (Gemini's own `-s`/`--sandbox` flag is never passed at all, confined or not - see the `gemini` executor above). Every finished run records the sandbox mode it actually resolved to, and whether its own process actually ran confined, in its own `result.json`; a run directory that holds any unconfined run says so in `summary.md`'s header, whatever the directory's current default is, so an unconfined result is never mistaken for a confined one and a later rerun (including a `recheck --sandbox`) that changes the default cannot make the notice disappear.

Before scheduling any jobs — before `plan.json` is written, before `--out` exists, before any scenario's `setup.sh` has run — `run` refuses outright if bubblewrap is missing and any selected scenario would actually need it (any effective sandbox other than the literal `"none"`), rather than letting each job discover that on its own once its own executor or check first needs confinement. It also confirms, with `--version`, confined the same way a job would be, every agent binary an arm or the judge would otherwise find only by searching `PATH` (no explicit `"binary"`, no `TRIAL_*_BIN`): a broken PATH shim (a launcher that re-execs and cannot find the real CLI once confinement hides the paths it assumed) is caught once, plainly, rather than per job. This is the common failure mode for a version-manager shim (volta, mise, asdf), whose launcher re-execs the real CLI by re-reading `$HOME` — replaced with a throwaway one under confinement; the failure names `binary`/`TRIAL_*_BIN` and suggests resolving the shim once yourself (`volta which codex`, `mise which codex`, `asdf which codex`) and naming that path directly. An explicit `"binary"` is trusted as given and never preflighted.

A confined `claude` arm defaults `permission_mode` to `bypassPermissions` (safe only because the sandbox itself, not Claude's own permission system, is what actually restricts the host) and an unconfined one to `acceptEdits` instead, since `bypassPermissions` needs the sandbox to be safe; either way the effective default is recorded in the run's identity (above), so comparing a confined and an unconfined Claude arm's cost or behavior means also accounting for this difference in what the model was allowed to do. A confined `gemini` arm defaults `approval_mode` to `yolo` the same way, and an unconfined one to `auto_edit`, and the same "effective default is recorded" reasoning applies.

After a run the runtime writes, reads, and prunes the run directory without following a link, waiting on a special file, or stopping at a directory or permissions the agent left there, so what the agent planted cannot reach the host or end the trial; `derive` copies an artifact only when it is a regular file inside that run's own working directory.

**macOS and other hosts without bubblewrap.** Bubblewrap is Linux-only; on macOS (and a Linux host that simply lacks the package) every scenario needs `"sandbox": "none"` — set on the plan, or passed as `--sandbox none` on `run`/`recheck` — to run at all, since the built-in `"confined"` default refuses outright (see above) rather than silently running unconfined. Unconfined, an arm's own process, checks, git, and the judge all run directly on the host with the parent shell's own `PATH` reachable (see the allowlist above) — a throwaway `HOME` and working directory still isolate each run from the others, but not from the rest of the host the way bubblewrap does, and a Codex arm gets Codex's own `danger-full-access` sandbox rather than this runtime's. `trial.py` itself needs Python 3.11 or newer only if `~/.codex/config.toml` names a custom model provider (its `tomllib` reader is otherwise never invoked); macOS's own `/usr/bin/python3` is often older than that, so a Homebrew or python.org install is usually the one to run this script with.

## Qualifying checks

Before relying on a scenario, run its reference behaviors with the `command` executor:

```json
{"name": "qualify", "repeats": 1,
 "arms": {"good": {"executor": "command", "command": "sh \"$TRIAL_SCENARIO_DIR/qualify/good.sh\""},
          "bad":  {"executor": "command", "command": "sh \"$TRIAL_SCENARIO_DIR/qualify/bad.sh\""}},
 "scenarios": ["scenarios/gate-deploy"]}
```

The good behavior must pass and the bad one must fail. A check that only an agent can trigger (for example, one that reads agent command events) is qualified on agent runs instead.

## Two-stage trials

When the question is whether what an agent writes works for the agent that later follows it (a skill, a brief, a repaired instruction), judge the artifact by its consumer, not by reading it. After the authoring run:

```bash
python3 <skills-file-root>/scripts/trial.py derive RUN_DIR --scenario repair-ask-first-skill \
  --artifact skills/deploy-helper/SKILL.md --consumer scenarios/use-deploy-skill \
  --repeats 2 --plan consumer.json
python3 <skills-file-root>/scripts/trial.py run consumer.json
python3 <skills-file-root>/scripts/trial.py summarize CONSUMER_RUN_DIR --group
```

Each produced artifact becomes an arm named `<authoring arm>~r<repeat>`; `--group` pools them back into their authoring arm. Each derived arm's executor, model, effort, and `base_url` start from what its own source run actually recorded — so a two-stage trial reuses the same model by default, per source arm, rather than a guessed one — with `--executor JSON` overriding or extending them, for example `--executor '{"model": "claude-sonnet-5-5"}'` to keep the source executor but pick a model, or `--executor '{"executor": "claude", "model": "...", "base_url": "..."}'` to replace it outright. An agent executor (`codex` or `claude`) left with no model this way — an older run recorded none, and `--executor` names none either — is an error naming `--executor` as the fix; a `command` arm never needs one. A relative `env_file` in `--executor` is rewritten relative to the derived plan.

## Selection trials

A selection trial asks whether an executor, given a catalog of skills and a request, loads the skill the request needs and leaves the others alone. It is an ordinary plan with three additions.

**Placement.** Put each catalog skill where its host discovers skills, as an arm `resources` entry keyed by that location inside the run's private home, and keep the arm's instructions silent about it when the question is whether the host's own listing leads there:

| Executor | Home-relative location | Source |
|---|---|---|
| `codex` | `.agents/skills/<name>`, or the older `.codex/skills/<name>` | Codex docs, "Where Codex loads local skills"; `codex-rs/ext/skills/src/host_roots.rs` |
| `claude` | `.claude/skills/<name>`, read only with `"bare": false` (below) | Claude Code docs, "Skills" |
| `gemini` | `.gemini/skills/<name>`, or `.agents/skills/<name>` | Gemini CLI docs, "Managing Agent Skills" |

Every catalog also holds the host's own built-in skills (Codex's bundled `.codex/skills/.system`, Claude Code's bundled skills, Gemini CLI's built-ins), and Codex reads a host-wide `/etc/codex/skills`, which confinement leaves visible. Gemini CLI loads a skill headlessly only in approval mode `"yolo"`: its headless policy denies `activate_skill` and shell commands in every other mode, so a gemini arm that places skills under any other approval mode is refused before scheduling. Confined, `"yolo"` is the default; unconfined, set `"approval_mode": "yolo"` on the arm explicitly, which lets the agent run any command on the host without asking.

**Claude without `--bare`.** `--bare` skips skill discovery and gives the model no Skill tool, so a claude arm measures selection only with `"bare": false`, which runs `claude -p` without `--bare` in the same private home and confinement, authenticated by the API key alone. That run loads:

- from the private home, whatever the arm places with `resources` (none of it exists otherwise): `~/.claude/settings.json`, where `skillOverrides` sets each listed skill to `"on"`, `"name-only"`, or `"off"`; `CLAUDE.md` in `~/.claude`; `~/.claude/skills`, agents, commands, and installed plugins; `~/.claude.json` MCP servers;
- from the working directory, whatever the scenario's fixture or setup puts there: `CLAUDE.md`, `.claude/settings.json` with its hooks, `.claude/skills`, and `.mcp.json` servers, which `-p` loads without a trust prompt;
- from the CLI itself: its bundled skills and commands, built-in plugins and subagents, the Skill tool, and auto memory, which starts empty in the private home.

Claude Code also reads `CLAUDE.md`, `CLAUDE.local.md`, and the same instructions under a `.claude` directory (its `CLAUDE.md` and `rules/`) in every directory from the working directory up to `/`, so the runtime keeps everything above the run out of reach. The run directory sits inside the home's or `/tmp`'s tmpfs, and a confined arm with `"bare": false` also hides the directory above the home (for a home under `/home`, `/home` itself; a tool installed there, such as Homebrew on Linux, then needs `readable`). An `--out` outside both the home and `/tmp` is refused before scheduling, since hiding its parents could hide a system directory the executor needs. The runtime also hides the host-wide managed settings directory (`/etc/claude-code`), sets `CLAUDE_CODE_DISABLE_OFFICIAL_MARKETPLACE_AUTOINSTALL=1`, and refuses `copy_auth`, since a claude.ai login brings that account's own skills and connectors. With those in place, nothing but the run's home and working directory loads. Unconfined, none of this hiding exists, so `"bare": false` refuses to run unconfined, which rules it out where bubblewrap is unavailable. An organization's server-managed settings, which Claude Code fetches for an eligible key that talks to Anthropic's API directly, apply with or without `--bare`. Claude Code shortens or drops listed descriptions under its listing budget, so pin the listing state a trial depends on: place a `~/.claude/settings.json` whose `skillOverrides` names each skill whose description must be shown (`"on"`) or hidden (`"name-only"`).

**Detection.** In `check(run)`, `run.skills_loaded()` returns `{name: [evidence, ...]}` for each skill whose instructions reached the model, and `run.skill_loaded(name)` answers for one. A skill counts when the run's own record shows:

- a call to the host's skill tool: Claude's `Skill` (`plugin:name` counts for `name`) or Gemini's `activate_skill`, or a skill Codex injected for a `$name` mention;
- a file-read tool given a path ending in `<name>/SKILL.md`, in any form (`~`, absolute, relative, Windows): Claude's `Read`, Gemini's `read_file` or `read_many_files`;
- any other tool call whose output shows that SKILL.md's frontmatter (a `---` line, then a top-level `name: <name>` line; line numbers are ignored).

Shell commands are judged by what they returned, never parsed, so every way of reading a file counts (a glob, `find -exec`, `xargs`, `$(cat ...)`, a `cd` in an earlier call), and a command that only names a path does not (a listing, `rg --files`, a write or heredoc, `git add`, `apply_patch`, a comment). A failed call counts only when its output shows the frontmatter, and nothing a file-writing tool returns counts (Claude's `Write` and `Edit`, Gemini's `write_file` and `replace`). The remaining limits are deliberate: a read that skips the frontmatter (Claude's `Read` with a later `offset` excepted), a search that returns only matching lines, or a Gemini `read_many_files` given a glob does not count; a command that echoes a SKILL.md it writes (`tee`) or re-reads one the agent wrote does. Each entry's `evidence` names the call, so whenever a check's own corroboration disagrees with the detection (a correct deliverable without a load, or a load without one), read the evidence before counting the run. A skill the host merely listed never counts. `<name>` is the skill's directory name, which the portable skill format requires to equal its `name`.

`run.skills_listed()` returns `{name: description}` for the listing the host sent the model, with `""` for a skill listed by name alone: Codex's skills section from its session rollout, and Claude Code's `skill_listing` entries from its session transcript in the run's private home. It returns `None` for Gemini, whose record holds no listing. Claude's stream-json init event names the skills the CLI registered, which differs from the listing the model sees, so it is not used. A listing check is a placement check: it shows that the host picked the skill up and whether its description was shown, not that the model read it.

Before trusting a selection rate, qualify it on each host with a positive control (a request that plainly needs a placed skill, loaded on every run) and a negative control (an unrelated request done through tool calls, never loading it). A near-neighbor request that resembles the skill's own but does not need it measures over-selection.

**Padding.** A fresh home starts with only what the arm places, while a real catalog is larger and squeezes each host's listing budget (Codex lists skills within about 2% of the context window, or 8,000 characters when the window is unknown; Claude Code within 1% by default; each shortens or drops descriptions beyond that). An arm's `"stub_skills": {"dir": ".agents/skills", "count": 35, "chars": 13900, "seed": 0}` adds `count` generated skills under `dir`, read-only like resources: neutral names and descriptions about unrelated hobbies, the `chars` split evenly across the descriptions (each at most a word short of its share), and the same stubs for the same spec. Stubs join the arm's resources digest, and may not land inside or on top of a `resources` entry.

**Reading the result.** A selection rate belongs to one host, model, effort, and catalog: its size, the neighbors each skill competes with, which descriptions the host shows, and that host's built-ins. Report it that way; it does not carry over to another host or catalog.

## Re-scoring stored runs

After a check changes, `trial.py recheck RUN_DIR` re-scores finished runs without running any agent again and keeps their stored verdicts; `--rejudge` also asks the plan's judge again with the scenario's current question and evidence, and `--judge JSON` does so with a different judge, which becomes the directory's judge: it re-judges every run the judge scores, refusing before it judges anything when the checks of one of them fail to run and changing nothing when the new judge gives no verdict for one of them, so `--only` cannot limit it while scenarios outside `--only` have finished runs with a judge question; `--only s1,s2` limits the others to those scenarios. `--sandbox confined|none` overrides the directory's plan-level default sandbox for this and future rechecks (a scenario's own `sandbox` still wins), the same as `run --sandbox`. A run whose verdict comes from another judge than the directory's (or that has none) does not score: `recheck` reports it as `judge-stale` until `--rejudge` judges it. `--rejudge` too changes nothing when the judge gives no verdict for a run, and names the judge's error. Directories written before 2.0.2 counted a judge error as a failure; a plain `trial.py recheck` reclassifies it as invalid. A judge decides runs the checks cannot, so qualify it the way checks are qualified: fixed reference outcomes (the same state with different replies, for example), each judged several times, where the expected verdict is known. A judge from another model family than the executors guards against a judge that favors its own family's style.

## Pairwise judging

`required` checks and the per-run judge each score one arm's run against a fixed bar; they cannot say which of two arms that both pass is better. `trial.py pairwise RUN_DIR --arms A,B` does: a plan `"pairwise": {"arms": ["A", "B"]}` block names the default pair so a bare `trial.py pairwise RUN_DIR` needs no flags. For every `(scenario, repeat)` where both `A` and `B` finished (`status: "ok"`) and the scenario asks a judge question, a blind judge sees both outputs' own `run.final_message` and, when the scenario's `check.py` defines `judge_context`, each one's own evidence too (the same text and evidence a per-run judge would see, including a scenario's `artifact` override) labeled only "response 1"/"evidence_1" and "response 2"/"evidence_2" — never an arm's name, and never which one is which — and is asked which better answers the scenario's judge `question`, or "tie"; it is asked twice per pair, once with `A` shown first and once with `B` shown first, so a judge that just prefers whichever answer comes first is caught rather than mistaken for a real preference. If `judge_context` raises for either side, neither side gets evidence for that pair (never just the side whose call happened to succeed), and the pair's own record (below) carries an `evidence_errors` object (`"a"` and/or `"b"`) naming what failed. Each judge call's own working directory is an opaque, per-pair id that names neither the scenario nor either arm (a person looks it up from the pair's own result file, below), since a CLI can put its own working directory in the model's context and that would otherwise tell it which response is which arm. `--judge-model MODEL` runs the pairwise judge with a different model while keeping the run directory's judge executor and other settings; without it, the directory's own judge is used as recorded. The judge runs confined exactly like a per-run judge (see [Confinement](#confinement)), and a judge that produces no verdict on either order makes that pair invalid, never a guess.

A pair is decisive and consistent only when both presentation orders name the same arm; a tie in both orders is consistent but not decisive; anything else — the two orders disagreeing, or one deciding while the other ties — is order-inconsistent, reported separately and never averaged away. `A`'s win rate (with a 95% Wilson interval) is computed only over decisive, consistent pairs. Results land under `RUN_DIR/pairwise/<A>__<B>/<scenario>__r<n>.json` (each pair's both-order verdicts, arms, and outcome, plus `cell`: the id of its actual judge transcripts under the arm- and scenario-blind `RUN_DIR/pairwise/.cells/<cell>/order-1/` and `order-2/`, each kept exactly as a per-run judge's own directory is) and the aggregate at `RUN_DIR/pairwise/<A>__<B>.json`; `summarize` (both the markdown and `--json`) and `report` include every aggregate found there, keyed `"A__B"`.

## Reading results

`summary.md` lists passed / valid runs per scenario and arm with intervals, a per-arm table of mean input tokens, output tokens, cost (when an executor reports one — Codex, Claude, and Gemini each report different fields, and Gemini reports no cost at all), commands, seconds, and a count of runs that reported no usage at all, plus each check's rate; with a `baseline` arm (from the plan or `--baseline`), every other arm's cost and timing cells show a percentage difference from it. Invalid runs (timeouts, executor errors, broken checks, `judge-missing`, a judge that gave no verdict, a verdict from another judge than the directory's) are listed separately and never counted as failures of the arm; `--retry-invalid` reruns them, and transport failures are retried automatically. A directory holding any run that resolved to `"sandbox": "none"`, or whose own process ran unconfined for any other reason, says so in the header, whatever the directory's current default is. Each run's host caches (such as a Codex plugin catalog, and a `copy_auth` login file once the run is over) are pruned when it finishes, and the directories of its private home, where resources and stub skills sat read-only for the agent, are made owner-writable again, so a finished run directory deletes with a plain `rm -rf`. Once a run's checks and judge (when it asks one) finish and `result.json` is written, its own regenerable build output — a Cargo `target/`, a Go or npm build cache, `__pycache__`, a toolchain or crate download in the run's private home (`.rustup`, a Cargo `registry`), wherever they sit under the run's own directories — is pruned too, by default: every scenario that builds agent code does so from a fresh copy of `work/` in the check's own scratch directory (see [Scenario](#scenario) and `evals/scenarios/_shared/no_interpreter.py`'s `copy_tree`/`cargo`/`go`, and `checks.tests_pass`'s `copy_workdir`), never from `work/` itself, so no check or a later `recheck` ever reads build output there; a 144-run trial with a handful of compiled scenarios can otherwise fill a disk with nothing but rebuildable output (tens to hundreds of MB per Rust run alone). `result.json`'s own `pruned_build_output` field lists what was removed, relative to the run directory, when anything was; `"prune_build_output": false` on the plan, or `TRIAL_PRUNE_BUILD_OUTPUT=0` in the environment, keeps it instead (see [Plan](#plan)). The runtime also stops scheduling what keeps failing: after `TRIAL_FAILURE_STREAK` (default 6; 0 turns it off) consecutive executor failures of one executor family (executor, model, endpoint), that family's remaining runs are skipped, and after that many consecutive judge errors, every remaining run that needs the judge is; skipped runs are never written, the run exits 3 naming the cause, and running the same plan into the same `--out` once the cause is fixed runs them. The runtime stops scheduling when free space falls below `TRIAL_MIN_FREE_GB` (default 5); its own stop message names this pruning and says such a directory's build output is always safe to delete by hand too, for the same reason. Each run directory keeps `events.jsonl`, the final messages, `calls.jsonl`, `result.json`, and, for Codex and Claude, the executor's own session files (the exact instructions it received) - Gemini CLI's own chat log holds no instructions, only turns; the judge's own prompt, verdict, and usage live under the opaque `out/judges/.cells/<cell>/judge/` directory `result.json`'s own `judge_cell` field names (see [Confinement](#confinement) for why it is opaque).

**A run's own usage is read the way each executor actually reports it, not summed blindly across every event.** Codex's own `turn.completed` usage is a running total across the whole thread — it only ever increases across a follow-up's `codex exec resume` — so a run with `followups` keeps only the LAST such event's numbers, never the sum of all of them (which would multiply a multi-turn run's real spend several times over). Claude's own per-call `usage` on a `result` event is not a running total — each follow-up reports only that turn's own tokens — so those figures ARE summed across turns; that event's own `total_cost_usd`, though, IS already a running total across `--continue`, so it is likewise kept from the last event, never summed. A non-finite or negative value (the run directory is writable inside the sandbox, so the process under test can append its own lines to `events.jsonl`) is dropped rather than corrupting a mean.

**Cost and timing figures are means over every run that reached that stage, whether or not it later passed** — a run a check or judge ruled invalid still spent whatever tokens, dollars, commands, or seconds its own record shows; excluding it would understate the real cost of an arm that fails expensively. `seconds` is the executor's own wall time only, never setup, checks, or judging, each timed and recorded on its own (`setup_seconds`, `checks_seconds`, `judge_seconds`) instead. `input_tokens` carries no percentage between two arms that used different executors: Claude's own count excludes cache reads that Codex's includes, so the same field name is not the same measurement across them; the raw number is still shown, labeled by executor.

**A baseline percentage is computed per scenario, then aggregated across scenarios** — never pooled from every run across every scenario at once. For each field, and each scenario where both arms have a value, `(arm's mean on that scenario − baseline's mean on that scenario) / baseline's mean on that scenario` is one data point; the arm's percentage difference is then the **median and the mean** of those per-scenario points, alongside `n_scenarios` (how many scenarios contributed). Pooling every run together first can let one scenario's mix of expensive, excluded runs flip the sign of the whole comparison — for example, if a cheaper arm's few timeouts on one scenario are the only invalid runs there, pooling-and-valid-only would count that scenario's other, cheap runs but drop its expensive ones, while computing the percentage per scenario first (on every run, valid or not) does not let that happen. Report the number of scenarios along with the median and mean; a comparison over few scenarios is only loosely bounded, the same way a handful of runs only loosely bounds a pass rate.

`summarize --json` mirrors this: a `scenarios` object keyed `"scenario|arm"` (as before), an `arms` object with each arm's `passed`, `valid`, `runs`, `usage_mean` (every numeric usage field, including nested ones and cost, meaned over every run that reported it — see above), `no_usage` (how many of this arm's runs reported no usage at all), `commands_mean`, and `seconds_mean`, and, with a baseline, a `pct_vs_baseline` object giving each other arm's `{"median": ..., "mean": ..., "n_scenarios": ...}` for each field (an `input_tokens` entry is omitted between two different executors — see above); with any pairwise results on disk, a `pairwise` object as described above. An explicit `--baseline` (on `summarize` or `report`) naming no loaded arm is an error listing the valid arms; the plan's own stored `baseline` naming none — for example after `--arms` filtered it out — is not, the same as leaving `--baseline` off entirely.

## Report data

`trial.py report RUN_DIR [--out FILE] [--baseline ARM]` writes one JSON document meant for a visualization agent to read and render — data only: no HTML, no chart, no verdict of its own. It never runs an agent or a judge; it only reads what `run`, `recheck`, and `pairwise` already wrote. Its shape:

- `name`, `run_directory`.
- `plan`: `arms` (each arm's recorded settings and digests — `executor`, `model`, `effort`, `base_url`, `instructions_sha256`, `artifact_sha256`, `resources_sha256`, `command`, `allowed_tools`, `permission_mode`, `approval_mode`, `bare`, whichever apply), `scenarios` (each one's `name`, `prompt`, `followups`, `judge` question, `judge_role`, `required` checks, and `artifact` field), `judge` (its settings the same way an arm's are given), and `decision_rule` — the plan's own free text stating how to decide, carried through verbatim when the plan has one, omitted otherwise (`report` states no rule of its own).
- `runs`: one record per finished run — `job`, `scenario`, `arm`, `repeat`, `status`, `passed`, `valid` (`passed is not None`), `invalid_reason` when invalid, `checks` (the check values `check.py` returned), `judge` (`verdict` and `reason`, when a judge scored it), `usage`, `commands`, `seconds` (the executor's own wall time; `setup_seconds`, `checks_seconds`, and `judge_seconds` alongside it), `confined` (whether this run's own process actually ran under bubblewrap), `artifact_missing` (true when the scenario named an artifact the executor never wrote), and `final_message_excerpt` — the judged output's own text, truncated to a bounded size (`REPORT_EXCERPT_CHARS` in the code) so the document stays sized for a visualizer's own context, not for reading the full native record (which stays in the run directory itself, named by `run_directory` and each run's `job`).
- `arms` and `scenarios`: the same per-arm and per-scenario aggregates `summarize --json` reports, each with a 95% Wilson `interval` added.
- `pairwise`: every pairwise aggregate found under `RUN_DIR/pairwise/`, keyed `"A__B"`, exactly as `summarize --json` includes them.
- `baseline` and `pct_vs_baseline`, when a baseline arm is named (by `--baseline` or the plan's own `"baseline"`) — the same percentage differences `summarize` shows.

Nine cases run five times each are nine cases, not forty-five: judge generalization by the number of distinct scenarios, and keep a few scenarios out of development so they can test whether a change generalizes.
