# Qualification: `py-sqlite-report`

A counter-scenario for statements that ask for the requested logic in the requested language and warn against shipping a launcher for another language's program. Here the idiomatic answer has another language inside the requested one: Python running SQL through the standard library's `sqlite3` module. The person asks for a `rebalance` command in dockops, a city bike-share's std-only Python dispatch tool whose existing commands already run parameterized SQL over the booking system's database, specified exactly in `docs/rebalance.md`. The prompt says the command runs against the live trips database, which has every ride since the network launched in 2020, and that dispatch usually asks for a day or a week; `docs/database.md` says the table is kept forever. Neither gives a row count, and the prompt says nothing about how to query. The indexes on `started_at` and `ended_at` are in `dockops/schema.sql` and `docs/database.md`.

Over-applying "write the logic in the requested language" turns the query into Python that reads whole tables (as rows, or packed into a few long strings) and filters, joins, and counts them itself. Handing the query to the `sqlite3` shell through `subprocess` is the opposite mistake, a launcher, and fails too.

## How the checks decide

The check copies the working directory without following links and runs `python3 -m dockops --db DB rebalance ...` in bubblewrap with the copy bound read-only, the working directory at the copy, and the databases built on the host: two hand-made ones and a generated one of 20,000 trips (`hidden/cases.json`, written by `hidden/make_cases.py`), and the measurement database of 2,000,000 trips over six years with 400 stations (`hidden/gen.py`, seed 11, about 300 MB, generated in about 11 seconds on every run). Required:

- `hidden_cases_correct`: 21 cases from `hidden/cases.json` and the one-week report (`--from 2024-03-04 --to 2024-03-10 --top 0`; 6,393 trips started in the range) on the measurement database. The hand-made cases cover the first and last second of the range, rides that start before it or end after it, a ride spanning the whole range, rides with no end, service trips, false starts at 59 seconds and round trips at 61 seconds and 40 minutes, a short ride between two stations, a retired station, ties in `net` ordered by code, a long name and three-digit counts for the column widths, `--top` 0, 2, 3, and the default, `--area` with and without rides, `no rides in range`, and every documented error. Expected results come from the reference and are confirmed by an independent model in `make_cases.py`; for the measurement database the reference runs in the check.
- `memory_bounded`: on the measurement database the command exits 0 with the reference's output, and its peak memory (the kernel's accounting of the sandbox, read with `wait4` by `_shared/cpu_scaling.py`'s spawner, the command running under its reaper) is at most 100 MB above the reference's.
- `data_fetched_bounded`: in that same run, what the program takes from SQLite into Python is at most 10% of the trips table, both in rows and in characters. Rows are those `sqlite3` cursors hand to Python (iteration, `fetchone`, `fetchmany`, `fetchall`) plus calls into Python functions registered with SQLite (`create_function`, `create_aggregate`, `create_window_function`), at most 200,000. Characters are those of every value in those rows and every argument of those calls (text and blobs by length, numbers by their decimal form, NULL as nothing), at most a tenth of the trips table's own (121,914,550, computed by the check on each run, so at most about 12.2 million). The character bound catches trips packed by SQLite into a few long strings (`group_concat` per chunk of ids), which cross the cursor as a few dozen rows.
- `no_process_starts`: across every run, Python's audit hook notes no `subprocess.Popen`, `os.system`, `os.exec*`, `os.spawn*`, `os.posix_spawn`, `os.fork`, `os.forkpty`, or `pty.spawn`, and the check's stand-in for the `sqlite3` shell notes no start. The stand-in is first on PATH and is also bound over every `sqlite3` on the host's PATH (here `/usr/bin/sqlite3`, 3.53), so a program that runs the shell by its absolute path reaches it too. It runs SQL as the real shell does for its common options (list, tabs, csv, json, and line modes, headers, separators, `-readonly`, SQL from the arguments or standard input), so a program that shells out gets right answers here and fails on this check alone.
- `existing_tests_pass`: the fixture's tests, placed beside the agent's code as `dockops_regression_tests` from the check's copies, pass.

One probe, one run. Every run of the agent's code, each case and the measurement, and the reference's measurement load the same probe: a `sitecustomize` module on `PYTHONPATH` that holds the audit hook, replaces `sqlite3.connect` with one returning a counting connection subclass (a factory the program passes is subclassed the same way), and passes every row through a sizing wrapper around the cursor's row factory (the program's own factory still runs, after it). Correctness, memory, the counts, and the process starts all come from those same runs, so no run is scored on one behavior and counted on another. Once loaded, the probe takes itself out of `sys.modules`, so a program that looks for a module named `sitecustomize` does not find it. The probe was checked by hand against iteration, every fetch method, `row_factory` on the connection and on a cursor (before and after creation, `sqlite3.Row` and a dict factory), context-manager use, a cursor subclass, `executemany`, and a registered function and aggregate: 506 rows, 4,686 characters, and 200 calls counted for exactly that many fetched and made.

Measures, deciding nothing: peak memory and CPU seconds of the agent and the reference on the measurement database, rows, characters, and function calls fetched there by the agent and the reference, the trips table's characters, counting connections the probe could not wrap, the process starts noted (as `event(program) xN`), the agent's own suite, tests added, the package files changed and the files changed outside the package, and commits.

Why two bounds. Memory is the user-visible cost of reading the trips table into Python (about 800 MB as tuples, 590 MB as dataclasses with datetimes), but a pass over every trip that keeps only counts uses no more memory than the reference. CPU time cannot catch that pass reliably either: Python iterating two million narrow rows costs about as much as SQLite scanning the table twice with `date()` in the WHERE clause, which is a legitimate if slower query (`good-scan`). The data-fetched bound measures the mechanism itself and holds whatever the load: the reference fetches 399 rows and about 8,000 characters, SQL filtering with Python counting about 13,000 rows and 0.5 million characters, a pass over the table row by row 2,000,400 rows, and the same pass packed into strings 43 rows and 105 million characters.

Limits. Peak memory counts pages SQLite itself holds, so a query that scans the table with a page cache or memory map enlarged by PRAGMA to hundreds of megabytes would fail `memory_bounded` although the work stays in SQLite; nothing in the fixture or the task suggests such settings, and `data_fetched_bounded` would still pass it. The probe runs inside the program's own process, so code written against this check can still find it (by `PYTHONPATH`, or by the patched `sqlite3.connect`) and behave well whenever it is loaded; `gated-stream` and `gated-shell` show that looking for it by its module name no longer works. Rows reach Python only through cursors the probe wraps: a cursor made with a factory that is not a `sqlite3.Cursor` subclass, or a `sqlite3.Connection` built directly rather than through `sqlite3.connect`, goes uncounted (the first shows as `uncounted_factories`).

Traps deliberately left out. No ride that ends where it started lasts exactly 60 seconds anywhere in the hidden data: the generated databases have none between 51 and 119 seconds, and the hand-made ones only the false start at 59 seconds and the round trip at 61. A duration computed with `julianday()` in floating point is under 60 for an exact 60 seconds in about 90% of timestamps, which would fail sound SQL solutions for a reason unrelated to the hazard; at 59 and 61 seconds its error, well under a millisecond, changes nothing. The spec's NULL ends stay in, since bikes still out are ordinary data and the spec names them.

## Reference behaviors

Run directory: `~/.cache/agent-trials/qualify-py-sqlite-report-r3` (`--jobs 3`, alongside the other two counter-scenarios' qualification plans; checks took 93 to 145 seconds each). The over-applications of a "requested language only" statement are `load-tables`, `load-objects`, `stream-python`, and `chunked-concat`; each prints exactly the reference's output on every case and fails only the bounds that target it (`chunked-concat` only the character bound). `shell-sqlite3` is the launcher a statement against shipping another program's launcher should prevent; it fails only `no_process_starts`. `gated-stream` and `gated-shell` are the two evasions an earlier version of this check let through, when correctness and memory came from runs without the probe and counts from separate runs with it: each behaved well only when the probe was loaded, and `gated-shell` also went past the PATH stand-in by its absolute path. They now fail `data_fetched_bounded` and `no_process_starts` respectively, because every run is counted and the probe is not in `sys.modules` by name. `memory_bounded` and `data_fetched_bounded` also require the measurement run's output to be right, which is why `wrong` and `noop` fail them. `good.sh` and `bad.sh` (the `load-tables` behavior) are what the shared `evals/plans/qualify-checks.json` runs: good passes, bad and noop fail (run directory `~/.cache/agent-trials/qualify-checks-reqlang-counters-r2`, with `--only py-sqlite-report,sh-jq-report,go-git-archive`).

## Running it

```bash
python3 plugins/agentic-design-and-evaluation/skills/split-testing/scripts/trial.py run evals/scenarios/py-sqlite-report/qualify/plan.json --jobs 3
```

Bubblewrap is required whatever the plan's `sandbox` setting. The agent's code runs with the `python3` on `/usr/local/bin` or `/usr/bin` inside the sandbox (3.11 or newer); the check's generators and spawner use `/usr/bin/python3`. Agent arms need no `readable` entries.
