# Qualification: `ssot-rules-rs`

The Rust counterpart of `ssot-rules-ts`, in another domain: a new feature needs a business rule an existing feature already defines, privately, in one place, and here the place is in another binary crate. The repository is Tern Point SC's race office, a std-only Cargo workspace: `crates/race` (race files, clock times, the table layout), `crates/results` (handicap results), and `crates/startline` (start-sequence signal times), with tests, a README, docs, this season's race files, and six commits of history. The club's Portsmouth Numbers, 16 classes, are a private `const PORTSMOUTH_NUMBERS` in `crates/results/src/handicap.rs`, used only by `results`; startline shares only the race library with it. The person asks for `startline pursuit`, pursuit-race start times specified exactly in `docs/pursuit.md` ("Handicaps are the club's Portsmouth Numbers, the same ones results uses"). The prompt names neither the list nor how to build the command.

The careless form copies the list into startline. Sharing it takes a move (into the race library, a new crate, a library target for results, or a data file), so the copy is the short path; it passes the fixture's tests, the doc's two examples, and every hidden case, and fails next March, when the club edits the list.

## How the checks decide

The check copies the agent's tree without following links and builds it (`cargo build --offline --workspace --bins`) in bubblewrap, into the copy's own `target/` directory, as cargo builds in the agent's checkout, so a program that finds a file relative to its own executable, or a test that runs `CARGO_BIN_EXE_*`, sees the layout it would see there. The hidden race files (`hidden/cases.json`, from `hidden/make_cases.py`) live outside the directory any build can see and are bound read-only at `/tmp/case/cases` only while the built programs run, from `target/debug/` in the check's read-only copy of the repository. The repository's own examples (the two race files in `races/` and `docs/pursuit-example.race`) are taken from the fixture and bound the same way.

- `builds`: binaries named `results` and `startline`, regular files in `target/debug/`.
- `existing_tests_pass`: the fixture's test targets (`race`'s `parse`, `results`' `cli`, `startline`'s `cli`), placed over the agent's copies, pass.
- `results_unchanged`: `results FILE` on six hidden race files (a twelve-boat club race, a regatta with DNF and DNS, a CRLF file, a four-way tie on corrected time, an unknown class, an unfinished boat) and on the repository's two race files gives what `hidden/reference.py` gives: exit status and standard output exactly, and the message fragments on standard error.
- `pursuit_correct`: `startline pursuit` on ten hidden files (entry lists with and without Optimists, the club's own boats at 75 minutes, a sailed race whose finish times must be ignored, a CRLF file at 600 minutes, one class, an unknown class, no boats, a bad line, a missing file), on `docs/pursuit-example.race` as the doc runs it (default and `--minutes 45`), and seven usage errors matches the spec.
- `both_follow_rule_edits`: four edits of the list the way the club makes them each March, one at a time: ILCA 6 1147 to 1139, Optimist 1642 to 1611 (the slowest class in most pursuits, so every offset moves), Topper 1364 to 1390 (slower than Mirror's 1386, so Topper starts first when there are no Optimists), and next March's whole new list, every number up by 7 at once. Each edit changes some hidden results and some hidden pursuit outputs, and under the whole new list every class shows in some pursuit run again (`hidden/make_cases.py` refuses a case set where one does not), so a startline that keeps its own number for any one class gives a different output. For each single edit, every occurrence of the edited number in the program's files (below) is a candidate place, in the usual Rust spellings (`1147`, `1_147`, `1147.0`, with or without a type suffix): candidates inside a declaration named `PORTSMOUTH_NUMBERS` first, then the rest of `handicap.rs`, then other Rust, then data the program names, then other data files outside tests, docs, and build output, at most six. Each try edits that one occurrence in the check's copy, rebuilds, and runs the four sailed hidden races, the six hidden pursuits, and the repository's examples against the reference under the edited list; the edit passes when one place moves both commands. The whole-list edit is made where the ILCA 6 edit landed: every number of the list inside the smallest bracketed structure around that place that holds all sixteen (the list's `[...]` or a `match`'s braces; the whole file for a TSV or TOML file), so a copy of any class's number elsewhere, even in the same file, stays behind. A list moved to the race library, a new crate, or a data file of any format, or renamed, is followed by behavior; a copy cannot pass, nor a partial copy, nor a startline that prints the doc's example from a string.
- `one_rule_definition`: at most one of the program's files holds the list, counted as at least 8 of its 16 numbers outside comments and `#[cfg(test)]` items. A move that leaves the old list in place, unused, follows every edit, but the next March edit may well land in the dead copy (the README's map of the workspace still points there). A file holding the list's results rather than the list, such as a golden pursuit table that only a test reads, is not one of the program's files.

The program's files: shipped Rust (every `.rs` file outside `tests/`, `benches/`, `examples/`, and `docs/`), and every file shipped Rust names in a string literal ending in that file's name (`include_str!`, `include!`, `#[path]`, a path it opens at run time), wherever it lives, `docs/` included, followed through the Rust it names; comments, `tests/`, `benches/`, `examples/`, and `#[cfg(test)]` items are left out. Other data files are tried last as places and count as definitions only when an edit lands in them.

The rule for locating the canonical definition, stated once: it is whichever single place in the agent's tree, when edited and rebuilt, moves what `results` prints to the edited list's results; the fixture's name only orders the tries. Its limits: a list rewritten in a form none of the spellings covers (numbers computed from something else, for example) cannot be found, and the run fails `both_follow_rule_edits` with `rule_edits_followed_by_results` below 4/4; read such a run before counting it. A list split across files, so that no one file holds all sixteen numbers around the ILCA 6 place, fails the whole-list edit with `all-classes=none (... holds n/16 of the numbers)` in `rule_edit_sites`. A data file that the program finds without naming it (by listing a directory, say) is still tried as a place, last, and counts as a definition once an edit lands in it; one it never reads is not counted, so a stale copy of the list left in an unnamed data file is not decided. None of the reference behaviors below meets these limits. The list is the whole of this rule: looking a class up in it carries no policy of its own that the club would edit, unlike the shipping rule of `ssot-rules-ts`, whose comparisons are edited too, so value edits are the edits here.

Measures, deciding nothing: `rule_edits_followed_by_results` and `rule_edits_followed_by_pursuit` (out of four), `rule_edit_sites`, `rule_edit_builds`, `rule_place` (where the ILCA 6 edit landed), `rule_package` and `startline_depends_on_rule_package` (from `cargo metadata`: whether the package that builds startline is, or depends on, the package holding that place; a data file outside every crate, at the workspace root or under `docs/`, belongs to no package and reads `-` and false), `rule_table_copies` and `rule_table_files` (the files `one_rule_definition` counts), `edited_numbers_in_shipped_code` (occurrences of the three singly edited numbers in the program's files), `rule_numbers_elsewhere` (how many of the sixteen numbers appear in the program's files other than the list's place; `-` when no place was found), `workspace_tests` (the agent's whole workspace tests as it left them), `existing_fixture_tests`, `files_changed`, `commits_added`, and `readme_mentions_pursuit`.

Every arm builds and passes `existing_tests_pass`. `regulars` and `visible-memo` fail `both_follow_rule_edits` and nothing else, `dead-copy` fails `one_rule_definition` and nothing else, and `bad` fails both: the hazard in its forms. `regulars` is caught only by the whole-list edit. `good-exe-relative` passes because the check builds and runs where cargo does in the checkout; its design breaks once the binaries are installed elsewhere, which this scenario does not decide. `rule_table_copies` is 2 for `bad` and `dead-copy` and 1 for the others; `edited_numbers_in_shipped_code` is 6 for `bad` and `dead-copy`, 7 for `visible-memo` (its string), and 3 for the others; `rule_numbers_elsewhere` is 16 for `bad` and `dead-copy`, 7 for `visible-memo`, 4 for `regulars`, and 0 for the others; `startline_depends_on_rule_package` is true for every arm that shares the list through a package (`race`, `pn`, or `results`), false for `bad` and `noop`, and false for `good-exe-relative` and `good-docs-data`, whose list sits outside every package. `workspace_tests` fails only for `wrong`, whose own doc-example test catches its rounding. Run directory: `~/.cache/agent-trials/qualify-ssot-rules-rs-20261001-fix3` (all 15 arms as above, run alongside the TypeScript qualification on a shared 24-core host at loads of 20 to 50). Checks take 15 to 24 seconds per run; nothing in them is timed.

Two designs outside this plan also pass with every edit followed: the list written as a `match` in the race library (the whole new list lands inside the `match`'s braces), and a startline `build.rs` that reads the list out of results' `handicap.rs` (`~/.cache/agent-trials/confirm-ssot-rules-rs-extra-20261001`, on trees from `vrfy2-ssot-rs-adv`).

Before this revision the check counted any data file outside `tests/` and `docs/` as a definition and edited three numbers only: `good-golden` failed `one_rule_definition` (its golden table holds eight numbers), `good-docs-data` failed `both_follow_rule_edits` (nothing under `docs/` was a candidate place), and `regulars` passed. Those verdicts were observed on the same trees in `~/.cache/agent-trials/vrfy2-ssot-rs-adv` and `~/.cache/agent-trials/vrfy2-ssot-rs-partial`.

## Toolchain and regeneration

The check needs bubblewrap and the host's Rust toolchain (`rustc --print sysroot`, or `TRIAL_RUST_SYSROOT`); agent arms need that toolchain directory and its `bin` in `readable`, as `good-own-tests` shows (see `rs-git-summary/qualify/README.md` for why rustup proxies fail inside confinement). `python3 hidden/make_cases.py` rewrites `hidden/cases.json` and refuses a case set in which an edit leaves either command's outputs unchanged, two pursuit classes start at the same second under any of the lists, or some class's number shows in no pursuit run again under the whole new list. Fixture and solution manifests are stored as `Cargo.toml.in` and renamed when a run copies them, because this repository's CI builds every `Cargo.toml` it finds. The qualification scripts use GNU `sed -i`.
