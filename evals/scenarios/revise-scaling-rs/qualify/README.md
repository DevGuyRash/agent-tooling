# Qualification: `revise-scaling-rs`

The person asks for a fix to bookdesk, a std-only Rust workspace for a city's leisure centres: a library that reads and checks the booking system's nightly export, and the front desks' tool with `clashes`, `usage`, and `check` commands, export and clash-list docs, a cron script with a 30-minute `timeout`, tests with a Kingsgate sample week, and four commits. It was written when the export held one centre's bookings (about 10k). Since all fourteen centres moved onto one system the morning clash list is killed at its limit; the export holds about 2.4 million bookings over about 1,100 facilities. The prompt asks for the list to finish again, exactly as it is, and names no cause or technique.

The defect under test is complexity left in existing code, in two places. `parse_export` (crates/booking/src/lib.rs) looks each booking's reference up among all bookings accepted so far, and `find_clashes` (crates/bookdesk/src/clashes.rs) compares every pair of bookings, normalizing both facility codes (an allocation each) for every pair. The old code takes 5 s on 10k bookings and 17 s on 20k; on 2.4 million it would need days. Removing the defect means neither place compares each booking with all the others: a map of references or sorting, and grouping by facility and date (then a sweep, or pairs within a facility-day). Running the comparisons on threads, raising the cron limit, or making each comparison cheaper leaves them quadratic, and fixing one place leaves the other. A search for repeated references that relies on the export's documented order (docs/export.md says it lists bookings in reference order) or looks only at the most recent lines is fast and right on every valid export, but misses repeats in an export that went wrong, which the old code reports; the hidden cases include such exports.

## How the checks decide

The check copies the working directory without following links, builds it with `cargo build --release --offline --workspace` in bubblewrap before any hidden input exists, and runs the built `bookdesk` in bubblewrap with everything read-only. Required:

- `builds`: the release build yields `bookdesk`.
- `hidden_cases_correct`: fifteen hand-made exports in `hidden/cases/` (three and more bookings overlapping at once, including identical times and a one-minute booking inside others; block bookings listed after the slots they cover, with a cancelled block and an all-day one; back-to-back and one-minute overlaps, midnight and 23:59 edges; seventy bookings in a scrambled export order on two courts; facility codes typed with case, spaces, and a tab; cancelled bookings inside overlaps; the summary line's singular forms; a header-only export; Windows line endings with blank lines; references given twice, three times, after an invalid line, and on a line that is itself invalid; references repeated in an export out of reference order, as exact copies and with other details; every kind of bad line; no header) and two generated ones: a valid export of about 20k bookings, and an invalid one of about 40k whose references are in scrambled order and nine of whose lines repeat a reference thousands of lines after its first line. `bookdesk clashes EXPORT` must give the reference's exit status and standard output byte for byte, and its standard error too. The reference (`hidden/reference/`, the fixture with both places rewritten) prints exactly what the fixture's own code prints on every hidden input, which the `noop` arm (the fixture's code) passing this check shows on each run.
- `existing_tests_pass`: the fixture's own test targets and their data (`crates/booking/tests/parse.rs`, `crates/bookdesk/tests/cli.rs`, `crates/bookdesk/tests/data`), placed over whatever the agent left, pass with `cargo test --offline -p booking -p bookdesk --test parse --test cli`.
- `existing_commands_unchanged`: `usage` on hand-made and generated exports (with `--centre` in lower case, given twice, and unknown), `check` on valid, Windows, generated, invalid, duplicate-reference, headerless, and missing exports, six usage errors, and an unreadable file (`hidden/existing.json`) give the reference's exit status, standard output, and standard error exactly.
- `scales_to_city_size`: on generated exports (`hidden/data.py`, deterministic) of about 2.4 million bookings (the size the person gives) and 150k (a sixteenth), `clashes` exits 0 with the reference's output byte for byte; its CPU time stays within 10 times the reference's plus 1 s at each size; and its growth in CPU time from the small input to the large one is at most 3 times the reference's.

How CPU time is measured and decided: the protocol in `_shared/cpu_scaling.py`, which is the one `perf-dedupe-ts` and `perf-dedupe-py` carry inline (see `perf-dedupe-ts/qualify/README.md` for its design and calibration): CPU time of every process and thread in the sandbox from the kernel's accounting, with a reaper as the sandbox's first process; rounds of (reference small, agent small, reference large, agent large) back to back, the median of up to three rounds deciding growth; an agent run stopped at its CPU bound, a size failing on the second stop. The growth bound is 3 here rather than 2; see Calibration.

Measures, deciding nothing: medians over the rounds of CPU seconds and their ratios to the reference, both growths and each round's growth ratio, peak memory, the cases and existing commands that failed, the build log's tail when the build fails, the agent's whole workspace tests, tests added, commits, files changed, whether `scripts/morning-clashes.sh` changed, and whether shipped Rust starts threads or processes.

`bad`, `micro-opt`, `partial`, and `by-date` leave exactly the reference's output on every hidden case and on both generated sizes, so they fail only the check that targets the defect. The first three, and `noop`, compare every pair somewhere and are stopped on the small input, at the bound of 10 times the reference's 0.3 to 0.5 s of CPU time plus 1 s. `by-date` is the subtle one: a date holds about one booking in 300 of the export, so on the small input it costs only about 1.5 times the reference's CPU time, but the facilities grow with the city and it is still quadratic. On the large input it costs 9 to 10 times the reference's CPU time, right at the CPU bound, and the CPU bound is what has stopped it in every run; in a round it finishes, its growth is 6 to 8 times the reference's, which the growth bound of 3 rejects as well. `centre-date` is the same kind of remnant with a smaller constant, and it passes. Comparing every pair of one centre's bookings on a date is quadratic in the facilities per centre, which also grow with the city, but with fourteen centres it makes roughly a fourteenth of `by-date`'s comparisons: about 1.5 times the reference's CPU time on the large input and 1.3 times its growth, far inside both bounds, although its comparisons grow about 240 times for 16 times the data (2.7 million on the small input, 640 million on the large, against `by-date`'s 35 million and 8.8 billion). The scaling check catches grouping coarser than a facility's day only when its constant brings it near the CPU bound. This is the perf scenarios' limit that superlinear work too cheap at these sizes is not caught; a sweep per date with one running list across all facilities is in the same class. The arm is in the plan to keep the limit on the record, and its passing is the expected outcome. (Pairs within one facility across all dates, by contrast, are bounded by the calendar, not the city, and are acceptable.) `wrong` passes the fixture's tests (the sample week has no booking that overlaps two others still running) and fails the hidden three-way overlaps, block bookings, spelling, scrambled-order, and one-facility cases. `bsearch` and `window` are fast and wrong in `parse_export`: `bsearch` takes docs/export.md at its word that the export lists bookings in reference order and binary-searches the bookings accepted so far, and `window` looks only at the last 64. Every valid export is in reference order without repeats, so both pass everything except the exports that went wrong, where they print a clash list and exit 0 while the old code reports the repeats and exits 1: `bsearch` on the hand-made `repeats-out-of-order` and the generated invalid export, `window` on the generated one, whose repeats come thousands of lines after their first line. `over-reach` also fails `hidden_cases_correct` on the duplicate-reference and invalid exports because `clashes` prints the reworded problems: rewording a library's messages changes every command that shows them. `good.sh` and `bad.sh` follow the convention of the shared `evals/plans/qualify-checks.json`: good passes, bad and noop fail.

Runs, each with the command arms and `--jobs 3` on a 24-thread host (AMD Ryzen 9 3900X) busy with other work, at the same time as the TypeScript scenario's runs (load average about 40 to 70). On the current files: `~/.cache/agent-trials/qualify-revise-scaling-rs-r5` (the table) and `~/.cache/agent-trials/qualify-revise-scaling-rs-r6`, with the same outcome for every arm. In `r6`, `good` passed at 1.15 (0.96, 1.34), `good-buckets` at 1.55 (1.58, 1.52), and `centre-date` at 1.36 times the reference's CPU time on the large input with a growth of 1.38 (1.58, 1.18); `bsearch` and `window` failed only their cases; `by-date` was stopped on the large input in its first round (71 s against the reference's 6.9 s); `bad`, `micro-opt`, `partial`, and `noop` were stopped on the small one; `wrong` and `over-reach` failed the same cases and commands. Checks took 24 to 123 s, except `by-date` (191 and 315 s), whose stops on the large input cost 70 to 95 s of CPU time each. After those two runs only the check's docstring and comments and the layout of one of its lines changed; `~/.cache/agent-trials/qualify-revise-scaling-rs-r7` ran `good`, `bsearch`, `window`, and `noop` on the final files with the same outcomes (`good` at 0.94, `bsearch` failing `repeats-out-of-order` and `generated-repeats`, `window` failing `generated-repeats`, `noop` passing every case and stopped on the small input). Earlier runs, `qualify-revise-scaling-rs-r1` to `-r4` in the same directory, were on the files before the exports that went wrong and the `bsearch`, `window`, and `centre-date` arms were added (fifteen correctness cases). Every arm they share had the outcome it has now, `by-date` stopped on the large input each time it ran (58 to 71 s against 5.7 to 7.0 s); `r1` used a growth bound of 2, at which `good-buckets` reached 1.96 in one round.

## Calibration

On this host the reference takes 0.2 to 0.5 s of CPU on the small input and 4.6 to 9.8 s on the large one depending on load, with a peak of about 810 MB on the large input; its growth is 12 to 24, more than the sixteenfold data, because its hash maps (2.4 million references, 330k facility-days) leave the cache on the large input. Correct solutions leave it differently: measured unsandboxed in three interleaved rounds at a load average of 60 to 130, `good-buckets` grew 1.22 to 1.86 times as much as the reference from 150k bookings to 2.4 million (1.07 to 1.79 from 75k, 1.31 to 2.11 from 300k), while `by-date` grew 5.9 to 7.9 times as much (4.6 to 8.8 across the three small sizes). The growth bound of 2 the perf scenarios use left `good-buckets` at 1.96 in one round of the first run, so this scenario's bound is 3, which still rejects `by-date` with room to spare; code that compares every pair is stopped by the CPU bound on the small input long before growth matters. A larger small input does not help: at 300k the reference's growth falls to about 10 and `good-buckets` still reached 2.11.

The old code takes 17 s on the generated 20k-booking correctness case and about 3 s on the generated invalid one, which it rejects before looking for clashes (the check allows 120 s per case). The generated export lists bookings in reference order with dates spread over ten months, about 6 bookings per facility a day on a slot grid, about one desk booking in 150 at an off-grid time (a third with the facility code typed in lower case or with spaces), and about one block booking in 2,000; about 13k clashing pairs on the large input. Generating the scaling inputs takes about 11 s of the check's time and about 160 MB of the check's scratch space; they are written fresh into the check's scratch directory after the builds and never exist where the agent works.

The generated invalid export (`hidden/data.py 40000 12 OUT 9`, `broken()`) is the 40k export with its references given in scrambled order and nine more lines, each repeating the reference of a line in the first quarter at least a quarter of the export later, alternately as an exact copy and with another booking's details; the old code reports all nine. It is 40k because the old code's search of every earlier booking makes a much larger invalid export too slow for the `noop` arm's check (about 11 s of CPU at 60k on this host, and unfinished after more than two minutes at 150k). That leaves one gap: a revision that keeps a correct search up to some size and switches to an order-dependent or windowed one only above 40k would pass, because every larger input is a valid export in reference order.

## Running it

```bash
python3 plugins/agentic-design-and-evaluation/skills/split-testing/scripts/trial.py run evals/scenarios/revise-scaling-rs/qualify/plan.json --jobs 3
```

Bubblewrap is required whatever the plan's `sandbox` setting, along with the host's Rust toolchain (`rustc --print sysroot`, or `TRIAL_RUST_SYSROOT`) and python3 at `/usr/bin` or `/usr/local/bin`. Agent arms need the toolchain readable inside confinement, as the scenario's description shows. The fixture's manifests are stored as `Cargo.toml.in` and renamed by `setup.sh` (and by `qualify/common.sh` for any solution manifests), because this repository's CI builds every `Cargo.toml` it finds.
