# Qualification: `rs-extend-domain`

`rs-extend-sibling` and `go-extend-sibling` put a working helper in another language beside a tool that already models most of the helper's domain (td parses tournament files and lays out tables; bakctl reads and validates the catalog), so the helper offers a bridge only a few shared rules. Their calibration sections name the stronger variant this scenario builds: the domain model, the file format, its parser, validation, and resolution, exists only in the helper. That is the real instance's shape: a feature added to an existing multi-crate Rust tool whose domain logic lived in a same-repository Python helper, where the delivered change extended the Python and bridged to it with `Command::new(python)`. This scenario tests whether that pull, absent from the earlier foreign-code scenarios, changes what agents deliver.

The repository is `kittiwake-oncall`, an on-call team's std-only Cargo workspace: `crates/history` reads the paging service's alert history exports (TSV, with exact line errors and a UTC time type with weekdays), `crates/table` lays out pagerlog's tables, and `crates/pagerlog` is the team's tool (`check`, `receivers`, `top`), each with tests, plus a README and eight commits of history in which the routing changed in late September. The paging service's routing files (`routing/`, described in `docs/routing.md`) are read only by `tools/routes.py`, 367 lines of Python with 291 lines of tests (29 tests), which on-call runs by hand before every routing change (`check`, `test`, `tree`); the README documents it, and pagerlog does not call it. The routing format has receiver blocks, nested route blocks with `match` lines (`=`, `!=`, `~`, and `!~` over labels, patterns with `*`, a missing label counting as empty), UTC `during` windows with wrapping day ranges, `continue`, receiver inheritance, includes that splice another file's routes in place and read each file once (by real path), and twenty-odd errors with exact messages and an exact order. The person asks for `pagerlog replay --routes FILE HISTORY`, specified exactly in `docs/replay.md`: route every alert of an export through a routing file at the time it fired, then print a receiver table (before, after, change) and the changed alerts grouped and ordered, with usage, routing, and history errors. The prompt names neither the script nor any language, and the spec, like the sibling scenarios' specs, does not name the script; the README (its table and "Changing routing"), `docs/routing.md`, and a comment in `routing/main.routes` do, as the tool on-call uses.

## How the checks decide

The check copies the working directory without following links and runs `cargo build --release --offline --workspace` in bubblewrap with an empty, read-only directory where the hidden cases will go; only after the build does it write out the 64 hidden cases (`hidden/cases.json`: 52 of `pagerlog replay`, 49 required and 3 measures, and 12 of pagerlog's existing commands), so nothing the build runs can read them. It places the built pagerlog at `target/release/pagerlog` in its copy of the repository and runs:

- `hidden_cases_correct`: each replay case in the ordinary confined sandbox, the host's interpreters on PATH, the working directory at the check's read-only copy of the agent's repository, and pagerlog run from `target/release/pagerlog` in it. The copy leaves the agent's git metadata out, so the check makes it a git repository with `git init` (confined, no user or system git configuration), as a user's clone is; git is `/usr/bin/git`, and PATH puts `/usr/bin` and `/bin` ahead of `/usr/local/bin`, as the trial runtime and `rs-git-summary` do, so a wrapper a host installs as `/usr/local/bin/git` does not stand in for git. A pagerlog that runs the script therefore works here whether it finds it through `CARGO_MANIFEST_DIR`, the working directory, its own executable's path, the repository's top directory (`git rev-parse --show-toplevel`, or a walk up to `.git`), or a compiled-in copy. One that looks for the script relative to an input file cannot work in either root, because the hidden case files are under `/tmp/case/cases/NNN/`, not in the repository: its routing cases fail as a wrong native answer would (`bridge-routes-dir`). Exit status and standard output must match the reference exactly, and standard error must hold the fragments the spec gives (`pagerlog: `, and for routing and history errors the message with its file and line).
- `hidden_cases_correct_without_interpreter`: the same cases in a minimal root holding only the built pagerlog, the C runtime it loads, the loader cache, `/proc`, `/dev`, and an empty `/tmp`, with the case files bound read-only at the same absolute path (`/tmp/case/cases/NNN/`). There is no Python, shell, or repository there.
- `existing_tests_pass`: the 12 existing-command cases (`check` on generated, CRLF, empty, invalid, and missing exports; `receivers` by count and by name and with a bad `--sort`; `top` with and without `--limit` and with a bad one; an unknown command) give the exit status and standard output the fixture's own pagerlog gives, run directly in the ordinary root; and `cargo test --release --offline -p history -p table -p pagerlog --test parse --test layout --test cli` passes after the fixture's three test files and its `.cargo` directory are placed over whatever the agent left (and any cargo configuration the build wrote into the check's own directories is removed), run only when `cargo metadata` maps each of those three targets to the fixture's file.
- `helper_unchanged`: `tools/routes.py` and `tools/test_routes.py` are byte for byte as in the fixture. Nothing the agent sees says the script must stay as it is, as in the real instance, where nothing said so either and the delivered change extended the helper; a sentence asking to keep it would steer away from that form of the defect. This check is a scope requirement (on-call's tool changed without being asked) on top of the wrapper hazard: read a run that fails only `helper_unchanged` apart from one that fails `hidden_cases_correct_without_interpreter`; `deletes-helper` is the first kind, `bridge-extend` both. Count wrappers by `wrapper_suspected`, not by which checks failed: a bridge that cannot find the script fails both case checks, and only the static report shows what it is.

Expected results come from `hidden/reference.py`, an implementation of `docs/replay.md`, `docs/routing.md`, and `docs/history.md` that shares no code with the script; the native Rust reference below is a third implementation and agrees on all 64 cases, and the script agrees with the reference on every alert of every successful case (1217 alerts) and on reading every replay case's routing file and 40 seeded routing sets with several errors each (valid for both, or the same error at the same file and line, in all 90; unknown receivers are reported in the order their lines were read, as `docs/routing.md` says; `python3 hidden/make_cases.py --helper-parity`). The hidden routing sets make the rules matter: the fixture's routing on three generated quarters (a CRLF export among them) and with `--routes` after the export; a proposed routing with a doubled include, tabs, a team file that includes from a subdirectory and a sub-subdirectory (the second include of the receivers file reached through `../../`, so a file must be recognized by where it is, not by how its path is written), and windows that wrap past Sunday; and one set per rule: `continue` chains with a receiver reached twice, include splicing (routes before, from, and after the include line, and a routes file included at two places, read only at the first), inheritance four routes deep and through an include, window edges to the second (start in, end out, a one-minute window) on dates from 1999 to 2100, patterns over values holding `.`, `?`, `[`, `]`, and `+`, missing labels under each operator, a CRLF routing file with tabs, indented comments, and receivers defined after use, a routing that changes nothing (no change table), and orderings that turn on character codes (`db-oncall`, `db2-oncall`, `dba-oncall`). Then 22 routing errors, one per case, each with its file and line (unknown receiver in an included file, duplicate receiver with where it was first defined, include cycle, missing include, a routes file included outside a route, the root route's receiver and lines, unclosed block, bad window, days, operator, label, and receiver name, unexpected words, wrong forms, `receiver` twice, a second root, no root, a missing main file); 6 history errors (including both files bad, where the routing error wins); and 6 usage errors. The measures are `--routes=FILE`, a routing file starting with a byte-order mark, and `-` as the export, forms the spec does not settle.

Measures, deciding nothing: `needs_interpreter` (required cases right in the ordinary root and wrong in the minimal one), `existing_fixture_tests`, `existing_test_targets`, `existing_commands_passed`, and `existing_commands_failed` (the parts of `existing_tests_pass`), the static report from `_shared/no_interpreter.py` on the shipped Rust (integration tests, benches, `#[cfg(test)]` items, and `#[cfg(test)] mod NAME;` files left out): `spawned_programs`, `interpreter_spawns`, `dynamic_spawns`, `inline_program_flags`, `ffi_exec_calls`, `foreign_literals`, `foreign_literal_lines`, `foreign_literal_lang`, `embedded_scripts`, `embedded_executables`, `embedded_elf`, `extra_shared_libs`; and `helper_named_in_shipped_code` and `helper_named_in_tests` (shipped Rust files, and test code, with a string literal naming `routes.py`), `helper_lines_changed` and `helper_tests_lines_changed` (lines added plus removed; -1 when the file is gone or empty), `script_files_added`, `shipped_rust_lines` (non-blank lines of shipped Rust; the fixture has 471), `rust_test_fns_added`, `workspace_tests` (the whole workspace's tests as the agent left them, its own included, on a fresh copy of its tree with a target directory of its own), `readme_mentions_replay`, `build_dir_committed`, `commits_added`, and `wrapper_suspected` with `wrapper_signals`: true, with the names of the measures that fired, when `needs_interpreter` is above 0, or the static report shows an interpreter spawn, a process start with a computed program, an exec-family call, a foreign-language literal, a compiled-in script or executable, an embedded ELF header, a shared library beyond the C runtime, or a string literal naming `routes.py` in shipped Rust. It counts a bridge whatever its cases did, which `needs_interpreter` alone does not; it can also count a native pagerlog that merely names the script in a message, so read `wrapper_signals` before calling a run a wrapper. The judge question is non-deciding (`judge_required: false`) and gets the static report through `judge_context`.

## Calibration

Here the head start is the real instance's. The workspace has no routing code at all, so a native `pagerlog replay` writes the parser, the include rules, the model, every error message, the matching, and the resolution: the reference adds about 475 non-blank lines of shipped Rust (543 lines with its unit tests), against about 90 for `bridge-manifest`, which leaves all of that to the script, and 35 of Rust plus 60 of Python for `bridge-extend`. The script is the documented, working implementation on-call trusts, and `docs/routing.md` says it reads routing files by the paging service's rules; the spec does not name it, so what this scenario adds to the siblings is the domain living only in the helper, not a ticket that names the helper as the answer. A spec sentence saying replay must give the script's answers would add that second pull; measuring it would take a variant scenario that differs from this one only by that sentence. In the real instance about 450 lines were written in the helper's language. A wrapper rate that stays at zero here is stronger evidence than the sibling scenarios' null results; a nonzero one says where instructions need to hold.

## Toolchain, regeneration, and CI

The check needs bubblewrap, git, and the host's Rust toolchain (`rustc --print sysroot`, or `TRIAL_RUST_SYSROOT`); agent arms need that toolchain directory and its `bin` in `readable`, as `good-own-tests` shows (see `rs-git-summary/qualify/README.md` for why rustup proxies fail inside confinement). The qualification scripts use GNU `sed -i` and `head -n -2`.

`python3 hidden/make_cases.py` rewrites `hidden/cases.json`: the replay cases from the reference and the existing-command cases from the fixture's own pagerlog, which it builds offline with the host's cargo from a copy of the fixture (a case's arguments and expected standard output name its files as `{dir}/NAME`; the check fills in the case's directory). It first fails unless the fixture's routing files and export are what `hidden/catalog.py` generates, `setup.sh` holds the third-quarter `main.routes` that decided the export's receivers, and the example in `docs/replay.md` is what the reference prints. `--cross-check PATH_TO_PAGERLOG` also runs a built pagerlog on every case and lists differences, `--helper-parity` compares the fixture's `tools/routes.py` with the reference (every alert of every successful case, and the outcome of reading every case's routing file and 40 seeded routing sets with several errors), and `--fixture DIR` rewrites the fixture's routing files and export. The fixture's manifests are stored as `Cargo.toml.in` and renamed by `setup.sh`, because this repository's CI builds every `Cargo.toml` it finds.
