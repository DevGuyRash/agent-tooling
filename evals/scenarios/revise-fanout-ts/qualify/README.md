# Qualification: `revise-fanout-ts`

The repository is plugctl, an existing TypeScript tool that Node runs directly, for a city's public charging network (list, read, and status commands, a client for the charge-point hub's line protocol whose timeout destroys the socket, a fake hub for its `node:test` tests, four commits of history). Its `status` command already does what the availability map needs: it asks every charger, prints one line per charger sorted by ID as `read` prints it, `CP-0412: no answer` when a charger has not answered within 2 seconds, `CP-0412: error 503 charger fault` on an ERR reply, a total line, and exits 0, 1, or 2. It asks one charger after another, so at today's 300 chargers it takes close to a minute. The hub's documentation (`docs/hub-protocol.md`) allows one account at most 16 TCP connections at a time, closes any beyond that without a reply, counts a connection until the reply is sent or the client closes it (shutting down the sending side counts as closing), holds a silent charger's connection for up to 30 seconds, and suspends an account that keeps going over. The person reports that the map's refresh job kills `status` at 15 seconds and asks to get it back under that, with the output and exit codes unchanged and without getting the hub account suspended, pointing at the doc for the hub's rules. The prompt names neither the cause, a technique, nor connections.

The defect is in code that already works: the one-charger-at-a-time loop the earlier change left. Removing it means asking chargers concurrently within the hub's limit. Keeping one charger at a time and trimming around it (a shorter wait per charger) stays over the budget, and so do too few connections at a time (2 or 3) and batches of 16 that each wait for their slowest charger; stopping at a deadline and reporting the rest as `no answer` meets the 15 seconds by not doing the work; `Promise.all` over the whole list, or a pool sized from `os.availableParallelism()`, is refused past 16; racing each reply against a timer without destroying the socket leaves connections open past the limit (and keeps Node alive, unless the sockets are unreferenced); moving the 2-second cutoff changes the lines of chargers that answer just inside or just past it; moving `read` onto the same new path as well, or giving the shared client a default timeout, changes `read`'s behavior.

## How the checks decide

The checks are those of `async-fanout-go`, on this fixture's hub, with the same driver design (one request line per connection, a connection limit), run through Node instead of a built binary, except for the time limits and the edge and overdue chargers described below. Every case runs `node bin/plugctl.ts status` from a read-only copy of the agent's repository, with `PLUGCTL_HUB` set, in its own bubblewrap sandbox: host read-only, home, `/tmp`, and `/run` hidden, its own network and PID namespaces. Node is the host's (`TRIAL_NODE` names another real Node binary), bound read-only when it lives under the home, and must run the fixture's TypeScript directly or the run is invalid. `hidden/driver.py` serves the hub on 127.0.0.1 inside that network namespace; the dataset and expected report are made in `check.py` and reach the driver on standard input. After the command exits the driver keeps the hub listening for 2 seconds, kills everything left in the sandbox, and only then prints its verdict.

The hub counts a connection from the moment it is accepted until it starts sending the reply, or until the client closes it; before refusing one it drops counted connections whose client has hung up, for up to 50 ms. A refused connection's request still counts as asked for. Connections counted longer than 8 seconds while the command ran count as held.

The cases:

- Main: 300 chargers. 280 answer in 30 to 150 ms; 5 slow ones in 1.0 to 1.2 s and 3 edge ones in 1.55 to 1.65 s (all within the 2 seconds, so read); 2 overdue ones in 2.4 to 2.8 s and 3 late ones only after 3.2 to 5.5 s (so `no answer`); 4 offline ones whose connection the hub holds for 30 s, then `ERR 504 charger timeout`; 3 get `ERR 503 charger fault` or `ERR 502 garbled reply`. Rated powers include `7.4` and whole numbers. The list comes in commissioning order, unrelated to ID order. Offline chargers are drawn from the first quarter of both the ID order and the list's order, the others from the first 60%. The edge and overdue chargers pin the cutoff: a client that moves it by more than about 0.4 s either way (below 1.64 s or past 2.41 s on these datasets) reports one of them wrongly, and a correct client keeps at least 0.35 s on either side for the host's delays (the correct arms' longest connection in every run on this host was 2.06 s).
- All answering: 36 chargers.
- Outage: 300 chargers, 20 offline, 27 slow, 3 edge, and 2 overdue, all in the first third of both orders.
- No hub: exit 2 within 10 s.
- Existing commands: `list`, `read`, and usage errors run one after another against a small hub, with the arguments, environment, and expected output the fixture's tests use (`read` keeps the order given, stops at the first ERR reply with the error on standard error, waits for the hub's own reply on a charger that takes 3 seconds, `--hub` wins over `PLUGCTL_HUB`, `--hub=` works).

The run is invalid (not failed) when the CPUs the check may run on are 16 or fewer, so a pool sized from `os.availableParallelism()` is judged alike on every host that decides.

The time limit is the ticket's 15 seconds, for the main case and the outage alike (the refresh job kills `status` at 15 seconds whatever state the network is in), plus only what the host adds to a correct client's time. `hidden/reference_client.py`, a correct client at the documented limit, runs first against the main dataset, up to three times, stopping once its best time is within 1.25 times the 4.04 s it spends waiting on the hub (16 slots taking chargers in ID order, each answering charger's latency or 2 s for each silent one); whatever its best time takes beyond those 4.04 s is the host's slack, added to the 15 seconds for both cases. The run is invalid (not failed) when even that best time is more than 1.5 times the 4.04 s, so the slack never exceeds 2.0 s. The slack is added rather than multiplied in: a client whose own waits add up to more than 15 seconds cannot pass on a loaded host, and a client within a second or two of the budget is the only one whose verdict the host's load can decide. The seconds each kind of client spends waiting on the hub alone on these datasets (main / outage) keep every arm below clear of that band in at least the case that decides it: 16 workers 4.0 / 6.4 s, 12 at a time 4.8 / 8.5 s, 8 workers 6.8 / 12.8 s, 4 workers 13.6 / 25.4 s (inside the band on an ordinary day, far past it in the outage), 3 workers 18.1 / 33.9 s, 2 workers 27.2 / 50.8 s, batches of 16 20.5 / 15.7 s; a pool of 6 (9.1 / 17.0 s) is the natural size nearest the boundary, and its verdict can depend on load. The reference also runs once against the outage, as a self-check and a measure. A sequential client cannot beat the floor (51.0 s here), however idle the host, and no limit reaches it. The main and all-answering cases are killed only at twice the floor (102.0 s), so the fixture's own status, which is correct, finishes and fails `within_budget` alone; the outage is killed 10 s past its time limit, and its report is judged only when it finished within that limit.

Required:

- `answered_chargers_correct`: one line per charger sorted by ID, each answering charger's line exactly as `read` prints it, in the main, all-answering, and outage cases.
- `failures_handled`: `no answer` and `error <code> <text>` lines as before, the total line, exit 1 (main, outage) and 0 (all answering), and exit 2 within 10 s with no hub.
- `within_budget`: the main case exits by itself within its time limit, having asked for every charger, and the outage within its own.
- `within_limit`: the hub refused no connection in the main, all-answering, and outage cases, and the main case asked for at least one charger.
- `no_held_connections`: no connection counted longer than 8 s in those cases, and the main case asked for at least one charger.
- `no_work_after_exit`: no connection reached the hub after the command exited by itself, and no process was left, in every case; the main case asked for at least one charger. A case the check killed is judged on processes left alone, since a connection in flight at the kill can reach the hub just after it.
- `existing_commands_unchanged`: `list`, `read`, and the usage errors behave as the fixture's tests expect and print what the fixture prints, run as commands.

Measures, deciding nothing: the seconds and limits of each case and of the reference (`reference_ideal_seconds` is its waiting alone, `host_slack_seconds` what the host added), peak and attempted connections, refusals, abandoned and held connections, the longest connection (the reference's too), connections open at exit, mean connections open, requests per charger, the CPUs the command could use, `source_lines_changed` and `source_files_changed` (lines added plus removed, and files touched, in `src/` and `bin/` against the fixture), `test_lines_changed` and `test_files_changed` (the same for `test/`), `fixture_tests` (the fixture's own 17 tests from the check's copies against the agent's code, under `node --test`), `own_suite`, `commits_added`, `final_words`.

## Running it

```bash
python3 plugins/agentic-design-and-evaluation/skills/split-testing/scripts/trial.py run evals/scenarios/revise-fanout-ts/qualify/plan.json --jobs 3
```

The check needs bubblewrap, `/usr/bin/python3` (3.8 or later), a Node that runs `.ts` directly (22.18+ or 23.6+; `TRIAL_NODE`), and more than 16 CPUs whatever the plan's `sandbox` setting. Agent arms need Node readable only when it lives under the home. A check takes about 45 to 70 s for a good solution and about 130 to 150 s for one that stays sequential.
