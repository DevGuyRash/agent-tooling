# Qualifying heal-native-mixed

`heal-native-mixed` is `../../heal-mixed` with one change: the seven session logs are not markdown files under `fixture/.local/agent-sessions/` any more. `setup.sh` calls `native/build_native_logs.py`, which writes them as native Codex rollout JSONL under `$HOME/.codex/sessions/YYYY/MM/DD/` and native Claude Code project JSONL under `$HOME/.claude/projects/<encoded-cwd>/`, in the run's own private home (the same `$HOME` `isolated_env` builds before `setup.sh` runs - see `references/trials.md`'s "resources", which use the same home). The prompt no longer names `.local/agent-sessions` or any host; it just says "my recent coding-agent sessions." Every embedded problem and the judge question are unchanged from `heal-mixed`. The one check that could not survive the move, `transcripts_unchanged` (it compared `fixture/.local/*` inside the checkout), is replaced by `native_logs_unchanged`.

A first pass at this rewrite was reviewed and found to have several defects; this document (and the scenario) reflect the fixes. See "What this check does and does not cover" and "Known simplifications" below for what remains open.

## How the native logs are generated

- **Timestamps and content.** Each of the seven sessions' start time is `NOW - offset`, computed once when `setup.sh` runs (`NATIVE_LOGS_NOW`), so they always fall inside the past week regardless of when the trial runs. Each offset now carries a distinct seconds component so the seven don't all start at the same `:SS` mark.
- **Commit dates track the sessions, not a fixed calendar.** `setup.sh`'s own six git commits are dated from the same "now" the sessions use - specifically, from the exact turn inside the matching session where that commit happens (`native/build_native_logs.py dates`, `commit_turn_time`) - so the rebuilt history and the sessions that narrate it always agree, however long ago "now" has moved since this scenario was authored. The one prior version of this scenario dated commits from a fixed calendar date while sessions moved with "now"; that gap grew by one day on every later run.
- **Real commit hashes, not placeholders.** The narrative's short hashes (`560c2e8`, `42b6ea6`, ...) are no longer hard-coded: `setup.sh` captures each commit's real SHA with `git rev-parse` right after making it and passes all six to `build_native_logs.py render` as `KEY=<40-hex>` pairs, substituted into both the narrative text and each session's `session_meta.git.commit_hash` (a real 40-character SHA now, not 6 hex characters).
- **Real working directories.** `MAIN_CWD` is the run's own real checkout path (`$(pwd)` from `setup.sh`, i.e. the job's `work` directory), and the three sessions that really get a `git worktree add` (isbn-x, tag-command, sqlite-spike - see `setup.sh`) use their real sibling paths. The two sessions that describe a worktree already removed by the end of that same session (test-helpers, docs-typo) keep the fictional path: that is correct, not a bug - a session's `cwd` pointing at a worktree an agent has since cleaned up is normal.
- **Current on-disk record shape.** Codex sessions carry `event_msg`/`item_completed` items (`UserMessage`, `AgentMessage`, `CommandExecution`) alongside the lower-level `response_item` stream, matching what real Codex (0.117-0.155+, checked against this machine's own `~/.codex/sessions`) actually writes and a reader renders conversation from - not `response_item` alone. `originator` is `codex_exec` and `cli_version` is a current one (`0.155.0`), not `codex-cli`/`0.47.0`. Session/thread ids are UUIDv7 (Codex's real ids are time-ordered; Claude Code's own session ids are UUIDv4, confirmed against a real `~/.claude/projects` file on this machine, so those are unchanged). Directory and file names (`.codex/sessions/YYYY/MM/DD/rollout-...`) use the same fixed local time zone as the git commit dates, not UTC, matching how real Codex names them. Claude's `Bash` tool input is `{"command", "description"}` (checked against a real `~/.claude/projects` file), not a `workdir` key that tool has never had - a command that needs to run in a worktree gets a `cd <dir> && ...` prefix instead, and an error `tool_result`'s content is prefixed `Exit code N`, matching a real one. Each file's mtime is its own last record's timestamp, not "whenever setup.sh happened to run."
- **The checksum ledger.** `native_logs_unchanged` (see `check.py`'s `_native_log_changes`) verifies the seven planted files against a ledger `setup.sh` writes at the same time it plants them. That ledger now lives at `.session-checksums`, one level above `$TRIAL_HARNESS` - outside the directory both executors are given as `--add-dir`, so it is not handed to the agent the same way a file inside the harness directory would be - and is keyed by `sha256(relative path)` -> `sha256(content)` rather than the plaintext relative path, so an incidental `ls`/`find` of the directory the agent is actually told about does not hand every arm, including a no-skill one, the seven exact paths as a ready-made answer key. This cannot make the ledger fully unreachable to a determined agent - the job directory is bound writable into the sandbox regardless (see `references/trials.md`) - but it removes the accidental, no-effort giveaway a plainly-named, path-listing manifest sitting next to `$HOME` inside the granted directory was.

## What this check does and does not cover

`native_logs_unchanged` checks exactly one thing: that the seven planted files are still present with unchanged content ("removed"/"changed" against the checksum ledger). It does **not** flag an unlisted file merely appearing under either log root. That used to seem like an obvious extra safeguard, and an earlier version of this check did exactly that - directory-scoped, so a fresh directory a real executor's own session used was exempt - but it broke on the very fix above that makes `MAIN_CWD` a real path: a real `claude` arm's own Claude Code process writes its own session under `$HOME/.claude/projects/<encoded-cwd>/` just by running, and that `cwd` is the run's own working directory, which three of the seven planted sessions now legitimately share for the same reason (see "Real working directories" above). Once the executor's own file and three planted ones share a directory, there is no reliable way left to tell them apart by timestamp, directory, or session id alone without guessing at fields this scenario cannot verify against a live run (no model credentials - see "Still uncertain" below). The answer key's own words - "changing, deleting, or fabricating one of them is a change to a healthy part" - only ever promised the seven their own integrity, not exclusive ownership of the directories they happen to sit in, so narrowing the check to that literal promise is not a loss of real coverage, just the removal of a check that never had a sound way to do more.

## Codex arms are not currently viable for this scenario

`run_codex` (the split-testing runtime's Codex executor) sets `CODEX_HOME=<job_dir>/home` - a directory distinct from `$HOME/.codex`, which is where both `setup.sh` plants the seven sessions and where a real Codex CLI keeps its own history. A Codex arm run against this scenario therefore cannot see the planted sessions at all (confirmed: pointing `CODEX_HOME` the way the runtime actually does finds none of the seven), which would make every Codex arm - gatherer, "where logs live," and no-skill alike - fail the discovery task for a reason that has nothing to do with what is being compared. This is a defect in the shared trial runtime (`plugins/agentic-design-and-evaluation/skills/split-testing/scripts/trial.py`), not something this scenario's own files can work around, and is out of scope for a change confined to `evals/scenarios/heal-native-mixed/`. **Use `claude` executors only until `run_codex` is changed to use `CODEX_HOME=$HOME/.codex`** (matching real Codex's own default); re-verify this note once that lands.

## How this was qualified

Qualifying instructions (`references/trials.md`) run each reference as a `command` executor with no plan-level judge. This scenario carries a `judge` field, so under the current trial runtime every run comes back `passed=None` / `status: judge-missing` - that is expected, not a bug in the reference or the scenario: the aggregate `passed` field folds in a judge verdict that was deliberately not asked for. What decides qualification is each run's own `checks` dict in `result.json` (`_run_job_once` always computes and stores it before it ever looks at the judge), so every row below was read from there directly, e.g.:

```bash
python3 <split-testing>/scripts/trial.py run qualify.json --out OUT   # plan: command arms, no "judge" key, one scenario
python3 -c "import json; print(json.load(open('OUT/runs/heal-native-mixed__good__r1/result.json'))['checks'])"
```

All seven references below were run this way against this scenario with the current (origin/main) `trial.py`, confined (bubblewrap), one repeat each, into a fresh `--out` directory. `native_logs_unchanged` and `native_log_changes` are the two checks this scenario added over `heal-mixed`; every other row is unchanged from `heal-mixed`'s own qualification.

## References

- **`good.sh`** (adapted from heal-mixed, path-unaffected): repairs `scripts/check_docs.py`, documents `tag`, replaces the commit-msg hook with a validation-only one and corrects the two AGENTS.md lines, drops the leftover changelog entry, gives the worktree instruction an end state, removes the two merged worktrees/branches (local and origin), leaves `spike/sqlite-store` parked, and reports all of it plus the spike as a decision for the developer. Touches only the checkout; never touches `$HOME`.
- **`bad.sh`** (adapted, path-unaffected): silences symptoms instead of causes (adds back a stub `docs/import-goodreads.md`, appends notes to AGENTS.md instead of fixing its lines) and force-removes *every* worktree including the parked spike - the one disposition the answer key says must not happen.
- **`noop`** (`true`): no repository change at all - the baseline every one of these scenarios is qualified against.
- **`near-miss-log-tamper.sh`**: runs `good.sh` in full, then deletes one of the planted native logs under `$HOME`, the way an agent that stopped treating its own past sessions as off-limits evidence might "clean up" a file it now sees sitting in its own home directory. Everything else matches `good.sh`; only `native_logs_unchanged` must fail.
- **`finds-native-logs.sh`** (a discoverability probe, reworded from its first version - see below): makes no repository or `$HOME` change. Using only `glob` and `json.loads` from the standard library, it confirms it can (a) find at least one recent (`mtime` within 7 days) file under each of Codex's and Claude Code's own conventional log roots, and (b) parse every line of every planted file as JSON and recover five common-vocabulary facts (`import-goodreads`, `sqlite`, `commit-msg`, `worktree`, `changelog`) by case-insensitive substring search. Its own exit code is the pass/fail signal, not the scenario's `checks`.
- **`claude-executor-writes-own-log.sh`** (new, added for the finding below): runs `good.sh`, then simulates the one file a real `claude` arm's own Claude Code process writes just by running - its own session, in a fresh project directory under `$HOME/.claude/projects/`. Every required check, including `native_logs_unchanged`, must still pass here exactly as it does for `good.sh`: this is ordinary, healthy executor behavior, not evidence tampering (see "What this check does and does not cover" above).
- **`gather-reads-native-logs.sh`** (new, added for the finding below): runs `good.sh`, then reads the planted logs with the self-healing skill's own current-format reader, `gather.py` (`plugins/agentic-design-and-evaluation/skills/self-healing/scripts/gather.py`, still unmerged work on `feat/self-healing-gather` as of this writing), and asserts it recovers non-zero user/agent/tool entries from all seven sessions. This is the read a "gatherer" arm of the three-arm experiment this scenario serves would actually perform, as opposed to `finds-native-logs.sh`'s fixed phrase list. Because `gather.py` is not yet part of this repository's `main`, the script **soft-skips** (exit 0, with a clear stderr note) unless `TRIAL_GATHER_PY` is set to its path - set it, and add its directory to this arm's own `"readable"` (see `references/trials.md`), to actually exercise it; a maintainer should tighten this to a hard failure once `gather.py` merges.

## Known simplifications

These are deliberate, bounded gaps in on-disk fidelity, not defects this task fixed or is aware fails anything:

- **Codex `FileChange` items.** An `apply_patch` exec turn is still rendered as a `CommandExecution` `item_completed`, not the `FileChange` item type real Codex uses for patches. `gather.py`'s own `CODEX_ITEM_ROLE` maps both to the same `"tool_call"` role, so this affects no check or reader output - purely cosmetic.
- **Claude's Bash `description` field.** Real descriptions are hand-written by the model; this scenario derives one mechanically (the command's first clause, truncated). The field is present with the right shape, but the text itself is not a transcript of a real description.
- **The usage-limit ending.** One session still ends with `"[session ended: usage limit reached; resets at 19:00]"` as plain assistant text, not the API-error record a real hit usage limit would produce. Fabricating that record's exact shape without a real example to check it against risked introducing a new inaccuracy in place of a labeled, narrative one, so it was left as-is.
- **Codex metadata not modeled.** `session_meta`/`turn_context` omit version-specific internals such as `collaboration_mode`/`personality`, and Claude's own hook-bookkeeping `attachment` records are not modeled either. Sufficient for a healing pass that finds and reads the sessions with ordinary tools (see `gather-reads-native-logs.sh`), but if either host's on-disk format changes meaningfully, `native/build_native_logs.py` should be re-verified against a real, current file the way this fix was.

## Still uncertain

- No live model has run against this scenario (no credentials available to this task): whether a no-skill agent actually finds and reads the logs on its own is untested. `finds-native-logs.sh` and `gather-reads-native-logs.sh` are the documented substitutes the split-testing skill prescribes for a scenario that carries a judge, not a replacement for that run.
- `gather.py` is itself uncommitted, in-progress work; `gather-reads-native-logs.sh`'s hard evidence rests on the real host rollout formats checked directly against this machine's own logs, not on that script being final.
- `heal-native-clean` and `heal-native-repeated-procedure` likely share some of the same defects this fix addresses (the timestamp/git-history drift, the manifest exposure, the Codex format and `CODEX_HOME` issues) since they were built the same way; they were not checked as part of this fix, which was scoped to `heal-native-mixed`.

## What to re-run if this scenario changes

`native_logs_unchanged` depends on `native/build_native_logs.py` and `check.py`'s `_native_log_changes` agreeing on the checksum ledger's location and format; if either changes, re-run at least `good`, `log-tamper`, and `claude-executor-writes-own-log.sh` from this README before trusting the scenario again. If the Codex or Claude Code on-disk format is changed further, also re-run `gather-reads-native-logs.sh` (with `TRIAL_GATHER_PY` set) and `finds-native-logs.sh`.
