# Qualification: `revise-fanout-py`

The repository is coldctl, an existing standard-library Python tool for a grocery distribution center's refrigeration (units, temp, and check commands, a gateway client on urllib that takes a timeout, a fake gateway for its tests, four commits of history). Its `check` command already does what the food-safety monitor needs: it reads every unit's temperature, prints one line per unit in ID order as `temp` prints it, `U-0412: no answer` when a controller has not answered within 2 seconds, `U-0412: failed (HTTP 502)` on an error, a summary line, and exits 0, 1, or 2. It reads one unit after another, so at today's 203 units it takes close to a minute. The gateway's documentation (`docs/bms-gateway.md`) allows each client at most 16 requests in progress, answers 429 beyond that, counts a request until the response is sent or the client hangs up, waits up to 60 seconds on a controller that does not answer, and locks out a client that keeps going over. The person reports that the monitor kills the check at 20 seconds and asks to get it back under that, with the output and exit codes unchanged and without a lockout, pointing at the doc. The prompt names neither the cause nor a technique.

The defect is in code that already works: the one-unit-at-a-time loop the earlier change left. Removing it means reading units concurrently within the gateway's limit. Keeping one unit at a time and trimming around it (a shorter wait per unit, a persistent connection) stays over the budget, and so do too few reads at a time (2 or 3, which miss the 20 seconds in an outage if not on an ordinary day); stopping at a deadline and reporting the rest as `no answer` meets the 20 seconds by not doing the work; starting every read at once, or sizing a pool from the CPU count, is refused past 16; moving the 2-second cutoff changes the lines of units that answer just inside or just past it; moving `temp` onto the same new path as well, or giving the shared client a default timeout, changes `temp`'s behavior.

## How the checks decide

The checks are those of `async-fanout-py`, on this fixture's gateway, with the same driver design, except for the time limits and the edge and overdue units described below. Every case runs `python3 -m coldctl check` from a read-only copy of the agent's repository, with `COLDCTL_GATEWAY` set, in its own bubblewrap sandbox: host read-only, home, `/tmp`, and `/run` hidden, its own network and PID namespaces. `hidden/driver.py` serves the gateway on 127.0.0.1 inside that network namespace; the dataset and expected report are made in `check.py` and reach the driver on standard input. After the command exits the driver keeps the gateway listening for 2 seconds, kills everything left in the sandbox, and only then prints its verdict.

The gateway counts a request from the moment its headers arrive until it starts sending the response, or until the client closes the connection; before refusing one it drops counted requests whose client has hung up, for up to 50 ms. A refused request still counts as asked for. Requests in progress longer than 8 seconds while the command ran count as held.

The cases:

- Main: 203 units. 187 answer in 60 to 260 ms; 2 slow ones in 1.0 to 1.2 s and 3 edge ones in 1.55 to 1.65 s (all within the 2 seconds, so read); 2 overdue ones in 2.4 to 2.8 s and 1 late one only after 3.2 to 5.5 s (so `no answer`); 4 offline ones the gateway holds for 60 s, then 504; 4 get 500 or 502. About one unit in twelve is mid defrost cycle, which changes its line. The list comes in no particular order. Offline units are drawn from the first quarter of both the ID order and the list's order, the others from the first 60%. The edge and overdue units pin the cutoff: a client that moves it by more than about 0.4 s either way (below 1.61 s or past 2.43 s on these datasets) reports one of them wrongly, and a correct client keeps at least 0.35 s on either side for the host's delays (the correct arms' longest request in every run on this host was 2.15 s, once, in a load spike).
- All answering: 40 units.
- Outage: 203 units, 20 offline, 27 slow, 3 edge, and 2 overdue, all in the first third of both orders.
- No gateway: exit 2 within 10 s.
- Existing commands: `units` and `temp` run one after another against a small gateway, with the arguments, environment, and expected output the fixture's tests use and the exact output the fixture prints: `units` with each unit's zone, `temp` keeping the order given, `, defrosting` included, stopping at the first failing unit with the error on standard error (alone and in the middle of a list), and waiting for the gateway's own answer on a unit that takes 3 seconds.

Every command gets `PYTHON_CPU_COUNT=32`, and the run is invalid (not failed) when the CPUs the check may run on are 16 or fewer, so a pool sized from the CPU count is judged alike on every host that decides.

The time limit is the ticket's 20 seconds, for the main case and the outage alike (the monitor kills the check at 20 seconds whatever state the plant is in), plus only what the host adds to a correct client's time. `hidden/reference_client.py`, a correct client at the documented limit, runs first against the main dataset, up to three times, stopping once its best time is within 1.25 times the 3.29 s it spends waiting on the gateway (16 slots taking units in ID order, each answering unit's latency or 2 s for each silent one); whatever its best time takes beyond those 3.29 s is the host's slack, added to the 20 seconds for both cases. The run is invalid (not failed) when even that best time is more than 1.5 times the 3.29 s, so the slack never exceeds 1.65 s. The slack is added rather than multiplied in: a client whose own waits add up to more than 20 seconds cannot pass on a loaded host, and a client within a second or two of the budget is the only one whose verdict the host's load can decide. The seconds each kind of client spends waiting on the gateway alone on these datasets (main / outage) keep every arm below clear of that band in at least the case that decides it: a pool of 16 3.3 / 6.5 s, 12 workers 4.3 / 8.7 s, 8 workers 6.4 / 13.0 s, batches of 16 14.1 / 11.9 s, 4 workers 12.7 / 25.8 s, 3 workers 16.9 / 34.3 s (within the budget on an ordinary day, far past it in the outage), 2 workers 25.3 / 51.4 s; a pool of 5 (10.2 / 20.6 s) is the natural size nearest the boundary, and its verdict can depend on load. Batches of 16 lose more time to load than a pool does (each batch starts 16 reads at once and waits for the slowest): on the first version of these datasets, where they waited 16.6 s, they took 16.8 to 17.0 s on a moderately loaded host and 19.2 to 19.4 s during load spikes of 63 to 76 (`~/.cache/agent-trials/light-revise-fanout-py-20261002`), within a second of the limit, so the main case now has fewer slow and late units to keep them clear of it. The reference also runs once against the outage, as a self-check and a measure. A sequential client cannot beat the floor (47.6 s here), however idle the host, and no limit reaches it. The main and all-answering cases are killed only at twice the floor (95.3 s), so the fixture's own check, which is correct, finishes and fails `within_budget` alone; the outage is killed 10 s past its time limit, and its report is judged only when it finished within that limit.

Required:

- `answered_units_correct`: one line per unit in ID order, each answering unit's line exactly as `temp` prints it, in the main, all-answering, and outage cases.
- `failures_handled`: `no answer` and `failed (HTTP n)` lines as before, the summary line, exit 1 (main, outage) and 0 (all answering), and exit 2 within 10 s with no gateway.
- `within_budget`: the main case exits by itself within its time limit, having asked for every unit, and the outage within its own.
- `within_limit`: the gateway refused nothing in the main, all-answering, and outage cases, and the main case asked for at least one unit.
- `no_held_requests`: no request held in progress longer than 8 s in those cases, and the main case asked for at least one unit.
- `no_work_after_exit`: no request or connection reached the gateway after the command exited by itself, and no process was left, in every case; the main case asked for at least one unit. A case the check killed is judged on processes left alone, since a request in flight at the kill can reach the gateway just after it.
- `existing_commands_unchanged`: `units` and `temp` behave as the fixture's tests expect and print what the fixture prints, run as commands.

Measures, deciding nothing: the seconds and limits of each case and of the reference (`reference_ideal_seconds` is its waiting alone, `host_slack_seconds` what the host added), peak and attempted requests in progress, refusals, abandoned and held requests, the longest request (the reference's too), requests and connections, requests per unit, the CPUs and CPU count the command saw, `source_lines_changed` and `source_files_changed` (lines added plus removed, and files touched, in `coldctl/` against the fixture), `test_lines_changed` and `test_files_changed` (the same for `tests/`), `fixture_tests` (the fixture's own 19 tests from the check's copies against the agent's package), `own_suite`, `commits_added`, `final_words`.

## Running it

```bash
python3 plugins/agentic-design-and-evaluation/skills/split-testing/scripts/trial.py run evals/scenarios/revise-fanout-py/qualify/plan.json --jobs 3
```

The check needs bubblewrap, `/usr/bin/python3` (3.10 or later), and more than 16 CPUs whatever the plan's `sandbox` setting. Agent arms need nothing readable beyond the default confinement. A check takes about 45 to 60 s for a good solution and about 125 to 145 s for one that stays sequential.
