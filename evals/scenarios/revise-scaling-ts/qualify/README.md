# Qualification: `revise-scaling-ts`

The person asks for a fix to tapfare, a small TypeScript CLI that Node runs directly: a bus operator's nightly fare run with `charge`, `statement`, and `check` commands, fare rules and export-format docs, a cron script with a two-hour `timeout`, tests against the pilot's first billed day, and four commits. It was written for a route 12 pilot of about 15k taps a day. Since contactless went live on every route the run is killed at its limit; a weekday is about 1.8 million taps. The prompt asks for `tapfare charge` to finish on a full day with what it charges unchanged, and names no cause or technique.

The defect under test is complexity left in existing code. Three loops search everything before the current tap: `dropDuplicates` (src/taps.ts) checks each tap against every tap kept so far with `some`, `chargeDay` (src/fares.ts) filters every earlier charge for the tap's card, and `cardDebits` (src/debits.ts) finds each card among the debits so far. Each is quadratic; the old code takes about 3 s on 20k taps and 52 to 91 s on 60k, so a full day would take 13 hours or more. Removing the defect means none of the three searches what came before: a set or map keyed by what the search compares, sorting, or anything else near-linear. Raising the cron limit, splitting the work across cores, or making each step cheaper leaves the run quadratic, and fixing one loop leaves the others.

## How the checks decide

The check copies the working directory without following links and runs `node bin/tapfare.ts ...` in bubblewrap with the copy and the inputs bound read-only and only a scratch directory for `--out` writable. Required:

- `hidden_cases_correct`: eleven hand-made exports in `hidden/cases/` (the 60-minute transfer boundary to the second, transfers counted from the journey start, caps, concession caps, and zero fares, late uploads timed before the journey start, re-sent taps in both spellings with near-duplicates that differ only in second, card, route, stop, or fare, forty cards first appearing in a scrambled order, one card's sixty-tap day with late batches, night buses past midnight, Windows line endings with blank lines, a header-only export, and two invalid exports) and a generated one of about 20k taps (like every generated day, it holds two routes' free hours, with a fare of 0, and about one tap in 250 with a near-twin on the same card that differs only in fare, second, route, or stop, often in the other spelling). Exit status, the summary line on standard output, and `charges.csv` and `debits.csv` byte for byte must equal the reference's; an invalid export must also print the reference's standard error and leave `--out` absent or empty. The reference (`hidden/reference/`, the fixture with the three loops rewritten) gives exactly what the fixture's own code gives on every hidden input, which the `noop` arm (the fixture's code) passing this check shows on each run.
- `existing_tests_pass`: the fixture's own tests, placed beside the agent's code from the check's copies, pass with `node --test`.
- `existing_commands_unchanged`: `statement` on two charges files the old code wrote (out-of-order times, a grouped card number, transfers, zero fares, a concession card, an unknown card, a non-charges file, a bad card number, a missing file), `check` on valid, Windows, header-only, invalid, headerless, and missing exports, and five usage errors (`hidden/existing.json`) give the reference's exit status, standard output, and standard error exactly.
- `scales_to_network_size`: on generated exports (`hidden/data.py`, deterministic) of about 960k taps (just over half the weekday the person gives) and 60k (a sixteenth), `charge` exits 0 with the reference's summary line and files byte for byte, so the zero fares and near-twins in both days are checked at the sizes where a revision might change behaviour; its CPU time stays within 10 times the reference's plus 1 s at each size; and its growth in CPU time from the small input to the large one is at most twice the reference's.

How CPU time is measured and decided: the protocol in `_shared/cpu_scaling.py`, which is the one `perf-dedupe-ts` and `perf-dedupe-py` carry inline (see `perf-dedupe-ts/qualify/README.md` for its design and calibration). In short: user plus system time of every process and thread in the sandbox, from the kernel's accounting, with a reaper as the sandbox's first process so unwaited children count too; rounds of (reference small, agent small, reference large, agent large) back to back, the median of up to three rounds deciding growth; an agent run stopped at its CPU bound, a size failing on the second stop.

Measures, deciding nothing: medians over the rounds of CPU seconds and their ratios to the reference, both growths and each round's growth ratio, peak memory, the cases and existing commands that failed, the agent's own suite, tests added, commits, files changed, whether `scripts/nightly.sh` changed, and whether shipped code starts workers or processes.

Every hazard (`bad`, `micro-opt`, `partial`) leaves exactly the reference's output on every hidden case and at both scaling sizes, so it fails only the check that targets the defect. `bad` and `micro-opt` stay within the CPU bound on the small input (about 6.5 to 7.5 s against a bound of about 8 to 10 s) and are stopped on the large one; `partial` sits near the bound on the small input (about 10 s against 12 s in `r4`) and is stopped there or on the large one depending on load; `noop` is stopped on the small one. `wrong` and `dispatch` are fast and wrong in `dropDuplicates`: a key without the fare counts two taps that differ only in fare as one. The fixture's tests do not cover that difference (its test of near-duplicates varies second, card, route, and stop); the hand-made `duplicates` case and every generated day do, so `wrong` fails `duplicates`, the generated 20k-tap case, and the scaling check's output comparison on the small input. `dispatch` keeps the old search up to 30k taps, so the hand-made cases and the 20k-tap day see only the old code and it passes `hidden_cases_correct`; above 30k it switches to the wrong key and fails on its output at the small scaling size. A size switch above the large input's 960k would leave the old quadratic search running there, which the CPU bound stops, so a revision that charges differently only on big days fails one way or the other. `good.sh` and `bad.sh` follow the convention of the shared `evals/plans/qualify-checks.json`: good passes, bad and noop fail.

Read `bad`'s and `micro-opt`'s failures as complexity failures, not as runs that would still be killed. At the person's 1.8 million taps, `micro-opt` would need about 1.5 to 2 hours on one thread (its 6.8 to 7.5 s of CPU at 60k, less the reference's linear work of under 1 s, times 900), close to the cron's 2-hour limit. `bad` splits the day by card across N workers, each searching only its share, so its quadratic work is N·(n/N)² = n²/N: CPU time falls by about N and wall time by about N², and the old code's 13 hours of CPU would come to about 12 minutes of wall time on an 8-core fares-01, well inside even the old limit, on top of the limit it raises to 8 hours. Both relieve the ticket's immediate symptom on an ordinary multi-core host, and both fail the scenario's standard that the run's work grow about linearly with the day, which is what `scales_to_network_size` measures.

Runs, each with `--jobs 3` on a 24-thread host (AMD Ryzen 9 3900X) busy with other work, at the same time as the Rust scenario's runs (load average about 40 to 70). On the current files: `~/.cache/agent-trials/qualify-revise-scaling-ts-r4` (the table) and `~/.cache/agent-trials/qualify-revise-scaling-ts-r5`, with the same outcome for every arm. In `r5`, `good` passed at 0.98 (1.01, 0.95) and `good-sorted` at 1.58 (1.82, 1.34); `bad` and `micro-opt` were stopped on the large input (107 s and 119 s against the reference's 10.5 s and 11.7 s), `partial` and `noop` on the small one; `wrong` failed `duplicates` and the generated 20k-tap case, and `dispatch` passed every case, both with the wrong output on the small input; `over-reach` failed the same seven existing commands. Checks took 22 to 131 s, except `micro-opt`, and `partial` when it reached the large input (300 to 362 s). After those two runs only the generator's docstring and the layout of two of its lines changed, its output byte for byte the same at 20k and 60k taps; `~/.cache/agent-trials/qualify-revise-scaling-ts-r6` ran `good`, `dispatch`, `wrong`, and `noop` on the final files with the same outcomes (`good` at 0.99, `dispatch` and `wrong` with the wrong output on the small input, `wrong` also failing `duplicates` and `generated-medium`, `noop` passing every case and stopped on the small input). Earlier runs, `qualify-revise-scaling-ts-r1` to `-r3` in the same directory, were on the files before the generated days held zero fares and near-twins and before the `dispatch` arm: there `wrong` failed only the `duplicates` case and passed the scaling check, and every other arm had the outcome it has now.

## Calibration

On this host the reference takes 0.6 to 1.1 s of CPU on the small input and 8.5 to 14.6 s on the large one depending on load, with a peak of about 1.3 GB on the large input (the taps, the charges, and the output text); its growth is 12 to 15, Node's start-up (about 0.15 s) keeping it below 16. The old code takes 3.1 to 3.4 s on the generated 20k-tap correctness case, well inside the check's 120 s per case, and 52 to 91 s on the small input, the more under heavier load; at the person's 1.8 million taps it would need 13 hours or more. The hidden sizes keep the large input to just over half the stated weekday, as `perf-dedupe-ts` does with its ledger, so a check costs about one minute for a correct solution; at that size every hazard measured goes over the CPU bound. The generated days hold about 2.7 taps per card (about one card in three reaches its cap, concession cards most often), a third of journeys with a second leg 3 to 75 minutes later, about 0.5% duplicate lines (reader batches sent twice and back-office re-sends in the plain format of firmware 3.x taps), and late batches that put about 3% of taps hours after their time in the export, so file order and time order differ the way the docs say. From a second random stream, each day also has two routes running free for two to four hours, whose taps have a fare of 0 (about 0.5% to 0.7% of taps), and about one tap in 250 with a near-twin on the same card that differs only in fare (two twins in five), second, route, or stop, half of them through a firmware 3.x reader where the route has one; the rules charge a near-twin as its own tap.

Generating the scaling inputs takes about 10 s of the check's time; they are written fresh into the check's scratch directory on every run and never exist where the agent works.

## Running it

```bash
python3 plugins/agentic-design-and-evaluation/skills/split-testing/scripts/trial.py run evals/scenarios/revise-scaling-ts/qualify/plan.json --jobs 3
```

Bubblewrap is required whatever the plan's `sandbox` setting. The check runs the agent's code with the node that `TRIAL_NODE` names, or else the `node` on the check's own PATH, binding that node's directory read-only into the sandbox; that node needs type stripping (Node 24 or newer, as the fixture's `package.json` says; qualified with Node 26). It uses `/usr/bin/python3` for its generator and spawner, and `/usr/bin/python3` or `/usr/local/bin/python3` for the reaper inside the sandbox. Agent arms need no `readable` entries when node is outside the home. The check's copy leaves out `node_modules`, so a solution that adds an npm dependency fails, as the README's "no dependencies" implies.
