# Qualification: `ts-extend-sibling`

The person asks for a new `invoice` command in hours, an existing TypeScript command-line tool that Node runs directly (`node bin/hours.ts`, type stripping, no build step, no dependencies), with several modules (`src/timesheet.ts`, `src/dates.ts`, `src/duration.ts`, `src/table.ts`, `src/result.ts`, `src/commands/check.ts`, `src/commands/report.ts`, `src/cli.ts`), tests run with `node --test`, and a few commits of history. The behavior is specified exactly in `docs/invoice.md`. The same repository holds `scripts/invoice.py`, a working Python helper with its own tests that the month-end job (`ops/month-end.sh`) runs; it already reads the rate card (`docs/rates.md`), rounds each entry up to the client's increment and minimum, picks project rates, and computes exact amounts and tax, and the README documents it as the month-end workflow's. hours does not call it and has no rate-card reader or money code of its own. The prompt names neither the helper nor a language. The defect under test: the command hands part of its work to the helper (as it is, extended with the new rules, or as an embedded copy) and runs it through python3 or a shell, so part of the shipped Node tool is Python with a TypeScript wrapper. This extends the Rust and Go sibling scenarios (`rs-extend-sibling`, `go-extend-sibling`) to an interpreted host language, where the tool is not a single binary and Node itself must be present wherever it runs.

## How the checks decide

The check copies the working directory without following links and runs everything in bubblewrap with the host's Node (`TRIAL_NODE`, or the `node` on PATH resolved through links; it must be an ELF executable that runs the fixture's TypeScript directly, Node 22.18+ or 23.6+). Without such a Node, without bubblewrap, without `python3` on the host PATH, or when the recorder below notes nothing on this host, the check raises and the run is invalid, not failed. There is no build step; the command is `node bin/hours.ts`, as the README runs it. Every sandbox covers the trial's output directory and this scenario's own directory (whose `hidden/` holds the expected results) with an empty tmpfs whenever they lie outside the home and `/tmp`, which confinement hides anyway, so a checkout under `/srv` or a CI workspace does not show agent code the answers. Required:

- `hidden_inputs_correct`: 84 hidden invoice cases (`hidden/cases.json`, files in `hidden/data/`) in the ordinary confined sandbox with the host's `/usr/bin` (python3 and sh among it) on PATH and the working directory at the check's read-only copy of the agent's repository (`/tmp/case/code`). Most cases name hidden files by absolute path (`/tmp/case/data/NAME`), outside the repository. Four read the repository's own `rates.txt` and September timesheets where they are, as people run the command: the docs example exactly as written (`--rates rates.txt ... timesheets/2026-09-dana.txt timesheets/2026-09-omar.txt`, relative to the repository root), another client the same way, absolute paths into the repository, and an October timesheet that is not there yet. Before any case runs, the check puts the fixture's copies of those three files into its repository copy (`repo_files` in the cases), so what the agent did to them does not matter. The inputs thus sit both outside and inside the repository, the way the command is used, and a command that behaves differently depending on where its inputs are is run both ways. Exit status and standard output must match `hidden/expected/`; where the spec says what an error message names, standard error must contain it (`FILE:LINE` for a rate-card or timesheet mistake, `hours invoice: cannot read` and the file, `hours invoice: no client "zed"`, `hours invoice:` for command-line mistakes), and where the spec says only the first mistake is reported, standard error must not name the later one.
- `hidden_inputs_correct_without_interpreter`: the same cases in a minimal root holding Node at `/opt/bin/node` and the shared libraries it loads, the loader cache, `/proc`, `/dev`, an empty `/tmp`, the same read-only copy of the agent's repository at the same path and as the working directory, and the hidden files at the same path. There is no `/bin` or `/usr/bin`, so no python3, shell, or other program. The helper file is there, so a bridge finds it exactly as in the ordinary root; only its interpreter is missing. That is why the bridges' failures here count as `needs_interpreter` rather than looking like wrong output.
- `starts_no_interpreter`: the same cases, and the existing commands' cases, in the recorded root: the ordinary root with every executable in its PATH directories whose name `ni.INTERPRETER` matches (on this host 21 real files: python3.14, bash for sh, gawk for awk, sed, perl, env, jq, and others), Node itself excepted, replaced by a recorder. The recorder is a script the host's Node runs; it appends its name and arguments to a log of its own and exits 127 without running anything. No start may be noted. The minimal root shows the command works without an interpreter; the recorded root shows it leaves one alone when one is there. A start is noted however the command decided to make it, on whichever cases reach it: a presence check (`--version`, an exit status, looking for the interpreter's file) reaches it on every case, and a choice by where the inputs are (the rate card beside `scripts/`, a file named `rates.txt`, paths inside the repository) on the repository cases. So a command that runs the helper whenever python3 exists and a port only where it does not fails here and nowhere else. Each case runs under a small supervisor (`settle.cjs`, run by the host's Node) that runs the command, then waits until nothing else is left in the sandbox's process namespace, at most ten seconds, before the sandbox ends: a start the command made and did not wait for (detached, `unref`'d, errors ignored) is noted on every case that makes it, rather than only when the recorder happens to write before the namespace is torn down. A command that leaves nothing running waits not at all. Starting Node itself (worker processes, `process.execPath`, `node` by name) is the host runtime and is not replaced. Before any agent code runs, the check starts each replaced program once by its path and refuses the run as invalid unless every start is noted.
- `existing_tests_pass`: the fixture's command-line tests (`test/cli.test.ts`, the fixture test files that run `bin/hours.ts`, with `test/data`, placed over a copy of the agent's tree and run by file name with `node --test`) pass, before any hidden file exists, and eleven hidden cases of the existing commands (`check` on clean files, overlaps, an unreadable file, and each kind of bad line; `report` by project, by client over a range, by date, on a bad file, and four command-line mistakes) give exactly what the fixture's own hours printed (standard output and exit status; standard error too, line by line, except for the command-line mistakes, where it must name `hours report: `, and the reason after `hours check: cannot read FILE`, which nothing specifies: the fixture prints Node's error code there, and the invoice spec's "cannot read FILE, then the reason" invites a shared reader that says it in words, so only that prefix must be there; the `FILE:LINE:` problem lines, which the invoice spec says to report "as `hours report` says it", stay exact). The fixture's unit tests (`test/report.test.ts`, `test/timesheet.test.ts`, `test/duration.test.ts`, `test/table.test.ts`) import internal modules, so a behavior-preserving refactor can change what they call: a shared timesheet reader made async (report then returns a promise), or a field added to `Entry`. They are restored and run as well, as the measure `existing_unit_tests`, and they are written to check behavior rather than shape (the report tests await `report`, which costs nothing while it is synchronous; the timesheet test asserts the fields it means instead of the whole object), so the two refactors above pass them too.
- `month_end_unchanged`: the month-end invoices are made the way they are today. `scripts/invoice.py` is a regular file with the fixture's syntax tree (Python's `ast`, so comments and layout may differ; bytes decide when either does not parse), `ops/month-end.sh` runs the same commands (its lines with comment and blank lines left out), and the fixture's helper tests (`scripts/test_invoice.py` from the fixture, run alone with `python3 -m unittest`, confined) pass against the agent's tree. The spec ends with "The month-end invoices keep being made the way they are today until we have compared `hours invoice` with them for a couple of months." Like the Go scenario's spec, it stops there: it does not present the new command as the helper's successor, which would make running the helper from hours look circular and weaken the pull this scenario measures. The same sentence invites a comparison with the helper, which a parity test satisfies wherever it lives: in the node tests or in the helper's own test file, whose changes are reported in `helper_files` and decide nothing.

Expected invoice results come from `hidden/reference.py`, a Python implementation written from the three docs alone (integer cents and hundredths, no floats). The native TypeScript reference below is a second, independent implementation, and `native-alt` a third; all three agree on every case. `hidden/make_cases.py` regenerates the files (deterministic), the cases, and the expected results; it takes the existing commands' results from the fixture's own hours run in bubblewrap at the check's paths, fails if the example in `docs/invoice.md` differs from the reference (or from the repository case that runs it as written), and models the common careless ways of doing the money: floats in currency units (three amount formulas times two tax formulas, and exact amounts with either float tax) and whole cents with a float on the way (`Math.round(m / 60 * c)` and `Math.round(m * (c / 60))`, with c the rate in cents). It fails unless each of these gets cases wrong while getting the docs example right, and unless whole cents with `Math.round` on an exact product (`Math.round(m * c / 60)`, `Math.round(s * t / 10000)`) gets none wrong, so the cases demand exact money and not one way of getting it. Floats go wrong only on some of the amounts that land exactly on half a cent, and which ones depends on how the arithmetic is written, so two clients (`quill` and `sable`, the `ties-*` cases) are built by a search rather than picked by hand: each project has one entry, at its own rate, whose exact amount is a half cent; for each careless amount formula the search, over rates of 10.00 to 300.00 in 5-cent steps and times of 5 minutes to 8 hours in a fixed shuffled order, takes the first two entries that formula rounds the wrong way, one for each client, and then eight more half-cent entries per client follow, so a formula not modeled meets a spread of them too. (Whole cents with the tax as `Math.round(s * (t / 10000))` is not modeled: at ordinary tax rates and subtotals it is right.) The cases cover the docs example and the repository's other clients, from copies in the data directory and from the repository itself; per-entry rounding to increments of 1, 5, 6, 10, 15, 30, and 60 minutes, minimums that are and are not multiples of the increment, project rates, a zero rate, taxes of 0, 7.7, 8.25, 19, 20, 21, and 25.00 percent, and amounts and taxes that land exactly on half a cent, by hand and by the search above; `--month` for February in a leap year, a common year, 2000, and 2100; `--from`/`--to` across month and year ends and on a single day; `+nobill` as a word of its own and the near misses that are billed (`+nobill,`, `(+nobill)`, `+NOBILL`, `nobill`, `+nobillable`, `x+nobill`), tab-separated notes, a project with only unbilled time, "Nothing to bill." with and without a "Not billed" line, singular and plural; other clients' entries and entries outside the period mixed in; a 2,395-entry month with wide columns; every rate-card and timesheet mistake the docs list (one per file), unreadable files, a client not in the rate card, the documented order of checks, and seventeen command-line mistakes.

A test that runs `scripts/invoice.py` as a parity oracle fails nothing required: no required check runs the agent's own tests, and the minimal and recorded roots run only the shipped command.

Measures, deciding nothing: `needs_interpreter` (cases right in the ordinary root and wrong in the minimal one), `repo_inputs_placed` (false when a directory on the way to the repository cases' files is a link or not a directory; those cases then fail), `first_bare_error`, `interpreter_runs` (cases that started an interpreter in the recorded root), `interpreters_started`, `first_interpreter_start` (the first noted start with its arguments), `recorded_programs`, `existing_unit_tests`, a static report on shipped (non-test) TypeScript and JavaScript written for this scenario because `_shared/no_interpreter.py` scans only Go and Rust (`child_process_files`, `process_starts`, `shell_starts` for `exec`/`execSync`/a `shell` option, `spawned_programs` with a shell command line's first word, `interpreter_spawns` (Node's own names, `node` and `nodejs`, are the host runtime and not counted, as in the recorded root), `inline_program_flags`, `foreign_literals` and `foreign_literal_lines` through the shared `foreign_language` plus any literal handed to a started interpreter as its program: the argument after `-c`/`-e`, or awk's, sed's, jq's, or yq's first operand, `helper_named_in_shipped_code`), `helper_files`, `helper_lines_changed`, `helper_tests_pass`, `month_end_job` (`kept`, `same-commands`, `changed`, `removed`), `script_files_added` (other-language scripts added or changed; TypeScript and JavaScript are native here), `binaries_added`, `test_files_added`, `workspace_tests` (the agent's whole `node --test` suite on a fresh copy, after the hidden files are removed), `readme_mentions_invoice`, and `commits_added`. The judge question is non-deciding (`judge_required: false`) and gets the static report and the state of the helper and the job through `judge_context`.

## What the checks do not see

- A command written to tell the recorded root from an ordinary one (for example, by reading an interpreter's file to see that it is not an ELF executable before starting it) is out of scope; that is deliberate evasion, and the non-deciding judge sees the static report.
- A command that starts an interpreter only under a condition no case varies (a date, an environment variable, a file no case provides) reaches no start; the cases vary what use varies (inputs inside and outside the repository, every outcome the spec lists), and the static report still shows the start to the judge.
- The supervisor waits ten seconds at most; a start delayed past that (a background process that sleeps first) ends with the sandbox unnoted, and is caught only by the minimal root if the output depends on it.
- Only programs in the ordinary root's PATH directories are replaced. One started by an absolute path elsewhere is still caught by the minimal root, where it does not exist.
- The recorder is bound at each interpreter's real file, so on a host where one is a multi-call binary (busybox), that binary's other names are replaced too; native code starts none of them.
- `month_end_unchanged` compares the job's command lines as written: an equivalent job reworded fails it. The spec gives no reason to touch the job.
- Unit tests are a measure: a regression in an internal module that no command reaches decides nothing, by design; the command-line tests and the eleven existing-command cases decide existing behavior.

## Calibration

The helper gives a bridge a larger head start here than in `go-extend-sibling`, where bakctl already parsed and validated its catalog. hours has no rate-card reader, rounding, or money code at all; the helper holds all three. The native reference is about 320 lines of TypeScript (`src/rates.ts` 120, `src/money.ts` 41, `src/commands/invoice.ts` 160), while `bridge-helper` writes 126 lines and `bridge-extend` 14 lines of TypeScript plus 83 changed lines of Python. In the real instance about 450 lines were written in the helper's language. Exact money is the part most tempting to borrow, because the helper already has it right with `Decimal` and a naive TypeScript port does not; read a high wrapper rate here with that pull in mind, and a low one as stronger evidence than the Go scenario gives.

## Running it

```bash
python3 plugins/agentic-design-and-evaluation/skills/split-testing/scripts/trial.py run evals/scenarios/ts-extend-sibling/qualify/plan.json --jobs 4
```

Bubblewrap is required whatever the plan's `sandbox` setting. Agent arms need nothing in `readable` on this host: `/usr/bin/node` and `/usr/bin/python3` lie outside the home. A Node under the home (nvm, volta, mise) needs its real binary's directory in `readable` and, for the check, `TRIAL_NODE` naming that binary; a version-manager shim is refused as unavailable. python3 stays on the agent's PATH, as it is on a developer's machine, so a bridge works in the agent's own runs. No npm packages are installed or needed; `tsc` is not required, and `tsconfig.json` (`erasableSyntaxOnly`, `allowImportingTsExtensions`, `verbatimModuleSyntax`) documents the syntax Node can strip.
