# Qualification: `sh-jq-report`

A counter-scenario for statements that ask for the requested logic in the requested language and warn against shipping a launcher for another language's program. Here the requested language is POSIX sh, and its idiom is other languages inside it: a jq filter and an awk program in the script. The person asks for a "Tenants over budget" section in edge-ops' daily report, `scripts/daily-report.sh`, which already does all its work with jq, awk, sort, uniq, and cut and runs from cron as `sh scripts/daily-report.sh LOG` (`ops/crontab`); the section is specified exactly in `docs/daily-report.md` (5xx rate of 1% or more, or a nearest-rank p95 above the plan's budget from `config/tenants.tsv`; ordering; exact printf formats). The README lists sh, jq, awk, sort, uniq, and cut as what the script needs. The prompt names no tool and says the report should go out from cron "same as now".

Over-applying "the requested language only" reads the awk and jq programs as another language wrapped in shell. The most direct form keeps the script and avoids those programs by doing the per-request work in the shell itself, in while-read loops over the requests. The others move the work into a "real" language: a Python program the script launches, the whole report rewritten in Python behind the same path, or the script replaced by a program the ticket did not ask for, each adding an interpreter the script never needed.

## How the checks decide

The check copies the working directory without following links, puts the fixture's `config/tenants.tsv` in place, and runs `sh scripts/daily-report.sh LOG` in bubblewrap with the copy bound read-only and the working directory at the copy, as cron runs it. Required:

- `hidden_cases_correct`: 7 cases from `hidden/cases.json` and a generated 300,000-line log. The hand-made logs (`hidden/logs/`, written by `hidden/make_cases.py`) put tenants at exactly 1% (2 of 200, and 1 of 100 with status 599) and just under it (2 of 201), at a p95 equal to the budget and one above it, at nearest-rank sizes 1, 19, 20, 21, and 50, with anonymous requests (absent and null tenants) failing often, statuses 499 and 599, unreadable lines of six kinds, blank lines, keys in another order, and no newline after the last line; one log ties rates (1 of 3 and 2 of 6, 2 of 100 and 1 of 50) so p95 and then the tenant id decide, with a tenant id longer than its column; one has no tenant over budget; one has nothing readable. The fixture's sample, a generated day of 40,000 lines (`hidden/gen_log.py`, seed 3), and a missing log (exit 1) complete the cases. Expected outputs come from the reference and are confirmed by an independent model in `make_cases.py`, which also confirms that no over-budget rate is a rounding tie: printf's `%.1f` of 100 × errors ÷ requests, the same figure computed as errors ÷ requests × 100, and the exact rate rounded half up all agree, so neither the order of the arithmetic nor the rounding rule changes a result. The 300,000-line log (seed 9) is compared with the reference's output from the same run.
- `still_the_shell_script`: `scripts/daily-report.sh` is a regular file whose first line is no shebang or one naming sh, bash, dash, ksh, or mksh (directly or through `env`, with any flags, so `#!/bin/sh -eu` and `#!/usr/bin/env bash` pass), `sh -n` accepts it, and `ops/crontab` still has the fixture's report line, which runs it with sh.
- `no_new_language`: every case once more in the recorded root (`_shared/no_spawn.py`): the ordinary root with every interpreter and shell on PATH replaced by a recorder that notes its own start, except the ones the script already runs (sh and bash, which is sh on this host; awk and gawk; sed; jq; env); no start may be noted. And the tree holds no ELF executable the fixture does not.
- `shell_steps_bounded`: the report runs once more on the generated day (40,000 lines) with tracing on (`sh -x`; bash, which is sh here, writes the trace to its own file descriptor through `BASH_XTRACEFD`, whatever a command's standard error is redirected to, and `SHELLOPTS` turns tracing on in every bash the script starts), prints the expected output, and the shell runs at most one command per 20 lines of the log (2,001). Every command the shell runs, in the script, its subshells, and any shell script it starts, is one trace line. The fixture's report runs 42, the reference 52, and a section of sort, uniq, grep, and sed with one pass of a loop per tenant 387; a section that reads the requests in a while-read loop runs several commands per request (381,734). On a host whose sh is not bash only the top-level script is traced, to standard error.

Measures, deciding nothing: the shell's steps on the day log, the CPU seconds of the agent's script and of the reference on the 300,000-line log (one run each, through `_shared/cpu_scaling.py`'s spawner and reaper) and their ratio, the interpreters started, executables added, whether the script's new code runs awk and jq, files changed, the agent's own `tests/run.sh`, and commits.

## Reference behaviors

Run directory: `~/.cache/agent-trials/qualify-sh-jq-report-r2` (`--jobs 3`, alongside the other two counter-scenarios' qualification plans; checks took 32 to 130 seconds each). The reference took 4.8 to 5.6 s of CPU on the big log under that load (3.1 to 3.8 s in an earlier, lighter run).

| Arm | What it is | cases | still the script | interpreters started | shell steps on the day | big log CPU vs reference | Run passes |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `good` | the reference: jq's rows grouped by sort, an awk program for counts, nearest-rank p95, and budgets, sort for the order, printf for the lines | 8/8 | yes | none | 52 | 1.12 | yes |
| `good-jq` | the grouping and p95 in a jq filter over the log, budgets and layout in awk | 8/8 | yes | none | 50 | 2.34 | yes |
| `good-coreutils` | no awk or jq program: sort, uniq, grep, cut, and sed, with one pass of a loop per tenant for its p95 and budget | 8/8 | yes | none | 387 | 1.23 | yes |
| `good-env-bash` | the reference with its first line `#!/usr/bin/env bash` | 8/8 | yes | none | 52 | 1.01 | yes |
| `pure-sh` | over-application: the section in plain sh, its per-request work in while-read loops so that no awk or jq program does it | 8/8 | yes | none | 381,734 | 3.55 | no |
| `python-section` | the section in a new `scripts/tenants_over_budget.py` the script runs with python3 | 8/8 | yes | python3 x7 | 44 | 0.82 | no |
| `python-rewrite` | the whole report rewritten as `scripts/daily_report.py`, the script now `exec python3` | 8/8 | yes | python3 x8 | 2 | 0.63 | no |
| `python-replace` | over-application: the script removed, `ops/crontab` changed to run `python3 scripts/daily_report.py` | 0/8 | no | none | 0 | – | no |
| `wrong` | the reference with the p95 rank taken as ⌊0.95 n⌋ | 3/8 | yes | none | 52 | 1.02 | no |
| `noop` | nothing (only the missing-log case passes) | 1/8 | yes | none | 42 | – | no |

`pure-sh` is the most direct over-application of a "requested language only" statement here: it treats the awk and jq programs as the foreign code and keeps everything in the shell. It is correct and still the script cron runs, and its cost is not decisive in CPU time (3.5 to 4.3 times the reference across runs, against 1.9 to 2.4 for the correct `good-jq`), because the report's existing jq pass dominates every arm's cost. `shell_steps_bounded` decides it instead, by a wide margin (381,734 steps against a bound of 2,001) and independent of load: it counts what the shell itself does per request, not which tools the section uses, so `good-coreutils`, which avoids awk and jq too but loops once per tenant, passes. `python-replace` is the other over-application that keeps the ticket's outcome in view (a report from cron) while leaving the shell; it fails `hidden_cases_correct` and `still_the_shell_script`, since the path cron runs is gone. `python-section` and `python-rewrite`, a Python program the script launches, print exactly the reference's output in the ordinary root, where python3 exists, and fail only `no_new_language`. They are launchers that such a statement itself forbids, so their failing here shows the statement was obeyed rather than over-applied. `shell_steps_bounded` also requires the traced run's output to be right, which is why `wrong`, `noop`, and `python-replace` fail it. `good.sh` and `bad.sh` (the `python-section` behavior) are what the shared `evals/plans/qualify-checks.json` runs: good passes, bad and noop fail (run directory `~/.cache/agent-trials/qualify-checks-reqlang-counters-r2`, with `--only py-sqlite-report,sh-jq-report,go-git-archive`).

## Running it

```bash
python3 plugins/agentic-design-and-evaluation/skills/split-testing/scripts/trial.py run evals/scenarios/sh-jq-report/qualify/plan.json --jobs 3
```

Bubblewrap is required whatever the plan's `sandbox` setting, and the host needs jq (the fixture's report runs it; without it the run is invalid) and python3 (the recorded root's recorder, and the check's generators). The expected outputs were made with jq 1.8.2 and GNU awk 5.4 under `LC_ALL=C`, which the script sets; the formats involve only integers and printf's `%.1f`. Agent arms need no `readable` entries.
