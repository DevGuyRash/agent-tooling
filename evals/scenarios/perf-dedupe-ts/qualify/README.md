# Qualification: `perf-dedupe-ts`

The person asks for a change to ledgerkit, a small TypeScript CLI that Node runs directly (a coffee chain's card-settlement importer with import, totals, and check commands, tests, four commits). The card processor's nightly export became rolling (the last three days), so `ledgerkit import` must skip transactions the ledger already holds. The export has no transaction ID, and the prompt says identical lines can be separate transactions: a line in the export three times with two copies in the ledger still adds one. The prompt gives the sizes as context (a ledger of about 2.4 million lines, exports of about 250k) and says nothing about speed. The defect under test is complexity: the obvious change looks each export row up in the ledger's rows with `findIndex`, `indexOf`, or a loop and splices out what it matched, which is quadratic and passes every small test. Counting the ledger's lines in a map, or sorting both sides, is near-linear.

## How the checks decide

The check copies the working directory without following links and runs `node bin/ledgerkit.ts import EXPORT --ledger LEDGER` in bubblewrap with the copy and the inputs bound read-only and only the ledger's directory writable. Required:

- `hidden_cases_correct`: eleven hand-made cases in `hidden/cases/` (a missing and a header-only ledger, an export the ledger already holds entirely, a rolling export with late settlements, more and fewer copies of a line than the ledger holds, near-identical transactions that differ only in sign, till, card, minute, store, amount, or date, Windows line endings with lower-case store codes, a ledger not in time order, an export with no lines, and an invalid export) and a generated one. A valid export must exit 0 and leave the ledger as it was with lines appended (a missing ledger gets its header first), ending in a newline, whose multiset equals the reference's; an invalid export must exit non-zero and leave the ledger byte for byte as it was. The reference (`hidden/reference/`, laid over the fixture) and the two alternative good solutions below agree exactly on the generated scaling inputs as well. Files with Windows line endings are stored with LF in this repository (whose git configuration may normalize line endings) and given CRLF by `setup.sh` and the check.
- `existing_tests_pass`: the fixture's own tests, placed beside the agent's code from the check's copies, pass with `node --test`.
- `scales_to_nightly_size`: on generated ledgers and rolling exports (`hidden/data.py`, deterministic: about 1.2M ledger lines, half the ledger the person gives, with a 240k-line export, the export they give; and a sixteenth of that, about 75k ledger lines with a 15k-line export), import exits 0 with the ledger before it intact and as many ledger lines as the reference leaves; its CPU time stays within 10 times the reference's plus 1 s at each size; and its growth in CPU time from the small input to the large one is at most twice the reference's growth.

How CPU time is measured. It is user plus system time of every process and thread in the sandbox, read with `wait4` by a small spawner process of the check's own (starting programs from the lean spawner keeps the trial process's memory out of the peak-memory measure). Inside the sandbox the command runs under a reaper of the check's, the namespace's first process (`bwrap --as-pid-1`): when node exits, the reaper kills and reaps every process still there, so child processes nobody waited for are counted too. Without it, two forked children doing 5 s of work in all, whose parent called `process.exit()` once they reported, measured 2.6 s.

How the decision is made. The measurement runs in rounds of (reference small, agent small, reference large, agent large), so the four runs one round's growth compares are close together in time and host load affects them alike. The median of up to three rounds decides growth, and measuring stops after two rounds when both fall on the same side of the bound. The agent's run is stopped as soon as its CPU time passes 10 times the reference run's just before it plus 1 s (the reaper sums the sandbox's own `/proc`), so a failing run's cost follows the reference's CPU time rather than its wall time, which grows far more with load; the size fails when that happens twice, the second time on an immediate repeat with a fresh reference run. A run is also stopped after 20 times the reference's wall time, or 60 s if that is more, a backstop for code that waits rather than computes.

Limit. A superlinear path that only a small, fixed share of the lines takes costs too little at these sizes to be reliably caught. Using a Set for lines the export holds once, and counting a line's copies among the ledger's recent lines with a scan only for the lines the export repeats (about 1 in 250), matches the reference and costs 1.7 to 2.2 times the reference's CPU time on the large input; its growth was 1.4 to 2.9 times the reference's per round under heavy load, so the check passes it in some runs and fails it in others. Raising the share of repeated lines in the generated data would catch it only by making an uncommon case common, so the generator keeps its share of about 1 in 250.

Measures, deciding nothing: medians over the rounds of the CPU seconds of the agent and the reference at both sizes, the ratios to the reference, both growths and their ratio, each round's growth ratio (`growth_vs_reference_rounds`), the peak memory at both sizes, whether the large result equals the reference's exactly and in the same order, the hand-made cases whose appended lines are in another order than the reference's (export order, earlier copies counted as held), the agent's own suite, tests added, and commits.

Every hazard leaves exactly the reference's ledger on all twelve hidden cases, so it fails only the check that targets the hazard. `hazard-used-flags` and `hazard-window` stay within the CPU bound even on the large input (about 6 to 7 times the reference's CPU time there, on a ledger half the size the person gives); the growth bound is what rejects them. `good.sh` and `bad.sh` follow the convention of the shared `evals/plans/qualify-checks.json`: good passes, bad and noop fail.

Runs, each with both perf plans at `--jobs 4` at the same time on a 24-thread host (AMD Ryzen 9 3900X), every arm as in the table each time: `~/.cache/agent-trials/qualify-perf-dedupe-ts-fix-r1` (other work only; load average about 10 to 55), `~/.cache/agent-trials/qualify-perf-dedupe-ts-fix-r2-hogs` (32 CPU-spinning and 10 memory-copying processes added at nice 19; load average about 25 to 60), `~/.cache/agent-trials/qualify-perf-dedupe-ts-fix-r3-cpuhogs` (12 CPU-spinning processes at normal priority and 4 memory-copying ones at nice 19; load average about 30 to 50), and, after a last edit that makes a stop by the reaper count as over budget whatever the outside measure says, `~/.cache/agent-trials/qualify-perf-dedupe-ts-fix-r4` (other work only; load average about 9 to 20). Checks took 14 to 100 s, 27 to 197 s, 34 to 314 s, and 14 to 99 s in those runs, the longest being `hazard-window` and `hazard-used-flags`, which run two full rounds. Across those runs and fourteen more rounds per solution measured with the check's own runners (seven at a load average of 12 to 19, seven with the nice-19 hogs at 53 to 96), the per-round growth of `hazard-window` was 5.1 to 14.7 times the reference's and that of `hazard-used-flags` 5.1 to 7.2 (22 rounds each, against a bound of 2), while the good solutions' and `breaks-existing`'s was 0.43 to 1.56 (74 rounds).

## Calibration

The reference takes 0.4 to 1.0 s of CPU on the small input and 4 to 9 s on the large one depending on load, with a peak of about 740 MB, most of it the ledger's rows; Node's start-up (0.12 to 0.25 s, its CPU time on a header-only ledger) keeps its growth at 8 to 13 rather than 16. Quadratic searches over the whole ledger go over the CPU bound on the small input. Searches limited to the export's own days are the subtler case: they do the reference's linear work plus work quadratic in the export, which at the large input costs 5 to 7 times the reference's CPU time. Over 8 times the data (a 30k-line export to 240k) their growth was only 2.5 to 3.8 times the reference's for `hazard-window` (fourteen rounds), and a review of the earlier check, which compared each program's fastest run per size with the two sizes measured minutes apart, saw it as low as 1.94 under heavy load. Over 16 times the data (15k export lines to 240k) it is 5 or more, and measuring all four runs of a round back to back keeps the comparison between programs within moments of each other. Subtracting each program's start-up time before computing growth lowered the hazards' ratios over 8 times and raised them over 16 times while widening the good solutions' spread, so the check does not. Retired-instruction counts would be steadier under load, but where the C library copies with rep-prefixed string instructions a long memmove may retire as a single instruction, which would hide exactly the splicing these hazards do; CPU time decides. The CPU bound (10 times) and growth bound (twice) leave room for solutions much slower than the reference by a constant factor.

Generating the scaling inputs takes about 7 s of the check's time; they are written fresh into the check's scratch directory on every run and never exist where the agent works.

## Running it

```bash
python3 plugins/agentic-design-and-evaluation/skills/split-testing/scripts/trial.py run evals/scenarios/perf-dedupe-ts/qualify/plan.json --jobs 4
```

Bubblewrap is required whatever the plan's `sandbox` setting. The check runs the agent's code with the node that `TRIAL_NODE` names, or else the `node` on the check's own PATH, binding that node's directory read-only into the sandbox; that node needs type stripping, and like the fixture's `package.json` this scenario calls for Node 24 or newer (it was qualified with Node 26). It uses `/usr/bin/python3` for its generator and spawner, and `/usr/bin/python3` or `/usr/local/bin/python3` for the reaper inside the sandbox (a python3 under the home is hidden there). Agent arms need no `readable` entries when node is outside the home (here `/usr/bin/node`); a node under the home needs its directory in `readable`. The check's copy leaves out `node_modules`, so a solution that adds an npm dependency fails, as the README's "no dependencies" implies.
