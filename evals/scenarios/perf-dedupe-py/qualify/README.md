# Qualification: `perf-dedupe-py`

The person asks for a `dedupe` command in shopcrm, a small Python package for an online tea shop's nightly customer export (validate, lookup, and stats commands, tests, four commits). The behavior is specified exactly in `docs/dedupe.md`: rows that share a normalized email or phone number are one person, directly or through other rows, and each person's row takes its fields by stated rules. The prompt mentions, as context, that last night's export was about 400k rows; it says nothing about speed. The defect under test is complexity: the obvious implementation compares each row with the people found so far (the repository even offers a pairwise `same_customer()`), or keeps the values seen so far in lists, which is quadratic and passes every small test. Indexing rows by normalized email and phone (a union-find, a graph search, or a sort by each key) is near-linear.

## How the checks decide

The check copies the working directory without following links and runs `python3 -m shopcrm dedupe FILE` in bubblewrap with the copy bound read-only. Required:

- `hidden_cases_correct`: eight hand-made exports in `hidden/cases/` (a chain held together by alternating emails and phones, a row late in the file that ties two people together, normalization and every kind of value that never matches, the oldest account decided by `created_at` with migrated accounts and same-second ties, the field rules with junk values and CSV quoting, a header-only export, one row, a household sharing a phone), the docs example and the fixture's sample export (both taken from the fixture when the check runs), and a generated 2,500-row export print the reference's rows. Output is compared as parsed CSV, so line endings and quoting style do not matter. The reference (`hidden/reference/`, laid over the fixture) and the three alternative good solutions below agree exactly on the generated 25k- and 400k-row exports as well.
- `existing_tests_pass`: the fixture's own tests, placed beside the agent's code from the check's copies, pass.
- `scales_to_nightly_size`: on generated exports of 25,000 and 400,000 rows (`hidden/data.py`, deterministic; 400k is the size the person gives, 25k a sixteenth of it), the command exits 0 with one row per person (as many rows as the reference prints); its CPU time stays within 10 times the reference's plus 1 s at each size; and its growth in CPU time from 25k to 400k rows is at most twice the reference's growth.

How CPU time is measured. It is user plus system time of every process in the sandbox, read with `wait4` by a small spawner process of the check's own (starting programs from the lean spawner keeps the trial process's memory out of the peak-memory measure). Inside the sandbox the command runs under a reaper of the check's, the namespace's first process (`bwrap --as-pid-1`): when the command exits, the reaper kills and reaps every process still there, so processes that nobody waited for are counted too. That matters for Python 3.14, whose default multiprocessing start method (forkserver) runs Pool workers under a server process the main process never reaps: without the reaper, a Pool doing 6 s of work measured 0.08 s, and a review found a quadratic search moved into a Pool passing the CPU and growth bounds. `hazard-pool-email` is such a solution.

How the decision is made. The measurement runs in rounds of (reference 25k, agent 25k, reference 400k, agent 400k), so the four runs one round's growth compares are close together in time and host load affects them alike. The median of up to three rounds decides growth, and measuring stops after two rounds when both fall on the same side of the bound. The agent's run is stopped as soon as its CPU time passes 10 times the reference run's just before it plus 1 s (the reaper sums the sandbox's own `/proc`), so a failing run's cost follows the reference's CPU time rather than its wall time, which grows far more with load; the size fails when that happens twice, the second time on an immediate repeat with a fresh reference run. A run is also stopped after 20 times the reference's wall time, or 60 s if that is more, a backstop for code that waits rather than computes.

Limit. Superlinear work whose cost at these sizes stays small next to the linear work is not reliably caught. Inserting each new email into a sorted list (`bisect` and `list.insert`: correct, and a quadratic memmove over an array that stays in cache) costs 1.5 to 1.9 times the reference's CPU time at 400k rows, and its growth was 1.35 to 1.84 times the reference's in fourteen rounds, so it passes. Catching it would take sizes far beyond the request.

Measures, deciding nothing: medians over the rounds of the CPU seconds of the agent and the reference at both sizes, the ratios to the reference, both growths and their ratio, each round's growth ratio (`growth_vs_reference_rounds`), the peak memory at both sizes, whether the 400k output equals the reference's exactly, the agent's own suite, tests added, whether new or changed modules use the shared `normalize_email`/`normalize_phone`/`same_customer` rather than their own, whether `contacts.py` changed, and commits.

Every hazard prints exactly the reference's rows on all eleven hidden cases, so it fails only the check that targets the hazard. `hazard-pool-email`'s 11.0 at 25k is still within the bound there, which adds 1 s to 10 times a reference of about half a second. `good.sh` and `bad.sh` (the obvious implementation) follow the convention of the shared `evals/plans/qualify-checks.json`: good passes, bad and noop fail.

Runs, each with both perf plans at `--jobs 4` at the same time on a 24-thread host (AMD Ryzen 9 3900X), every arm as in the table each time: `~/.cache/agent-trials/qualify-perf-dedupe-py-fix-r1` (other work only; load average about 10 to 55), `~/.cache/agent-trials/qualify-perf-dedupe-py-fix-r2-hogs` (32 CPU-spinning and 10 memory-copying processes added at nice 19; load average about 25 to 60), `~/.cache/agent-trials/qualify-perf-dedupe-py-fix-r3-cpuhogs` (12 CPU-spinning processes at normal priority and 4 memory-copying ones at nice 19; load average about 30 to 50), and, after a last edit that makes a stop by the reaper count as over budget whatever the outside measure says, `~/.cache/agent-trials/qualify-perf-dedupe-py-fix-r4` (other work only; load average about 9 to 20). Checks took 10 to 231 s, 15 to 417 s, 25 to 570 s, and 10 to 233 s in those runs, and the good arms 38 to 174 s. The longest are `hazard-lists` and `hazard-email-list`: both of their runs on the 400k export use up the CPU bound, 10 times a reference whose own CPU time grew from 7 s to 15 s with the load.

## Calibration

Measured with the check's own runners on that host, seven rounds per solution at a load average of 12 to 19 and seven more with the nice-19 hogs (load average 47 to 94), and in the four runs above: the reference takes 0.4 to 0.9 s of CPU at 25k rows and 7 to 15 s at 400k depending on load (a peak of about 410 MB), a growth of 14 to 20; per round, the growth of the alternative good solutions and `breaks-existing` was 0.70 to 1.28 times the reference's (96 rounds). The quadratic variants are far outside the CPU bound: `bad` is stopped on the 25k export, and the list-lookup hazards stay within the bound at 25k rows (3.7 to 11 times the reference's CPU time) and are stopped on the 400k export, which is why the larger size is the size the person gives. Start-up costs about 0.1 s, so subtracting it before computing growth changes nothing here. Why the smaller export is a sixteenth of the larger and the decision is made per round rather than from each program's fastest run per size: see the Calibration section of `perf-dedupe-ts/qualify/README.md`, whose hazards needed both. The CPU bound (10 times) and growth bound (twice) leave room for solutions much slower than the reference by a constant factor; what they reject is time that grows faster than the data.

Generating the two scaling exports takes about 7 s of the check's time; they are written fresh into the check's scratch directory on every run and never exist where the agent works.

## Running it

```bash
python3 plugins/agentic-design-and-evaluation/skills/split-testing/scripts/trial.py run evals/scenarios/perf-dedupe-py/qualify/plan.json --jobs 4
```

Bubblewrap is required whatever the plan's `sandbox` setting, and the check runs the agent's code and the reference with the `python3` on `/usr/local/bin` or `/usr/bin` inside the sandbox (3.11 or newer), its own generator and spawner with `/usr/bin/python3`, and the reaper inside the sandbox with `/usr/bin/python3` or `/usr/local/bin/python3` (a python3 under the home is hidden there). Agent arms need no `readable` entries for this scenario. A solution that relies on a package installed into the agent's own environment (outside the standard library) fails here, as the README's "standard library only" implies.
