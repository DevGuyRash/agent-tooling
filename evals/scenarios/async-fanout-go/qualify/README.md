# Qualification: `async-fanout-go`

The person asks for a new `farmctl yield` subcommand in farmctl, an existing standard-library Go tool for a solar farm. It has list and read subcommands, a client for the plant SCADA gateway's line protocol that dials with no deadline, an `internal/fakegw` package for its tests, and a few commits of history. `yield` reads every inverter (300), prints one line each sorted by name as `read` prints it, reports inverters with no answer within 2 seconds as `no answer` and ERR replies with the gateway's code and text, ends with a total line, and exits 0, 1, or 2. The Grafana agent kills it after 15 seconds. The gateway's documentation (`docs/gateway.md`) says the gateway accepts at most 16 TCP connections at a time and closes any beyond that without a reply, counts a connection until it has replied or the client closes it, holds a silent inverter's connection for up to 30 seconds, and takes a client that closes, or shuts down only its sending side, before the reply as hanging up. The prompt states the budget and points at the documented limit; it names no technique.

A sequential loop prints the right report and takes over 38 seconds. A goroutine per inverter, or a pool sized from `runtime.NumCPU`, gets dropped past 16. Racing each read against `time.After` in a `select` (the existing client has no deadline) gives up on time, but the losing goroutine keeps its connection open until the gateway's own 30 seconds end, so the gateway counts more than 16 connections once enough inverters fall silent, whatever the client's own cap, while the program still exits on time; a client that only paces its reads has no bound at all. A fixed pool of 16 workers calling the client as it is, with a collector that gives each inverter 2 seconds from when its read began and moves on (returning from main ends the workers still waiting), never goes over the limit and exits on time on an ordinary day, but each worker stays on its silent inverter's connection until the gateway's 30 seconds end, so when more inverters are silent than it has workers, the whole run waits on them.

## How the checks decide

The check copies the working directory without following links and builds `go build ./cmd/farmctl` in bubblewrap, offline (`GOPROXY=off`, `GOTOOLCHAIN=local`), with the host's Go (`TRIAL_GOROOT`, or the GOROOT the host's `go` reports). Only after the build does anything hidden reach a sandbox. Each case runs `farmctl yield` with `FARMCTL_GATEWAY` set, in its own bubblewrap sandbox (host read-only, home, `/tmp`, and `/run` hidden, its own network and PID namespaces), and `hidden/driver.py` serves the gateway on 127.0.0.1 inside that network namespace. The dataset and expected report are made in `check.py` and reach the driver on standard input. After the program exits the driver keeps the gateway listening for 2 seconds, kills everything left in the sandbox, and only then prints its verdict.

The gateway counts a connection from accept until it starts sending its reply, or until the client closes it; a client that shuts down its sending side has hung up too (a server cannot tell that from a close), as `docs/gateway.md` says and `internal/fakegw` does for every request, so the visible tests show a client that does it. When a connection arrives the gateway first drops counted connections whose client has hung up, and before refusing one it keeps doing so for up to 50 ms, so a client that closes one connection and opens the next on another CPU is never counted for the old one. A refused connection's request line is read for the record only, so a refused read still counts as asked for. The driver also records how long each connection stayed counted while the program ran (up to its exit, when the kernel closes whatever it still holds), and counts as held every connection counted longer than 8 seconds: 4 times the ticket's 2 seconds, and past the latest reply of a late inverter (5.5 s), so only a connection to a silent inverter that the client neither got a reply on nor closed can be held. A correct client's longest connection, the reference client's included, was at most 2.11 s across these runs, at load averages up to 100.

The cases:

- Main: 300 inverters. 285 answer in 30 to 150 ms; 5 slow ones answer in 1.0 to 1.2 s (within the ticket's 2 seconds); 3 late ones answer only after 3.2 to 5.5 s (so `no answer` by the ticket's rule); 4 offline ones whose connection the gateway holds for 30 s, then `ERR 504 inverter timeout`; 3 get `ERR 503 inverter fault` or `ERR 502 bus error`. LIST gives a shuffled bus order. Offline inverters are drawn from the first quarter of both the name order and the bus order; slow, late, and erroring ones from the first 60%.
- All answering: 36 inverters, some with 0 W, some with 0 Wh.
- Outage: 300 inverters, 20 offline and 30 slow, all in the first third of both orders. More inverters are silent than the gateway's limit, which separates the clients described above whatever their own cap.
- No gateway: exit 2 within 10 s.
- Existing commands: `list`, `read`, and the usage errors run one after another against a small gateway, with the arguments, environment, and expected output the fixture's tests use.

A pool sized from the CPU count (`runtime.NumCPU`, or `GOMAXPROCS`, which defaults to it) is judged alike on every host that decides: the run is invalid (not failed) when the CPUs the check may run on, which every case inherits and `NumCPU` reports, are 16 or fewer.

Timing is calibrated in the same check, and the time limit is the ticket's. The Grafana agent kills the command at 15 seconds whatever state the farm is in, so the main case and the outage are both held to 15 seconds, plus only what the host adds to a correct client's time (`_shared/fanout_timing.py`, shared with the other fan-out checks). `hidden/reference_client.py`, a correct client at the documented limit, runs first against the main dataset, up to three times, stopping once its best time is within 1.25 times its ideal time, and once against the outage. The ideal time is what it spends waiting on the gateway alone: 16 slots taking inverters in name order, each answering inverter's latency or 2 seconds for each one that must be reported as not answering (2.88 s here). The reference's best time beyond the ideal is what the host added just now, and that slack is added to the 15 seconds for both cases, so a limit is 15 s plus at most 1.4 s. When even the reference's best time is more than 1.5 times the ideal (4.3 s) the check raises and the run is invalid. The limit is additive rather than a multiple of the reference's time, which an earlier version used (15 seconds or 5 times the reference's best time for the main case, 5 times its outage time for the outage): under load the multiple rose well above the ticket's budget, so a client that is only partly bounded and would still be killed in production passed (a semaphore of 4 takes about 24 s in the outage, and the earlier outage limit was 5 times the reference's 6.1 s, at least 30 s). A sequential client cannot beat the floor (38.99 s in the main case, 79.08 s in the outage) however idle the host, and no limit reaches it (the check asserts this as it loads). The reference must also give the exact report with nothing refused and nothing held, or the check raises. The main and all-answering cases are killed only at twice the main floor (78.0 s), so a correct but slow client finishes and fails `within_budget` alone; the outage is killed 10 s past its time limit, and its report is judged only when it finished within that limit.

Required:

- `builds`: `go build ./cmd/farmctl` succeeds offline.
- `answered_inverters_correct`: one line per inverter sorted by name, each answering inverter's line exactly as `read` prints it, in the main, all-answering, and outage cases.
- `failures_handled`: `no answer` and `error CODE text` lines, the total line, exit 1 (main, outage) and 0 (all answering), and exit 2 within 10 s with no gateway.
- `within_budget`: the main case exits by itself within its time limit, having asked for every inverter, and the outage within its own (the same seconds).
- `within_limit`: the gateway refused no connection in the main, all-answering, and outage cases, and the main case asked for at least one inverter.
- `no_held_connections`: no connection held longer than 8 s in those cases, and the main case asked for at least one inverter.
- `no_work_after_exit`: no connection reached the gateway after the program exited, and no process was left, in every case; the main case asked for at least one inverter.
- `existing_commands_unchanged`: `list`, `read`, and the usage errors behave as the fixture's tests expect, run through the built program (observed from outside, so a change to internal signatures that keeps the behavior is not held against it).

Measures, deciding nothing: `build_error`, `time_limit_seconds`, `hard_limit_seconds`, `reference_seconds`, `reference_ideal_seconds`, `host_slack_seconds`, `reference_longest_connection_seconds`, `reference_runs`, `sequential_floor_seconds`, `outage_time_limit_seconds`, `outage_reference_seconds`, `main_seconds`, `main_exit`, `main_killed`, `allok_seconds`, `outage_seconds`, `outage_exit`, `outage_killed`, `down_exit`, `down_seconds`, `peak_connections`, `outage_peak_connections`, `most_attempted_at_once`, `refused`, `outage_refused`, `abandoned_connections`, `outage_abandoned_connections`, `held_connections`, `outage_held_connections`, `longest_connection_seconds`, `outage_longest_connection_seconds`, `connections_without_request`, `open_at_exit`, `mean_connections_open`, `connections_total`, `list_requests`, `inverters_asked`, `most_reads_for_one_inverter`, `late_connections`, `survivors`, `cpus_available`, `problems`, `main_stderr_tail`, `fixture_tests` (the fixture's own Go tests alone, every `_test.go` the agent left removed from that copy and the fixture's placed back, run by name in their packages), `fixture_tests_output`, `own_suite` (`go test ./...` on the tree as the agent left it), `commits_added`, `final_words`.

## Running it

```bash
python3 plugins/agentic-design-and-evaluation/skills/split-testing/scripts/trial.py run evals/scenarios/async-fanout-go/qualify/plan.json --jobs 4
```

The check needs bubblewrap, `/usr/bin/python3` (for the driver and the calibration client), the host's Go, and more than 16 CPUs, whatever the plan's `sandbox` setting, and it is invalid where the reference's best time is more than 1.5 times its time waiting on the gateway. Agent arms need Go readable inside their own confinement only when it lives under the home: here `go` resolves to `/usr/lib/go`, so they need no entry, while a Go under the home needs its GOROOT in `readable`. A check takes about 40 s for a good solution and up to about 120 s for one that runs sequentially or waits out the gateway's 30 s.
